## Executive summary

This Flutter port of the Thai auto-parts POS is fundamentally sound on its data/money core: the transactional repositories faithfully mirror db.js (saveSale strict-decrement, createReturn proportional reversal, receivePO weighted-average cost, atomic snapshot import), and 10 repository unit tests cover that layer. The audit surfaced ONE genuine critical defect and a small cluster of high/medium issues that should gate any production cutover.

The single must-fix-now bug is the dead Quote→Checkout hand-off: pendingQuoteForCartProvider is written by QuotesScreen but never read by CheckoutScreen, so "convert to sale" / "edit quote" land the user on an EMPTY cart — and the EDIT path deletes the quote first, making it UNRECOVERABLE data loss. This single root cause was independently flagged across three review dimensions (state-mgmt, routing-nav, ux-flows). Two high-severity issues follow: (1) web backup/CSV export is dart:io-only and silently fails on the Web target — meaning a web shop has NO data-safety path at all (a browser clear loses everything); and (2) the ClosingReport dialog hard-codes a two-column 320px layout that collapses/overflows on phones.

Beyond those, the dominant themes are pervasive responsive-layout fragility (5 dialogs/screens with fixed-width Rows and no narrow fallback), a wholly bypassed design system (brand fonts never applied on screen, ~250 ad-hoc TextStyles, 51 raw color literals, under-adopted component kit), and broad a11y gaps (no Semantics, sub-44dp touch targets, multiple WCAG-failing brand colors at small sizes). Most data-layer "issues" (FP money drift, missing FKs/indexes, ordering tiebreaks, receivePO double-receive) are faithful ports of pre-existing db.js behaviour and were correctly downgraded to latent-hardening items — real, but not regressions. The app is demonstrably solid where it matters most (atomic transactions, money math, tested repos); the work is finishing the presentation layer and the web target.

## Top fixes (prioritized)

### #1 🔴 CRITICAL — Quote→Checkout hand-off is dead: convert/edit lands on an empty cart; EDIT permanently loses the quote
- **Dimension:** state-mgmt / routing-nav / ux-flows (same root cause)
- **File:** `lib/presentation/screens/checkout_screen.dart + lib/presentation/screens/quotes_screen.dart + lib/presentation/providers/pending_quote_provider.dart`
- **Location:** pendingQuoteForCartProvider written at quotes_screen.dart:134 (_loadToCart), set from _handleConvert (114-130) and _handleEdit (which deletes the quote at 110-111 first); NEVER consumed in checkout_screen.dart
- **Why it matters:** The entire reason QuotesScreen exists in the money path. JS CheckoutScreen.jsx:46-65 loads the quote into the cart via the loadQuote effect + validateItems. In Flutter nothing reads the provider, so convert/edit navigate to an empty checkout. EDIT runs deleteQuote BEFORE the dead hand-off, so the quote's items/discount/customer/mechanic are unrecoverable. CONVERT marks status='converted' yet nothing reaches the cart, stranding the quote.
- **Fix:** In CheckoutScreen.build (or a one-shot ref.listen/initState) read pendingQuoteForCartProvider, run the existing _validateItems (checkout_screen.dart:261) against the fresh _productsProvider list, CartNotifier.setLines(res.safe), apply discount/customer/mechanic, surface res.issues via _warn, then .clear() the provider — mirroring CheckoutScreen.jsx:47-65. Critically, swap _handleEdit order so the quote is NOT deleted until after the cart consumes it (or restore on failure).

### #2 🟠 HIGH — Backup + CSV export are dart:io-only — silently broken on the Web target (no data-safety path on web)
- **Dimension:** security-integrity
- **File:** `lib/presentation/screens/settings_screen.dart`
- **Location:** _handleExport (560-576), _download (1192-1208); import 'dart:io' at line 17
- **Why it matters:** Web is a first-class target (web DB was just wired so flutter run -d chrome boots). On web getApplicationDocumentsDirectory()/dart:io File throw, so BOTH the JSON backup and all three CSV exporters fail with a confusing Thai error toast. For an offline-first app whose ONLY data-safety mechanism is manual export (cloud sync not built), a web user can never back up — one browser data-clear loses everything.
- **Fix:** Branch export on kIsWeb: on web use universal_html / a Blob + anchor download (or package:web) to save the JSON/CSV; keep the dart:io path for native. Isolate the io import behind a conditional import so the web build does not pull dart:io.

### #8 🟡 MEDIUM — On-screen receipt + ~10 other surfaces render Thai labels in bare 'monospace' — typography/parity drift (tofu on Thai-less platforms)

### #9 🟡 MEDIUM — Unhandled async errors + missing confirmations on cash/quote/park/close write paths

## Cross-cutting themes

- Faithful-port-of-a-pre-existing-db.js-quirk: the single largest pattern. Money FP drift on accumulators, missing FK enforcement/indexes, receivePO double-receive, round2 .round() vs Math.round, createReturn totalCredit fallback, unconditional parked-resume delete, csvSafe index-0-only guard, ungated destructive restore, unencrypted PII — all correctly identified as parity-matching legacy behaviour, NOT regressions. Implication: most data-layer findings are latent-hardening items; fixing them unilaterally risks diverging from the binding spec and should be a deliberate dual-app decision.
- Responsive layout never designed for phones: 5+ fixed-width Row layouts (ClosingReport 320px, LabelPrinter 300px, Suppliers 260px, Mechanics 9-col, Returns stepper) have no narrow fallback and overflow with real data. The fix is the same LayoutBuilder breakpoint pattern that already exists in cash_drawer _drawerTab and was applied to CustomersScreen — apply it consistently.
- The design system is advisory, not enforced: brand fonts never applied on screen, ~247 ad-hoc TextStyles + 302 hardcoded fontSizes bypass the type scale, 51 raw Color literals duplicate AppColors, the component kit (AppCard/AppButton) is under-adopted vs 98 inline BoxDecoration cards + 61 raw buttons, and AppTheme lacks CardTheme/ButtonTheme. Root cause: no semantic type/color/radius tokens and missing component themes, so divergence is the default.
- Accessibility was not a design input: zero Semantics in lib/, multiple WCAG-failing brand colors at the small sizes actually used, several sub-44dp touch targets on the highest-frequency register controls, no global textScaler clamp + fixed-height chrome. Compounding for an all-day shop-floor app used by older staff.
- Migration introduced new async-failure surfaces the JS app never had: localStorage writes were synchronous/non-throwing; Drift writes (esp. on web IndexedDB / locked SQLite) can throw, but several handlers (park, save-quote, cash open/close) lack try/catch, so failures are silent. A systematic 'every write handler shows a Thai error toast' pass closes this.
- Test coverage is strong on data/transactions but absent on presentation and on the highest-leverage helpers: 10 repository tests cover the money/transaction core well, but there are no UI interaction/golden tests (the 'route smoke test' pumps a bare Scaffold, never the router), no money/csv helper unit tests, and the most rounding-sensitive refund paths are untested.
- N+1 / quadratic query patterns recur but are low-urgency at single-shop scale: receivePO re-SELECTs all products per line, Returns fires 2 unindexed queries per card, getReturns/getPOs/getQuotes use 1+N loops, reports aggregation is O(S·I·P), _catColorsProvider re-reads categories per category. SalesRepository._attachItems already shows the correct isIn(ids)+in-memory-grouping idiom to copy; combined with missing indexes this is gradual multi-year degradation, not a current bug.

## What is genuinely solid

The few rounding/format divergences from JS are confirmed unreachable in practice (operands already round2'd) or purely cosmetic.

### DB schema design — 10 findings

1. 🟡 **MEDIUM** — Declared foreign keys are never enforced — no PRAGMA foreign_keys = ON / beforeOpen, so orphaned child rows are admitted silently  
   `lib/data/db/database.dart` : MigrationStrategy (L70-75) — onCreate only, no beforeOpen _(verdict P/high)_  
   - **Impact:** SQLite has foreign-key enforcement OFF by default and Drift does NOT turn it on unless you do so in beforeOpen. The five `.references(...)` declarations in tables.dart (SaleItems.saleId, PoItems.poId, ReturnItems.returnId, QuoteItems.quoteId, DrawerEntries.shiftId) therefore emit FK clauses in the DDL that are completely inert. A SaleItem can point at a non-existent saleId; deleting a Sale leaves orphan SaleItems (no ON DELETE CASCADE either). The snapshot importer deletes saleItems then reinserts (snapshot_repository L570, L668) relying on no enforcement — which works only because FKs are off. This is a latent corruption surface the schema claims to protect against but does not.  
   - **Fix:** Finding is factually correct but over-severitied. Downgrade high -> medium: declared FKs are genuinely inert (no PRAGMA foreign_keys=ON / beforeOpen; 5 REFERENCES clauses confirmed in database.g.dart), but no current code path produces orphans — deleteQuote, deletePO, and the importer all delete children-first in transactions, and Sales are voided not deleted. This is a latent referential-integrity / defense-in-depth gap, not an active corruption or broken core flow. Recommendation is valid; if implemented, re-verify existing delete paths under enforcement.

2. 🟡 **MEDIUM** — No UNIQUE constraint on Products.partNo — duplicate part numbers can be persisted despite app-layer guard  
   `lib/data/db/tables.dart` : Products.partNo L16 (`TextColumn get partNo => text()();`) _(verdict P/high)_  
   - **Impact:** db.js treats partNo as the natural key: addProduct returns null on dup, updateProduct returns false on collision, and receivePO matches incoming PO lines to products BY partNo (db.js L459 `p.partNo.toLowerCase() === item.partNo.toLowerCase()`). With no DB UNIQUE backstop, any path that bypasses the repository check — the snapshot importer (which inserts products directly, snapshot_repository L595), a concurrent add, or a future bulk import — can create two products with the same partNo. receivePO would then update only the first match, silently corrupting stock/WAC accounting for the other. The check is also case-insensitive in code but the DB stores raw case, so a UNIQUE(partNo) alone wouldn't fully match; a COLLATE NOCASE unique index is needed for true parity.  
   - **Fix:** Confirm the defect and the recommendation (add a COLLATE NOCASE unique index on partNo via customConstraints, and have importLegacyBackup validate/upsert). Downgrade severity high -> medium: the only true bypass today is the snapshot importer fed with non-canonical (corrupted/hand-edited/future-bulk) data; the live add/update UI path is guarded and a faithful JS snapshot is dup-free, so this is a latent data-integrity backstop gap rather than wrong behaviour on a common flow.

3. 🟡 **MEDIUM** — Zero secondary indices on hot foreign-key / filter / sort columns  
   `lib/data/db/tables.dart` : SaleItems.saleId L105; ReturnItems.returnId L161; PoItems.poId L131; QuoteItems.quoteId L192; Returns.saleId L142; Movements.productId L202; Suppliers.productId L218; CreditPayments.mechanicId L231; DrawerEntries.shiftId L256; Sales.date L94 / customerId L88 / mechanicId L90 _(verdict P/high)_  
   - **Impact:** Every aggregate read does a full-table scan + in-memory join. e.g. sales_repository getRefundedQty filters returns by saleId (L164) and returnItems by returnId IN (...) (L169-170); _attachItems filters saleItems by saleId IN (...) (L182-183); suppliers_repository.getSuppliersForProduct, movements by productId, credit payments by mechanicId, shift entries by shiftId all scan. Sales are sorted by date on every getSales/watchSales (L149,156) with no index on date. On a shop running for years this degrades from O(1) index seeks to O(n) scans on the largest tables (sales, saleItems, movements). For an offline POS this is a real, growing perf defect.  
   - **Fix:** Confirm the index gap and prioritize: (1) Sales.date for the orderBy on the largest table; (2) the true FK WHERE/IN columns SaleItems.saleId, ReturnItems.returnId, Returns.saleId, PoItems.poId, QuoteItems.quoteId, DrawerEntries.shiftId, Suppliers.productId. Drop/deprioritize CreditPayments.mechanicId and Movements.productId from the recommendation — those reads are full-table fetch-then-filter-in-memory (mechanics_repository.getCreditPayments L119-126; movements_repository getMovements L21), so an index there is moot until those queries push the filter into SQL. Note: adding @TableIndex requires bumping schemaVersion and a build_runner regen on an ASCII path per CLAUDE.md.

4. 🟡 **MEDIUM** — Mechanics.totalCredit column is dead/ambiguous — db.js never maintains it; only totalDiscount is used  
   `lib/data/db/tables.dart` : Mechanics.totalCredit L71 (`RealColumn get totalCredit => real().withDefault(const Constant(0))();`) _(verdict P/high)_  
   - **Impact:** totalCredit is a write-once-zero column that is never incremented anywhere in the Flutter port, mirroring a legacy migration fallback in JS. ### ❌ [money-points] NumberFormat HALF_EVEN rounding in baht() differs from JS toLocaleString HALF_UP at the display boundary
The finding's central claim — that NumberFormat in baht() uses HALF_EVEN rounding and therefore differs from JS toLocaleString's HALF_UP — is factually wrong. I traced the actual rounding path: lib/core/utils/money.dart:8 declares NumberFormat('#,##0.##') with NO roundingMode set; baht() (line 11) calls _bahtFormat.format(v). In intl 0.20.2, NumberFormat's rounding is in src/intl/number_format.dart:609-625 (_round), which for a num delegates to Dart's num.round() (line 614). Dart's round() is round-half-AWAY-from-zero (HALF_UP), not banker's rounding. A runtime probe in the project confirmed this: 0.125 -> 0.13 and 0.135 -> 0.14 (both round up); (2.5).round()=3, (0.5).round()=1. Under HALF_EVEN, 0.125 would format to 0.12 — it does not. So intl rounds the SAME direction as JS Math.round / toLocaleString (half-up); there is no mode mismatch.

The probed symptom baht(2.675)=฿2.67 is genuine, but its cause is (a) the IEEE-754 representation of 2.675 as 2.67499999… (2.675*100=267.499…), so HALF_UP also yields 2.67; and (b) the 2-digit precision cap of '#,##0.##'. The finding itself concedes the FP part. The only true divergence vs JS is precision width: JS toLocaleString() (used pervasively in the legacy app, e.g. CheckoutScreen.jsx:432 subtotal.toLocaleString(), CashDrawer.jsx) defaults to maximumFractionDigits:3, so 2.675 displays as ฿2.675, whereas Flutter caps at 2 and shows ฿2.67 — verified JS via node: (2.675).toLocaleString()='2.675'. But that is a precision-cap issue, which the finding explicitly attributes to a SEPARATE '3-decimal precision finding' and defers its fix there. The recommendation to set a half-up rounding mode is a no-op since intl already rounds half-up.

Net: the cited code does not do what the finding claims (no HALF_EVEN). The diagnosed root cause is incorrect; the residual real divergence is owned by a different finding. Reject this one; the cosmetic precision-cap concern belongs to the 3-decimal precision finding (recommend NumberFormat('#,##0.###')).
