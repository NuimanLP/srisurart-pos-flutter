Migration plan — draft for review

Riverpod → flutter_bloc

Full replacement of Riverpod with flutter_bloc across the Srisurart POS app: DI, the four stateful controllers, and ~20 one-shot data loads. One open decision below needs your call before implementation starts.

Scope: Flutter/ 20 files in lib/ + 3 tests touch Riverpod today CONTRACT.md §0.5, §1, §3, §4, §5, §11 all reference it 2026-07-14
Decision needed

The ~20 one-shot data loads (FutureProvider) are the single biggest lever on how much code this migration adds. See “The one decision that changes the whole plan” below before Step 5 starts.

Ordering risk

quotes_screen.dart writes to pendingQuoteForCartProvider (hand-off to checkout on quote-convert); checkout_screen.dart reads and ref.listens the same provider to prime the cart. If quotes_screen.dart converts to PendingQuoteCubit in the parallel Phase 2 batch while checkout_screen.dart is still deferred to Step 7, the old Riverpod listener on the checkout side simply stops firing — no crash, no analyzer error, just a silently empty cart on quote-to-checkout. This is the exact regression quote_to_checkout_test.dart exists to catch. PendingQuoteCubit's two call sites must convert together, not independently — see the revised sequencing below.

Decision point

The one decision that changes the whole plan

The 13 repository providers and the 4 stateful controllers have an obvious 1:1 target in flutter_bloc. The ~20 FutureProvider one-shot loads don't — FutureProvider is a Riverpod-only convenience with no direct flutter_bloc equivalent. This is the actual scope lever: pick one default policy so the 20 sites aren't each re-litigated during implementation.

OptionWhat it looks likeCost / risk
A — FutureBuilder + RepositoryProvider
recommended		 Call context.read<ProductsRepository>().getAll() directly inside a FutureBuilder in the widget. No Cubit, no state class. Least code, matches what FutureProvider was actually doing. Loses Riverpod's built-in "invalidate and refetch" — a manual setState/key-based refresh is needed anywhere a screen currently expects a reload after a write (e.g. checkout re-fetching stock after a sale).
B — thin Cubit per load Each site gets an XCubit with Initial/Loading/Loaded/Error states and a load() method. Consistent with the 4 "real" Cubits, explicit refetch via a method call. ~20 extra small files/classes for what was previously a one-line provider — the boilerplate cost flagged earlier in this conversation.
C — Cubit only where refetch is needed, FutureBuilder elsewhere Audit the 20 sites; use A by default, upgrade to B only where the screen currently relies on ref.invalidate/rebuild-triggered refetch. Right-sized, but requires the case-by-case audit up front (Step 5 below) rather than a blanket rule — slightly more planning time, least wasted code.
Corrected count

A second review pass grepped every site directly — the split is the opposite of what this plan first assumed. 15 of the 20 loads are ref.invalidated after a write, not just checkout's: customers_screen.dart:58, mechanics_screen.dart:66-67,305, quotes_screen.dart:54, returns_screen.dart:80-82, purchase_orders_screen.dart:45-46, cash_drawer_screen.dart:124, plus checkout's 6 (checkout_screen.dart:419,450,484,669-676). Only 5 are truly one-shot: reports_screen.dart:38, vehicle_search_screen.dart:42, checkout's _categoriesProvider/_catColorsProvider (lines 186, 190), and closing_report.dart:117.

Recommendation: still C, but every refetch is within its own screen (this app has no cross-screen state preservation — app_router.dart uses a plain ShellRoute, so a screen re-fetches on every visit regardless). That means "refetch" for 15 of the 20 sites is satisfiable by a StatefulWidget just re-running its FutureBuilder's future via setState — no Cubit required for any of the 20, provided the implementer follows one rule: create the future in initState/an explicit refresh method, never inline in build (an inline future re-runs on every rebuild, which is the actual bug a naive FutureBuilder port risks — not "loses refetch," but "refetches too often" or, if memoized wrong, "never refetches"). Reserve an actual Cubit for checkout only if its 6 loads end up sharing enough refresh logic to be worth centralizing — a judgment call for whoever does Step 7, not a rule to decide now.

Implementation

Migration sequence

Both frameworks can live in the widget tree at once — ProviderScope and MultiRepositoryProvider/MultiBlocProvider are just separate InheritedWidgets with no conflict. That means this doesn't have to be a big-bang cutover: root wiring goes in once, then screens convert one at a time (matching the existing 1:1 screen-ownership rule in CONTRACT §3/§5), and flutter_riverpod only comes out at the very end once nothing references it.

Phase 1 — foundation (blocks everything else)

  • Add packages, don't remove anything yet

    pubspec.yaml: add flutter_bloc + bloc. Leave flutter_riverpod in place — both coexist through the whole migration.

  • Stand up the repository DI tree

    New repository_providers.dart with 13 RepositoryProvider entries mirroring today's providers.dart + shift_providers.dart. Wire MultiRepositoryProvider in main.dart alongside (not instead of) the existing ProviderScope.

  • Port ThemeModeCubit + FontScaleCubit — reader and writers together

    Direct ports of their Notifiers (same methods, same persistence calls), wired via MultiBlocProvider at app root. This step must also convert every writer's specific call site in the same pass, not just app.dart's read side — a second review found the same bug class as the quotes/checkout coupling: app_shell.dart:299 (theme toggle) and settings_screen.dart:489,633,673 (theme + font-scale pickers, the 🎨 ธีม tab) all write to these two providers. If the read side (app.dart) converts to Cubit while these writers are still on the old Notifier, the toggle/picker keep persisting to shared_preferences but silently stop repainting the app — no crash, no analyzer error, just a UI that looks unresponsive. This only needs to touch those specific lines, not convert app_shell.dart/settings_screen.dart wholesale — their other repo reads stay on Riverpod until their normal Phase 2 slot, since coexistence is fine within a single file.

  • Port PendingQuoteCubit (state shape only, for now)

    Direct port of PendingQuoteNotifier. Wire it in, but hold off converting its two call sites (quotes_screen.dart write, checkout_screen.dart read) until Step 5 below — same coupling risk as the theme/font-scale pair above.

Phase 2 — convert consumers, screen by screen

  • Convert 9 of the 11 screens' repository reads

    Per screen (its own file + the sub-views it owns, per CONTRACT §5): swap ref.watch(xRepoProvider) → context.read<XRepository>(), drop Consumer(Stateful)Widget where nothing else needs it. This is the largest mechanical pass and each of these screens is independent — except quotes_screen.dart, held out of this batch (see next step) — see Files & Sequencing below for parallelization.

  • Convert PendingQuoteCubit's two call sites together

    quotes_screen.dart writes to pendingQuoteForCartProvider (hand-off on quote-convert); checkout_screen.dart reads + ref.listens it to prime the cart. Converting one side without the other breaks the hand-off silently (no crash — the old listener just never fires). Convert both call sites in the same pass, immediately before or alongside Step 7, not in the parallel Step 4 batch.

  • Apply the FutureProvider policy from the decision above

    Convert the ~20 one-shot loads per whichever option was chosen. Do this in the same pass as the screen it lives in, not as a separate sweep.

  • Convert shared widgets outside the 1:1 screen model

    app_shell.dart (theme toggle + settings watch) and closing_report.dart (6-repo aggregate load) — do these after the screens that embed them are otherwise converted, so there's no half-Riverpod/half-Bloc state inside one widget.

  • Port CartCubit — do this alone, last among the conversions

    checkout_screen.dart's CartNotifier has validation methods (add, setQty, setPrice) that return a String? error message synchronously alongside mutating state — this maps cleanly onto a Cubit method (emit + return in the same call, no event indirection needed), but it's the most stateful, most-touched file, plus it owns the 6 co-located data loads.

Phase 3 — close out

  • Rewrite CONTRACT.md §4

    Replace the provider table with the Cubit/RepositoryProvider table. Keep the repository list itself unchanged — only the DI mechanism changed, not the domain boundary.

  • Update the 3 Riverpod-dependent tests

    route_smoke_test.dart, quote_to_checkout_test.dart, closing_report_layout_test.dart — replace ProviderScope overrides with MultiRepositoryProvider/MultiBlocProvider test harnesses, keeping the same NativeDatabase.memory() seam.

  • Remove Riverpod and verify

    Delete the old provider files, drop flutter_riverpod from pubspec.yaml. Run dart analyze (never flutter analyze — non-ASCII path constraint per CLAUDE.md), flutter test, then a manual pass through all 11 screens.
