# 01 — Product & Pitch: เราสร้างอะไร ทำไม เพื่อใคร ต่างจากคนอื่นยังไง

บทนี้ตอบคำถาม: "ก่อนจะดูว่าระบบ**ทำงานยังไง** — ระบบนี้**มีไว้ทำไม** แก้ปัญหาอะไรของร้านจริง
และถ้าต้องยืนเล่าให้อาจารย์ฟัง 10 นาที เราจะเล่าอะไร โดยไม่โม้เกินของจริง"

> 📌 บทนี้เป็นทั้ง "บทเรียน" และ "บทพูด (pitch)" ที่ทีมใช้นำเสนออาจารย์
> ทุกประโยคที่อ้างว่าระบบ "ทำได้" มี path ไฟล์จริงในวงเล็บให้ตามไปเปิดดู
> ประโยคไหนที่ยังเป็นแค่ความตั้งใจหรือสมมติฐาน จะติดป้ายไว้ชัดเจน

## 🧱 ปูพื้นฐาน: product คิดยังไง (ก่อนแตะโค้ด)

บทอื่นในชุดนี้สอน "ท่า" ทางวิศวกรรม — transaction, RLS, CI/CD ฯลฯ บทนี้ถอยออกมาหนึ่งก้าว
แล้วถามว่า **"ท่าพวกนั้นมีไว้เพื่อใคร"** เพราะถ้าตอบข้อนี้ไม่ได้ ท่าที่เก่งแค่ไหนก็อาจแก้ปัญหาผิดข้อ

### 1. Problem → Solution → Value

ลองนึกถึงร้านข้าวมันไก่หน้ามหาลัย:

```
Problem (ปัญหา)     : คิวยาว ลูกค้ารอ 15 นาที แล้วเดินหนี
Solution (ทางแก้)    : ให้สั่งผ่าน QR ล่วงหน้า
Value (คุณค่าที่ได้)  : ขายได้มากขึ้นช่วงเที่ยง, ลูกค้าไม่หนี
```

- **Problem** = สิ่งที่เจ็บจริงของคนจริง (ไม่ใช่ "ร้านนี้ยังไม่มีแอป" — นั่นคือทางแก้ที่แอบใส่มาในรูปปัญหา)
- **Solution** = สิ่งที่เราสร้าง
- **Value** = สิ่งที่เปลี่ยนในชีวิตเขาหลังใช้ของเรา วัดได้เป็นเงิน เวลา หรือความเสี่ยงที่ลดลง

กับดักที่นักศึกษาวิศวะชอบตก: เริ่มจาก solution ("อยากลองทำ Flutter + NestJS") แล้วค่อยหาปัญหามารองรับ
บทนี้จะเริ่มจากปัญหาของร้านก่อนเสมอ

### 2. User vs Customer vs Owner — สามคนนี้ไม่ใช่คนเดียวกัน

| บทบาท | นิยาม | ในร้านอะไหล่ |
|---|---|---|
| **User** (ผู้ใช้) | คนที่กดหน้าจอจริงทุกวัน | พนักงานหน้าร้าน / คนคิดเงิน |
| **Customer** (ผู้ซื้อ product) | คนที่ตัดสินใจจ่ายเงินหรือเลือกใช้ระบบ | เจ้าของร้าน |
| **Owner / stakeholder** | คนที่ได้ผลจากตัวเลขที่ระบบให้ | เจ้าของร้าน (อยากรู้กำไร), ช่าง/อู่ (อยากรู้ยอดค้าง) |
| **End customer** (ลูกค้าของร้าน) | ไม่แตะระบบ แต่ได้รับผล | คนมาซื้ออะไหล่, ช่างที่มาเบิกของ |

ทำไมต้องแยก: user อยากได้ "กดน้อย เร็ว" แต่ customer อยากได้ "ตัวเลขถูก ตรวจย้อนได้"
สองอย่างนี้บางทีขัดกัน — เช่น ระบบบังคับให้ยืนยันก่อนขายเครดิตเกินวงเงิน (ช้าลงหนึ่งคลิก
แต่เจ้าของร้านไม่โดนหนี้บาน) product ที่ดีต้องชั่งน้ำหนักทั้งสองฝั่ง

### 3. Feature vs Benefit

- **Feature** = สิ่งที่ระบบทำ ("คิดต้นทุนเฉลี่ยถ่วงน้ำหนักตอนรับของ")
- **Benefit** = สิ่งที่คนได้ ("รู้กำไรจริงของแต่ละบิล แม้ของแต่ละล็อตจะซื้อมาคนละราคา")

เวลา pitch ให้พูด **benefit ก่อน แล้วค่อยพิสูจน์ด้วย feature** — อาจารย์และเจ้าของร้านจำ benefit ได้
ส่วน feature เป็น "หลักฐาน" ว่าเราทำได้จริง

### 4. MVP (Minimum Viable Product)

**MVP** = ของชิ้นเล็กที่สุดที่ยังแก้ปัญหาหลักได้จริง แล้วเอาไปให้คนจริงใช้เพื่อเรียนรู้

Analogy: อยากเปิดร้านกาแฟ → MVP ไม่ใช่ตึกสามชั้น แต่คือรถเข็นขายกาแฟหน้าคณะหนึ่งอาทิตย์
ดูว่ามีคนซื้อไหม

ในโปรเจกต์นี้ MVP จริงๆ คือ **build offline-first (Drift) ที่ร้านใช้อยู่ทุกวันตอนนี้** — ขาย ตัดสต็อก
คืนของ ปิดกะ ได้บนเครื่องเดียว ส่วน server multi-tenant คือ "ขั้นถัดไป" ที่สร้างบนบทเรียนจาก MVP

### 5. Product–Market Fit (PMF)

**PMF** = จุดที่ product ตรงกับความต้องการของตลาดจนคนอยากใช้ต่อเอง (และยอมจ่าย)

พูดตรงๆ: **เรายังไม่มี PMF** เรามีแค่ "product–**shop** fit" กับร้านเดียว (ร้านศรีสุรัตน์)
ถ้าจะอ้าง PMF ต้องมีร้านที่สอง สาม ที่ใช้แล้วไม่อยากเลิก — ซึ่งยังไม่มี (ดูหัวข้อ 7 ธุรกิจ)

### 6. Competitive analysis — ทำไมต้องดูคู่แข่ง

ร้านไม่ได้เลือกระหว่าง "ใช้ของเรา" กับ "ไม่ใช้อะไร" แต่เลือกระหว่าง:
สมุด + Excel, แอป POS สำเร็จรูปรายเดือน, โปรแกรมร้านอะไหล่แบบซื้อขาด, หรือของเรา

การวิเคราะห์คู่แข่งที่ดีต้อง:
1. ใช้**ข้อมูลที่มีแหล่งอ้างอิง** (หน้าราคา/ฟีเจอร์ของผู้ขาย) ไม่ใช่ความจำหรือความรู้สึก
2. บอก**จุดที่เราแพ้**ด้วย — ถ้าตารางเทียบมีแต่ ✅ ฝั่งเรา คนฟังจะไม่เชื่อทั้งตาราง
3. แยก "ไม่มี" กับ "ไม่พบข้อมูลสาธารณะ" ออกจากกัน (หาไม่เจอ ≠ ไม่มี)

### 7. ทำไมวิศวกรต้องเข้าใจ "ทำไม" ของ product

ตัวอย่างจริงจาก repo นี้: เจ้าของร้านบอกว่า "ไม่รู้ว่ากำไรกี่บาท" ถ้าวิศวกรคิดแค่ "เพิ่มหน้ารายงานกำไร"
จะได้หน้าจอที่คำนวณกำไรจาก **ต้นทุนปัจจุบัน** — ซึ่ง**ผิด** เพราะทุกครั้งที่รับของล็อตใหม่ ต้นทุนเปลี่ยน
แล้วกำไรของบิลเดือนที่แล้วก็เปลี่ยนตามย้อนหลัง (บั๊กนี้เกิดขึ้นจริง บันทึกใน
`docs/Backend_design/adr/0008-cost-at-sale.md`) คนที่เข้าใจ "ทำไม" จะรู้ว่าเจ้าของต้องการ
"**กำไรที่เกิดขึ้นจริงตอนขาย**" ไม่ใช่ "ตัวเลขที่ชื่อว่ากำไร" → จึงต้องเก็บต้นทุน ณ วันขายไว้ในบิล

สรุป: **"ทำไม" กำหนดว่าโค้ดที่ถูกหน้าตาเป็นยังไง** ไม่ใช่แค่ว่าต้องมีหน้าจออะไร

## 🔥 ปัญหาจริงของร้าน (คำของเจ้าของโปรเจกต์)

นี่คือปัญหาที่ร้านศรีสุรัตน์เจอจริงก่อนมีระบบ (สรุปความจากเจ้าของโปรเจกต์ ไม่ได้แต่งเพิ่ม):

| # | ปัญหา (Pain) | ผลที่ตามมา |
|---|---|---|
| P1 | ส่วนใหญ่**เขียนบิลด้วยมือ** | ช้า, ลายมืออ่านยาก, บิลหาย, ไม่มีอะไรรวมยอดให้ |
| P2 | **ไม่แน่ใจว่าของในสต็อกเหลือไหม** | รับปากลูกค้าแล้วของหมด หรือสั่งของซ้ำทั้งที่ยังมี |
| P3 | **ไม่แน่ใจราคา** เพราะจำราคาไม่ได้ + ของที่เข้าคนละล็อตต้นทุนต่างกัน | อาจบอกราคาผิด — ขายขาดทุนโดยไม่รู้ตัว หรือแพงจนลูกค้าหนี |
| P4 | **ไม่รู้ว่าวันนี้ยอดจ่าย / ยอดเงินเท่าไหร่** | ปิดร้านแล้วเงินในลิ้นชักไม่ตรง ไม่รู้ว่าขาดตรงไหน |
| P5 | **ไม่รู้ว่าช่างใช้เครดิตไปเยอะแค่ไหน** | หนี้ค้างบาน ทวงไม่ถูกคน ไม่รู้ว่าควรหยุดให้เครดิตเมื่อไหร่ |
| P6 | **ไม่รู้ว่ากำไรกี่บาท** | ขายเยอะแต่ไม่รู้ว่ารวยขึ้นหรือจนลง |
| P7 | **ไม่รู้ยอดขายเท่าไหร่** | ตัดสินใจอะไรไม่ได้ (จ้างคนเพิ่ม? ขยายร้าน?) |
| P8 | **ไม่รู้ว่าอะไรขายดี** | สั่งของผิดตัว เงินจมกับของที่ไม่หมุน |

ขนาดของปัญหา (บิลต่อวัน, จำนวนรายการสินค้า, ยอดหนี้ช่างรวม) — **(รอตัวเลขจริงจากร้าน)**
เราไม่แต่งตัวเลขพวกนี้ขึ้นเอง

> 💡 สังเกตว่าปัญหา 8 ข้อนี้แบ่งได้ 2 กลุ่ม:
> **"งานหน้าร้าน"** (P1–P3: ขายให้ถูก เร็ว) และ **"ความมองไม่เห็นของเจ้าของ"** (P4–P8: รู้ตัวเลข)
> กลุ่มแรกคือสิ่งที่ user (พนักงาน) รู้สึก กลุ่มหลังคือสิ่งที่ customer (เจ้าของ) จ่ายเงินเพื่อแก้

## 🎤 One-liner, Elevator pitch และ "หนึ่งวันที่ร้าน"

### One-liner (ประโยคเดียว)

> **ระบบขายหน้าร้านสำหรับร้านอะไหล่รถยนต์ไทย ที่ตัดสต็อกจริง คิดต้นทุนตามล็อตจริง
> และคุมเครดิตช่างได้ — ใช้ได้แม้เน็ตหลุด**

(ข้อ "แม้เน็ตหลุด" จริงสำหรับ build ที่ร้านใช้อยู่ ซึ่งทำงานในเครื่องทั้งหมด ส่วน build แบบมี server
ยังต้องต่อเน็ต — offline ของ build นั้นคือ phase 2 ที่กำลังทำ ดูหัวข้อสถานะ)

### Elevator pitch (~30 วินาที)

> "ร้านอะไหล่เล็กๆ ในไทยส่วนใหญ่ยังเขียนบิลมือ เจ้าของร้านที่เราทำงานด้วยบอกว่า
> ไม่รู้ว่าของเหลือไหม จำราคาไม่ได้ ของแต่ละล็อตต้นทุนไม่เท่ากัน ไม่รู้ว่าช่างค้างเครดิตเท่าไหร่
> และไม่รู้ว่าแต่ละวันกำไรเท่าไหร่
> เราสร้าง POS ที่ออกแบบสำหรับร้านอะไหล่โดยเฉพาะ — ค้นด้วยรหัสอะไหล่หรือรุ่นรถ, ตัดสต็อกทุกบิล,
> คิดต้นทุนเฉลี่ยทุกครั้งที่รับของ, เก็บต้นทุน ณ วันขายไว้ในบิลเพื่อให้กำไรไม่เพี้ยน,
> และมีบัญชีเครดิตช่างพร้อมวงเงิน ร้านจริงใช้เวอร์ชันออฟไลน์อยู่ทุกวันแล้ว
> ตอนนี้เรากำลังต่อยอดเป็นระบบกลางที่รองรับหลายร้าน มี test อัตโนมัติกว่าพันตัวเฝ้าอยู่"

("กว่าพันตัว" = 533 Flutter + 412 server unit + 607 server e2e ตามผลรันจริงใน [CI/CD](15_cicd.md))

### หนึ่งวันที่ร้าน — ก่อน vs หลัง

**ก่อน (บิลมือ)** — เรื่องสมมติที่ประกอบจากปัญหา P1–P8:

```
08:00  เปิดร้าน นับเงินทอนในลิ้นชัก — จดไว้บนกระดาษ (หรือไม่จด)
09:15  ช่างโทรมา "มีผ้าเบรกหน้าวีโก้ไหม"
       → เดินไปดูชั้น... ไม่แน่ใจว่าหลังร้านเหลือไหม (P2)
09:20  ลูกค้าถามราคาหัวเทียน
       → จำไม่ได้ ล็อตก่อนซื้อมาถูก ล็อตนี้แพงขึ้น บอกราคาเดิมไป (P3 — อาจขาดทุน)
10:00  เขียนบิลมือ 5 รายการ บวกเลขในหัว (P1)
13:00  ช่างประจำเบิกของ "ลงบัญชีไว้ก่อน" → จดในสมุดเล่มเล็ก (P5)
       ช่างคนนี้ค้างอยู่เท่าไหร่แล้ว? ต้องไล่เปิดสมุดย้อนหลัง
18:00  ปิดร้าน นับเงิน — ไม่ตรงกับที่คิดไว้ แต่ไม่มีอะไรให้เทียบ (P4)
สิ้นเดือน เจ้าของถามตัวเอง "เดือนนี้กำไรไหม? อะไรขายดี?" — ไม่มีคำตอบ (P6, P7, P8)
```

**หลัง (ใช้ระบบ)** — ขั้นตอนเดียวกัน แต่ระบบทำให้:

```
08:00  เปิดกะในหน้า "ลิ้นชัก/กะ" ใส่เงินทอนตั้งต้น → ระบบจำไว้
09:15  ค้น "วีโก้" ในหน้าค้นหาตามรุ่นรถ → เห็นรหัสอะไหล่ + สต็อกคงเหลือ + ป้ายสต็อกต่ำ
09:20  ค้นด้วยชื่อหรือรหัสอะไหล่ในหน้าขาย → ราคาขายที่ตั้งไว้ขึ้นเอง
       (ราคาขายตั้งโดยเจ้าของ โดยมีตัวช่วยคำนวณ margin จากต้นทุนเฉลี่ยล่าสุด)
10:00  กดขาย → ตัดสต็อกทันที, ออกใบเสร็จ 58mm, ถ้าสต็อกไม่พอระบบไม่ยอมขาย
```

### ทำไม "ต้นทุนเฉลี่ย" แก้ปัญหา "คนละล็อต คนละต้นทุน" (อธิบายแบบไม่มีสูตร)

นึกถึงโถลูกอม: มีลูกอม 10 เม็ด ซื้อมาเม็ดละ 1 บาท แล้วเติมอีก 10 เม็ดที่ซื้อมาเม็ดละ 2 บาท
พอเขย่ารวมกัน คุณ**แยกไม่ออกแล้ว**ว่าเม็ดไหนมาจากล็อตไหน — ร้านอะไหล่ก็เหมือนกัน
หัวเทียนบนชั้นไม่มีป้ายบอกว่ามาจากล็อตไหน

ต้นทุนเฉลี่ยถ่วงน้ำหนักตอบว่า "โถนี้ตอนนี้ เฉลี่ยเม็ดละเท่าไหร่" = (10×1 + 10×2) ÷ 20 = **1.50 บาท**
(ตัวอย่างสมมติ) ทุกครั้งที่เติมของ ระบบคิดค่าเฉลี่ยใหม่ให้เอง ไม่ต้องจำ ไม่ต้องเปิด Excel

ทำไมต้อง "ถ่วงน้ำหนัก" ไม่ใช่เฉลี่ยธรรมดา (1+2)/2: ถ้าล็อตแรก 100 เม็ด ล็อตหลัง 1 เม็ด
ค่าเฉลี่ยธรรมดาจะบอก 1.50 ทั้งที่ของเกือบทั้งโถราคา 1 บาท — คอมเมนต์ในโค้ดเขียนไว้ตรงนี้เลย:
"Prevents 1 expensive PO unit from corrupting unit cost of existing units" (`purchase_orders_repository.dart:120`)

แล้วทำไมยังต้องมี **ต้นทุน ณ วันขาย** อีกชั้น? เพราะค่าเฉลี่ยของโถ**เปลี่ยนทุกครั้งที่เติม**
ถ้ารายงานกำไรไปอ่านค่าเฉลี่ยวันนี้ กำไรของบิลเดือนที่แล้วจะเปลี่ยนตามไปด้วย ADR-0008 จึงให้ "ถ่ายรูป"
ต้นทุนเก็บไว้ในบิลตอนขาย — กำไรของบิลนั้นจึงนิ่งตลอดไป

### เราแข็งกว่าตรงไหน

1. **Domain fit ครบในที่เดียว** — part number, เครดิตช่างพร้อมวงเงินและการยืนยันเกินวงเงิน,
   ใบเสนอราคา A4 ที่แปลงเป็นบิล, ต้นทุนเฉลี่ย, แต้มลูกค้า, คืนของที่กลับรายการตามสัดส่วน
   — cloud POS ทั่วไปที่ตรวจไม่ได้ประกาศครบชุดนี้
2. **ข้ามแพลตฟอร์ม** — โปรแกรมร้านอะไหล่ไทยที่พบส่วนใหญ่ผูกกับ Windows desktop
   ของเรารันบนมือถือ แท็บเล็ต และเว็บจาก code base เดียว (Flutter)
3. **ความถูกต้องของตัวเลข** — กำไรจากต้นทุน ณ วันขาย, คืนของเกินไม่ได้, สต็อกติดลบไม่ได้
   (ดูหัวข้อถัดไป) ผู้ขายรายอื่นไม่เปิดเผยระดับนี้ จึง**เทียบตรงๆ ไม่ได้** — เราอ้างได้แค่ฝั่งเรา
4. **ออฟไลน์ที่ตั้งใจให้คืนของได้** — Loyverse ระบุว่า offline คืนเงินไม่ได้; build ที่ร้านใช้ทำได้ทุกอย่าง
   ในเครื่อง และ spec phase 2 ออกแบบให้เครื่อง POS ออกเลขใบเสร็จ/ใบลดหนี้ได้ทั้ง online และ offline
   (**phase 2 ยังไม่ ship**)
5. **ข้อมูลเป็นของร้าน** — export snapshot ได้เอง ไม่ต้องจ่าย add-on
6. **ไม่มีค่า license รายเดือน** — แต่ดูข้อ "ราคาแฝง" ด้านล่าง

### เราอ่อนกว่าตรงไหน (พูดตรงๆ)

1. **เอกสารภาษี** — ใบกำกับภาษีเต็มรูปอยู่นอก scope v1 และยังไม่ได้ตรวจเรื่องใบกำกับภาษีอย่างย่อ
   ที่ต้องขออนุมัติด้วยแบบ ภ.พ.06[^rd] ขณะที่ POSPOS, DMART, PSS, ITECStock ประกาศว่ามี
2. **ฮาร์ดแวร์** — ยังไม่ต่อเครื่องพิมพ์ความร้อน ลิ้นชัก สแกนเนอร์ คู่แข่งเกือบทุกรายขายเป็นชุดพร้อมใช้
3. **การชำระเงิน** — ยังไม่เชื่อม PromptPay API / EDC
4. **ราคาหลายระดับ / สินค้าทดแทน** — MyCarSoft มีราคา 4 ระดับ, PSS มีสินค้าทดแทน เรายังไม่มี
5. **ยังไม่ขึ้น production แบบ server** — CD ติด FortiGate, ไม่มี offsite backup, มีร้านเดียว
6. **ไม่ใช่ธุรกิจ** — ไม่มีทีมซัพพอร์ต ไม่มี SLA ถ้าทีมนักศึกษาแยกย้าย ความต่อเนื่องมีความเสี่ยงสูง
7. **ราคาแฝง** — "ไม่มีค่า license" ไม่ได้แปลว่าฟรี ต้นทุนคือเวลาดูแล server, VM, backup

## 🏆 Why us — จุดต่างที่มีหลักฐานทางวิศวกรรม

pitch ที่ดีไม่พูดว่า "ระบบเราดี" แต่ชี้ว่า "ดีเพราะอะไร ดูได้ที่ไหน"

### 1. Domain fit — สร้างจากร้านจริง ไม่ใช่จาก template

- กติกาทุกข้อ port มาจาก `pos/db.js` ของแอปเดิมที่ร้านใช้จริง ข้อความภาษาไทยตรงทุกตัวอักษร
  (CLAUDE.md "Conventions") — พนักงานไม่ต้องเรียนภาษาใหม่
- โครงข้อมูลมีสิ่งที่ร้านอะไหล่ต้องการ: `partNo`, `compat`, `minStock` (`tables.dart:14-25`),
  เครดิตช่าง + วงเงิน (`tables.dart:69-78`), ต้นทุนเฉลี่ย, ใบเสนอราคา A4

### 2. ตัวเลขถูก — บังคับด้วย transaction และ database ไม่ใช่ด้วยความระวังของคน

- **Transaction** (ชุดคำสั่งที่ต้องสำเร็จทั้งหมดหรือไม่เกิดเลย): ขายหนึ่งบิล = ตัดสต็อก + เพิ่มยอดลูกค้า
  + เพิ่มเครดิตช่าง + บันทึกบิล ถ้าข้อไหนพัง ทั้งหมดย้อนกลับ (`sales_repository.dart:55`)
  → ไม่มีวันที่ "สต็อกลดแต่ไม่มีบิล"
- **Over-refund guard**: คืนได้ไม่เกิน (ขาย − คืนไปแล้ว) ทั้งในแอปและ server
  (`returns_repository.dart:51-66`, `returns.service.ts:638`)
- **Invariant ในฐานข้อมูล**: เช่นรหัสอะไหล่ซ้ำไม่ได้เป็น constraint ของ PostgreSQL
  ไม่ใช่แค่ `if` ในโค้ด (รายละเอียดใน [database](07_database.md))
- **เงินคิดเป็นสตางค์ (integer)** ตอนคิดต้นทุนเฉลี่ยฝั่ง server เพื่อไม่ให้ทศนิยมเพี้ยน
  (`weighted-average.ts:17-23`) — ดู [money & Thai correctness](08_money_thai.md)

### 3. Offline-first — ร้านไม่หยุดขายเพราะเน็ตหลุด

build ที่ร้านใช้อยู่เก็บข้อมูลในเครื่อง (Drift/SQLite) ขายได้โดยไม่ต้องมีเน็ต
phase 2 จะเอาความสามารถนี้กลับมาในรุ่น server ผ่าน outbox — ดู [offline / phase 2](10_offline_phase2.md)

### 4. Multi-tenant — ทางไปสู่หลายร้าน

server ออกแบบให้ฐานข้อมูลเดียวรองรับหลายร้าน แยกข้อมูลกันด้วย **RLS** (Row-Level Security —
กฎในฐานข้อมูลที่ทำให้แต่ละร้านมองเห็นแค่แถวของตัวเอง) → ต้นทุนต่อร้านต่ำลงเมื่อมีหลายร้าน
(**ยังไม่มีร้านที่สองจริง**)

### 5. ข้อมูลเป็นของร้าน

`exportSnapshot()` / `importLegacyBackup()` (`snapshot_repository.dart:132, 595`)
และ server มี `POST /backup/export` — ร้านเอาข้อมูลออกไปได้ทุกเมื่อ (ADR-0005 data portability)

## ✅ สรุป

- Product เริ่มจาก **problem** ไม่ใช่ tool — ร้านนี้มีปัญหาจริง 8 ข้อ: บิลมือ, สต็อก, ราคา/ต้นทุนคนละล็อต,
  เงินวันนี้, เครดิตช่าง, กำไร, ยอดขาย, ของขายดี
- ทุกข้อมี feature ที่ตรวจแล้วใน repo — แต่บางข้อยัง**ครึ่งทาง** (ราคาขายไม่ปรับตามต้นทุน, ค้นรุ่นรถเป็นแค่ค้นข้อความ,
  ใบปิดร้านยังคิดกำไรจากต้นทุนปัจจุบัน)
- **ต้นทุนเฉลี่ยถ่วงน้ำหนัก** แก้ "ของคนละล็อต"; **ต้นทุน ณ วันขาย** ทำให้กำไรของบิลเก่าไม่เปลี่ยนย้อนหลัง
- User (พนักงาน) ≠ Customer (เจ้าของ) — ฟีเจอร์ที่ช้าลงหนึ่งคลิก (ยืนยันเกินวงเงิน) อาจเป็นสิ่งที่เจ้าของจ่ายเงินให้
- เทียบคู่แข่ง: เราแข็งเรื่อง domain fit + ข้ามแพลตฟอร์ม + ความถูกต้องของตัวเลข;
  อ่อนเรื่องภาษี ฮาร์ดแวร์ การชำระเงิน และความพร้อมเชิงธุรกิจ
- มุมธุรกิจทั้งหมดเป็น**สมมติฐาน** — เรามี product–shop fit กับร้านเดียว ยังไม่มี PMF
- สถานะตรงๆ: ร้านใช้ build ออฟไลน์; server อยู่บน demo tenant; CD ติด FortiGate; ยังไม่มี offsite backup

## ❓ Quiz

**1. ทำไม "ร้านยังไม่มีแอป" ไม่ใช่ problem statement ที่ดี?**

<details><summary>เฉลย</summary>

เพราะมันคือ solution ที่ปลอมตัวมาเป็นปัญหา มันบอกว่า "ต้องสร้างอะไร" แต่ไม่บอกว่า "ใครเจ็บตรงไหน"
problem ที่ดีคือ "เจ้าของไม่รู้ว่าช่างค้างเครดิตเท่าไหร่ จึงให้เครดิตเกินตัว" — ซึ่งแก้ได้หลายทาง
(แอป, สมุดที่ออกแบบดีขึ้น, กฎร้าน) และทำให้เราวัดได้ว่าทางแก้ของเราได้ผลไหม

</details>

**2. ถ้ารายงานกำไรใช้ `products.cost` ปัจจุบันแทน `costAtSale` จะเกิดอะไรขึ้นเมื่อร้านรับของล็อตใหม่ที่แพงขึ้น?**

<details><summary>เฉลย</summary>

`receivePO` คิดต้นทุนเฉลี่ยใหม่ → `products.cost` สูงขึ้น → กำไรของบิลเดือนที่แล้วที่คำนวณจากค่านี้
**ลดลงย้อนหลัง** ทั้งที่บิลนั้นขายไปแล้วด้วยต้นทุนเดิม ยิ่งแย่กว่านั้น ถ้าสินค้าถูกลบ/แก้รหัส โค้ดเดิม
ใช้ต้นทุน 0 → กำไร 100% (ADR-0008) ทางแก้คือถ่ายรูปต้นทุนเก็บไว้ในบรรทัดบิลตอนขาย
— และบทนี้พบว่า `closing_report.dart` ยังใช้วิธีเก่าอยู่

</details>

**3. ร้านมีหัวเทียน 100 ตัวทุน 50 บาท รับเข้าอีก 10 ตัวทุน 80 บาท — ทำไมต้นทุนใหม่ควรเป็นประมาณ 52.73 ไม่ใช่ 65?**

<details><summary>เฉลย</summary>

65 คือค่าเฉลี่ยธรรมดา (50+80)/2 ซึ่งให้น้ำหนักล็อต 10 ตัวเท่ากับล็อต 100 ตัว
ต้นทุนเฉลี่ยถ่วงน้ำหนัก = (100×50 + 10×80) ÷ 110 = 5,800 ÷ 110 ≈ 52.73
ถ้าใช้ 65 ระบบจะบอกว่าของเกือบทั้งหมดแพงกว่าความจริง → ตั้งราคาสูงเกิน หรือรายงานกำไรต่ำเกิน
(ตัวเลขในข้อนี้เป็นตัวอย่างสมมติ)

</details>

**4. ทำไมการใส่ "จุดที่เราอ่อนกว่า" ในสไลด์ pitch ถึงช่วยเรา แทนที่จะทำร้ายเรา?**

<details><summary>เฉลย</summary>

ผู้ฟัง (อาจารย์) รู้อยู่แล้วว่าไม่มีระบบไหนชนะทุกข้อ ตารางที่มีแต่ ✅ ฝั่งเราทำให้ไม่เชื่อทั้งตาราง
การบอกจุดอ่อนพร้อมแผน (Phase 8b, นอก scope v1) แสดงว่าเราเข้าใจตลาดและจัดลำดับความสำคัญเป็น
และป้องกันไม่ให้โดนถามแล้วตอบไม่ได้ — ความน่าเชื่อถือของข้อแข็งเพิ่มขึ้น

</details>

**5. หน้าขายถามยืนยันก่อนขายเครดิตเกินวงเงิน ทำไม server ยังต้องเช็คซ้ำ และทำไมต้องส่ง `overrideCreditLimit` ไปกับบิลแทนที่จะให้ server เดาเอง?**

<details><summary>เฉลย</summary>

Server เช็คซ้ำเพราะ client ไม่ใช่แหล่งความจริง — อาจมีอีกเครื่องขายเครดิตให้ช่างคนเดียวกันไปก่อน
ถ้าไม่มี flag server ตอบ `409 CREDIT_LIMIT_EXCEEDED` (`sales.service.ts:411-414`)
ส่วน flag ต้องส่งไปเพราะ "ความยินยอม" เดาย้อนหลังไม่ได้ — คอมเมนต์ที่ `checkout_screen.dart:562-566`
อธิบายว่าคำยืนยันผูกกับข้อมูลช่างที่หน้าจอเห็นตอนนั้น ถ้าให้คนอื่นเช็คใหม่ภายหลังจะเห็นยอดคนละตัว
ในแง่ product: เจ้าของต้องการหลักฐานว่า "มีคนตั้งใจอนุมัติ" ไม่ใช่ระบบปล่อยผ่านเอง

</details>
