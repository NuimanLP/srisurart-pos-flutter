## Flow 1 — สร้างร้านใหม่ (platform-ui) · ~2 นาที

**เป้าหมาย:** ระบบเดียวรองรับหลายร้าน — สร้างร้านใหม่ได้ในนาทีเดียว ไม่ต้องติดตั้งอะไรเพิ่ม

**บนจอ:**
1. platform-ui (`http://127.0.0.1:3200`) → สร้าง tenant ใหม่ (ชื่อร้านเดโม)

## Flow 2 — ขายปกติ: ช่าง/สินค้า → เปิดกะ → ขาย → ใบเสร็จ · ~2 นาที

**เตรียมในร้านใหม่ (ทำตอนเดโมหรือก่อนขึ้นเวทีก็ได้):** สินค้า 2–3 ตัว (สต็อก 10) · ช่าง 1 คน **วงเงิน ฿5,000**
(ค่า default = 0 = ไม่ให้เครดิต) · ลูกค้า 1 คน ถ้าจะโชว์แต้ม

**บนจอ:**
1. เปิดกะ เงินตั้งต้น ฿1,000
2. ขาย 1 ชิ้น เงินสด → **กรอกช่อง "รับเงิน" ก่อน** (ไม่งั้นขึ้น `รับเงินไม่ครบ`) → ใบเสร็จ
3. กลับหน้าสินค้า ชี้สต็อก 10 → 9
4. (ถ้ามีเวลา) กด + เกินสต็อก → `สต็อก "<ชื่อ>" เหลือเพียง N ชิ้น`

**พูด:**
> "นี่คือ flow ที่พนักงานหน้าร้านทำทั้งวัน เลขบิล `RC01-2569-10-0001` — RC = ใบเสร็จ, 01 = เลขเครื่อง,
> 2569-10 = ปี พ.ศ. กับเดือน, แล้วเลขรัน — เครื่องออกเลขเองได้แม้ตอนออฟไลน์ เลขจึงต่อกันไม่ชน"
>
> "กติกาธุรกิจ — ตัดสต็อก, แต้มลูกค้า (ยอด ÷ 10 ถ้าเลือกลูกค้า), ยอดช่าง — ทำใน transaction เดียวบน server
> ข้อไหนพัง ทั้งบิลย้อนกลับ ไม่มีครึ่ง ๆ กลาง ๆ"
>
> "ตะกร้ากันขายเกินสต็อกตั้งแต่หน้าจอ และ server กันซ้ำอีกชั้นด้วย `สต็อกไม่พอ` เผื่อมีคำขอชนกัน"
>
> "เงินส่งเป็น string `"150.00"` ไม่ใช่ float เพื่อไม่ให้สตางค์เพี้ยน"

## Flow 3 ⭐ — ส่งบิลซ้ำ key เดิม (idempotency) · ~1.5 นาที

> ทำ **ต่อจาก Flow 2 ทันที** — ต้องเป็นบิลที่ส่งออนไลน์ (`POST /api/v1/sales`) และภายใน 15 นาที (access token หมดอายุ)
> Chrome ไม่มีปุ่ม "Replay" สำหรับ `fetch` ของ Flutter web — ใช้ Copy as fetch (ทำแบบนี้จริงแล้ว 2026-10-07)

**บนจอ:**
1. เปิด DevTools → Network **ก่อน**ขายบิลใน Flow 2
2. คลิกขวา `POST /api/v1/sales` → **Copy → Copy as fetch** → วางใน Console → รัน 2 ครั้ง
3. ชี้ response ทั้งสองครั้ง: status `201`, **`receiptNo` + `id` เดิม**
4. Grafana: `Idempotent replays` +2 · จำนวนบิลไม่เพิ่ม (รอ scrape ~15–30 วิ)

> ⚠️ อย่าชี้รายการบิล/สต็อกบนจอแอปเป็นหลักฐาน — หน้าจออ่านฐานในเครื่อง คำขอจาก Console ไม่แตะมัน
> หลักฐานจริงอยู่ฝั่ง server (response + Grafana)

**พูด:**
> "สถานการณ์จริง: พนักงานกดชำระ เน็ตค้าง ไม่รู้ว่าบิลเข้าหรือยัง เลยกดอีกที
> ถ้าไม่มี idempotency ร้านจะตัดสต็อกสองรอบ และลูกค้าถูกเก็บเงินสองครั้ง"
>
> "id บิลกับ key ผูกกับตะกร้า — ทุกครั้งที่ยังไม่รู้ผล (timeout หรือ server ตอบ 5xx) กดซ้ำจะส่ง key เดิม ภายใน 10 นาที
> ได้คำตอบแล้วจึงปิด server เห็น key ซ้ำ ก็คืนผลเดิมจากครั้งแรก"
>
> "ตัวนับ replay นับเฉพาะตอน transaction commit จริง — ถ้า rollback ไม่นับ"

**หลักฐานที่มีแล้ว:** บน `mob04` 2026-10-07 — `RC01-2569-10-0002` ส่งซ้ำ 2 ครั้ง ได้ `201` บิลเดิม, `sales` ยัง 2 แถว,
`pos_idempotency_replay_total` = 2 ([handoff](../handoff_log/session-2026-10-07-demo344-run.md))

## Flow 4 — เครดิตช่าง + รับชำระหนี้ · ~1.5 นาที

**บนจอ:**
1. หน้าขาย **เลือกช่างก่อน** → ปุ่ม `เครดิตช่าง` จึงขึ้น → ขาย → ยอดค้างของช่างเพิ่ม
2. (โชว์วงเงิน) ขายเกินวงเงิน → dialog `เกินวงเงินเครดิต! ยอดค้างใหม่ … > วงเงิน … ยืนยันขายเครดิต?` → กดยกเลิก
3. หน้าช่าง → รับชำระบางส่วน → ยอดค้างลด
4. ลองรับเงินเกินยอดค้าง → dialog `ยืนยันรับเงิน — จำนวนเงิน ฿X เกินยอดค้าง ฿Y` → กด **ยกเลิก** (ห้ามกดยืนยัน — กดแล้วรับจริง)

**พูด:**
> "ร้านอะไหล่ขายเชื่อให้อู่ซ่อมเป็นเรื่องปกติ ระบบเก็บยอดค้างรายช่าง มีวงเงิน —
> เกินวงเงินหรือรับเงินเกินยอดค้าง ต้องให้คนยืนยันเองจาก dialog ที่เห็นจริงเท่านั้น ระบบไม่เดาแทน"
>
> "error ที่ระบบรู้จักแปลงเป็นข้อความไทยที่เจ้าของร้านรับรองแล้ว และมีเทสต์ 2 ตัวบังคับว่า
> exception ดิบของ API หลุดไปถึงหน้าจอไม่ได้"

## Flow 5 — คืนสินค้า (ใบลดหนี้ CN) · ~1 นาที

**บนจอ:**
1. ค้นบิลจาก Flow 2 → คืนครบ → ได้เลข `CN…` → ชี้สต็อกกลับ
2. บิลเดิมขึ้น `✕ ยกเลิกแล้ว` และกดไม่ได้ = auto-void ตอนคืนครบ
3. (บิลหลายชิ้น) ปุ่ม + หยุดที่จำนวนที่ยังคืนได้

**พูด:**
> "การคืนเฉลี่ยส่วนลด แต้ม และยอดช่างกลับตามสัดส่วน คืนครบทั้งบิล ระบบ void บิลเดิมให้เอง
> หน้าจอกันคืนเกินที่ขาย server ก็กันซ้ำ (`คืนเกินจำนวนที่ขาย`)"
>
> "กฎชุดเดียวกัน (`planReturn()`) ใช้ทั้ง build ออฟไลน์และตอนเน็ตหลุด ส่วนออนไลน์ server ใช้กฎเดียวกันที่ port มาเป็น TypeScript"

## Flow 6 ⭐ — ขายตอนเน็ตหลุด · ~2 นาที

> 🔴 **ซ้อมบน `mob04` ก่อนวันจริง** — flow นี้ยังไม่ได้เดินบน VM รอบ 2026-10-07 ถ้าซ้อมแล้วไม่ราบรื่น ใช้คลิปแทน
> 🔴 **ห้าม reload / ปิดแท็บระหว่าง Offline** — access token อยู่ในหน่วยความจำเท่านั้น (ADR-0009)

**บนจอ:**
1. DevTools → Network → **Offline** → **รอ ~15 วิ** (เช็กทุก 5 วิ ต้องพลาด 3 ครั้งติด) → ป้ายเป็น `ออฟไลน์ (ขายสำรอง)`
2. ขาย 1 บิล → ได้เลข RC ต่อจากบิลออนไลน์ทันที → ป้ายขึ้น `· ค้าง 1`
3. ไปหน้าลิ้นชัก → ปุ่ม `🔒 ยืนยันปิดลิ้นชัก` **กดไม่ได้** (มีงานค้างส่ง) — ใช้ประกอบ Flow 7
4. ปิด Offline → ภายใน ~5 วิ ป้ายเป็น `กำลังส่งข้อมูล...` แล้ว `ออนไลน์` (ค้าง 0) → Grafana จำนวนบิล +1

> ⚠️ รายการบิลบนจอแอปไม่ใช่หลักฐานว่าถึง server (บิลอยู่ในเครื่องตั้งแต่ตอนขาย) — ชี้ป้าย + Grafana

**พูด:**
> "นี่คือเหตุผลที่โปรเจกต์นี้เป็น offline-first — เน็ตหลุดเป็นเรื่องปกติ ร้านต้องขายต่อได้"
>
> "บิลออฟไลน์ลงคิวในเครื่อง (Drift/SQLite) พร้อม id + key เดิม พอเน็ตกลับ `/sync/push` ส่งทั้งคิว
> server เช็ก key ก่อน แล้วเช็ก id ของบิลก่อนจะอ่าน payload — ส่งซ้ำกี่ครั้งก็ได้บิลเดียว"
>
> "เข้าคิวเฉพาะตอนส่งไม่ถึงหรือไม่ได้คำตอบ (timeout) — server replay ด้วย key จึงไม่ซ้ำ
> ถ้า server ตอบ 5xx/429 แปลว่า server ยังอยู่ เราจอดไว้ให้กดซ้ำด้วย key เดิมแทน
> ไม่ออกเลขบิลออฟไลน์ซ้อนกับบิลที่ server อาจรับไปแล้ว"

## Flow 7 — ปิดกะ + รายงานปิดกะ · ~1 นาที

**บนจอ:**
1. หน้าลิ้นชัก → ชี้ยอดเงินที่ควรมี
2. ลองจ่ายเงินออกเกินที่มี → `เงินในลิ้นชักไม่พอ (มี ฿…)`
3. กรอกเงินที่นับได้ → `🔒 ยืนยันปิดลิ้นชัก` → รายงานปิดกะ

**พูด:**
> "เงินที่ควรมี = ตั้งต้น + รับเงินสด (ขายและรับชำระเครดิต) − คืน ± เงินเข้า/ออก — นับ **ตามกะ** ไม่ใช่ตามวัน
> ทุกบาทที่รับระหว่างกะเปิดเป็นของกะนั้น แม้ข้ามเที่ยงคืน แอปกับ server คิดด้วยกฎเดียวกัน มี fixture ทดสอบว่าตัวเลขตรงกัน"
>
> "จ่ายเงินออกเกินที่มีในลิ้นชักไม่ได้ทั้งหน้าจอและ server (409)
> ปิดกะไม่ได้ถ้ายังมีงานค้างส่ง — อย่างที่เห็นตอนเน็ตหลุดเมื่อกี้ ปุ่มกดไม่ได้"
