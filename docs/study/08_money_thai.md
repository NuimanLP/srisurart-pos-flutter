## 🧱 ปูพื้นฐาน

### คอมพิวเตอร์เก็บตัวเลขยังไง

คอมพิวเตอร์ไม่มีคำว่า "ตัวเลข" แบบที่หัวเราคิด มันมีแค่ลำดับของ 0/1 (**bit**) จำนวนคงที่ต่อช่อง
(32 bit, 64 bit) แล้วตีความบิตพวกนั้นตาม "แบบ" (type) ที่เราเลือก

- **จำนวนเต็ม (integer)** — เก็บง่าย: 64 bit เก็บเลขเต็มได้แม่นยำ 100% ตั้งแต่ประมาณ
  −9.2×10¹⁸ ถึง 9.2×10¹⁸ ไม่มีจุดทศนิยม ไม่มีการปัดเศษเลย เพราะไม่มีเศษให้ปัด
- **จำนวนทศนิยมแบบ floating point (IEEE-754)** — เก็บ "ทศนิยมแบบวิทยาศาสตร์ในฐาน 2"
  คล้าย `1.2345 × 10³` แต่เป็นฐาน 2: `mantissa × 2^exponent` ปัญหาคือ **เลขฐาน 10 หลายตัวไม่มีค่าตรงในฐาน 2**
  เหมือนที่ 1/3 ไม่มีค่าตรงในฐาน 10 (เขียนได้แค่ 0.3333... ไม่จบ)

ลองรันใน Dart REPL หรือ `dart run` เอง:

```dart
void main() {
  print(0.1 + 0.2);           // 0.30000000000000004
  print(0.1 + 0.2 == 0.3);    // false
}
```

หรือ JavaScript (คอนโซล browser):

```js
> 0.1 + 0.2
0.30000000000000004
```

**ทำไม:** `0.1` ในฐาน 2 คือ `0.0001100110011...` (ซ้ำไม่จบ เหมือน 1/3 ในฐาน 10) คอมพิวเตอร์เก็บได้แค่
64 bit ก็ตัดปัดตรงนั้น พอบวกเลขที่ถูกตัดปัดสองตัว ผลจึงเพี้ยนไปนิดหน่อยในหลักท้ายๆ ที่ตามนุษย์มองไม่เห็น
แต่คอมพิวเตอร์เห็น — เวลาเทียบ `==` หรือบวกสะสมหลายรอบ (เช่น ราคาสินค้า 50 บิลต่อวัน) ความเพี้ยนแค่
`0.00000000000000004` บวกสะสมจนวันหนึ่งยอดขายในรายงานไม่ตรงกับที่พนักงานนับเงินสดในลิ้นชักจริง

> **บทเรียนสำคัญ:** ห้ามเก็บ**เงิน**เป็น `float`/`double` เด็ดขาด ไม่ว่าภาษาไหน (Dart `double`,
> JS `Number`, Python `float`) เพราะเงินต้อง "ตรงเป๊ะ" ทุกสตางค์ ไม่ใช่ "ใกล้เคียง"

### วิธีแก้ 1: หน่วยย่อยสุด (minor unit / satang)

แทนที่จะเก็บ "85.50 บาท" เป็นทศนิยม ให้เก็บเป็น**จำนวนเต็มของหน่วยย่อยสุด** — "8550 สตางค์"
1 บาท = 100 สตางค์ เหมือนดอลลาร์ = 100 เซนต์ พอเป็นจำนวนเต็มแล้ว บวกลบคูณกันได้แม่นยำ 100%
ไม่มีการปัดเศษระหว่างทางเลย (ปัดแค่ตอนแปลงกลับเป็นภาพที่คนอ่าน)

Backend (`server/`) ของโปรเจกต์นี้ทำแบบนี้เป๊ะ — ดูหัวข้อ "ของจริงใน repo" ด้านล่าง

### วิธีแก้ 2: decimal type ของฐานข้อมูล

Postgres มี type ชื่อ `NUMERIC(precision, scale)` ที่เก็บทศนิยมแบบ**แม่นยำเป๊ะ** (ไม่ใช่ binary
floating point) — `NUMERIC(12,2)` แปลว่า "ตัวเลขสูงสุด 12 หลัก โดย 2 หลักหลังจุด" เบื้องหลังมันเก็บ
เป็นเลขฐาน 10 จริงๆ ไม่ผ่าน binary approximation เลย ต่างจาก `FLOAT`/`DOUBLE PRECISION` ที่เป็น
IEEE-754 เหมือนกับที่ทำให้ `0.1+0.2` เพี้ยนในโปรแกรม

### ทำไมเงินถึงวิ่งผ่านเครือข่ายเป็น "string"

เมื่อ backend ส่งยอดเงินกลับไปให้ frontend ผ่าน HTTP (ภาษา JSON) มันส่งเป็น `"1234.50"`
(ข้อความ) ไม่ใช่ `1234.50` (ตัวเลข) เหตุผล: **JSON number เป็น IEEE-754 double ตามสเปกของมัน**
ถ้าส่งเป็นตัวเลขจริง ทั้งสองฝั่ง (server เขียนด้วย string เข้ารหัส JSON, client ถอดรหัส JSON)
ต้องผ่านการแปลงเป็น double อย่างน้อยหนึ่งจุด ซึ่งเปิดช่องให้เพี้ยนแบบที่อธิบายไปแล้ว การส่งเป็น
string ตัดปัญหานี้ทิ้งทั้งหมด: string ไม่มีการปัดเศษ ฝั่งรับแปลงกลับเป็น integer สตางค์ของตัวเองตรงๆ

### rounding modes (โหมดการปัดเศษ) — ไม่ได้มีแบบเดียว

พอมีเศษต้องปัด (เช่น ส่วนลดตามสัดส่วน, ต้นทุนถัวเฉลี่ย) ต้องเลือกว่า "ปัดยังไง" คนละแบบให้ผลต่างกัน:

| โหมด | กฎ | ตัวอย่าง 2.5 → ? | ใช้ที่ไหนบ่อย |
|---|---|---|---|
| **Truncate (ตัดทิ้ง)** | ตัดเศษทิ้งเฉยๆ ไม่สนใจว่าเศษมากหรือน้อย | 2.5 → 2 | นับแต้มสะสม (ปัดลงเสมอ กันร้านแจกแต้มเกิน) |
| **Half-up (ปัดครึ่งขึ้น)** | เศษ ≥ 0.5 ปัดขึ้น | 2.5 → 3 | ร้านค้า ใบเสร็จ (คนคุ้นเคยแบบนี้จากโรงเรียน) |
| **Half-even / banker's rounding** | เศษ = 0.5 พอดี ปัดไปทางเลขคู่ | 2.5 → 2, 3.5 → 4 | บัญชี/ธนาคารสเกลใหญ่ (ปัดสะสมจำนวนมากครั้ง ไม่เอนเอียงขึ้นหรือลงไปทางเดียว) |

โปรเจกต์นี้ปนกันสองแบบ **โดยตั้งใจ** ระหว่าง Dart (float, half-away-from-zero) กับ TypeScript
(integer satang, explicit half-up) — เหตุผลเต็มๆ อยู่ในหัวข้อ "ของจริงใน repo" #2

### การแบ่งสัดส่วนแล้วมีเศษเหลือ (proportional allocation & rounding remainder)

โจทย์คลาสสิก: ลูกค้าซื้อของ 3 ชิ้น รวม 100 บาท ได้ส่วนลด 10 บาท ทีนี้คืนของ 1 ใน 3 ชิ้น
ต้องคืนส่วนลดเท่าไหร่? คำตอบไม่ใช่ "10/3 = 3.33 พอดี" เพราะถ้าคืนของทั้ง 3 ชิ้นทีละใบ
(3.33 + 3.33 + 3.33 = 9.99) เงินหายไป 0.01 บาทจากไหนไม่รู้ — ต้องมีกฎที่การ์ดกันผลรวมให้ตรง
เป๊ะเสมอ ไม่ว่าจะคืนกี่ครั้ง กฎที่โปรเจกต์นี้ใช้: **คำนวณส่วนลดที่ต้องคืนจากยอดขายจริงทุกครั้ง**
(ไม่ใช่หารเท่าๆ กันแล้วบวกสะสม) — ดู `refundAmounts` ด้านล่าง

### ต้นทุนถัวเฉลี่ยถ่วงน้ำหนัก (weighted average cost)

ร้านอะไหล่ซื้อของล็อตเดียวกันหลายครั้ง คนละราคา (คู่ค้าขึ้นราคา, ซื้อช่วงโปร ฯลฯ) เวลาคำนวณ
"กำไร" ของสินค้าชิ้นหนึ่งที่ขายออกไป ต้องรู้ว่า "ต้นทุนเฉลี่ย" ของสต็อกที่มีอยู่ตอนนี้คือเท่าไหร่
สูตร: ต้นทุนใหม่ = (ของเก่า×ราคาเก่า + ของใหม่×ราคาใหม่) ÷ (ของเก่า+ของใหม่) — เหมือนหาค่าเฉลี่ยถ่วง
น้ำหนักในสถิติ แค่ "น้ำหนัก" คือจำนวนชิ้น

### แต้มสะสม (loyalty points)

สูตรง่ายๆ: ทุกๆ 10 บาทที่ซื้อ ได้ 1 แต้ม (`floor(ยอดขาย / 10)`) ใช้ `floor` (ปัดลงเสมอ) ไม่ใช่
`round` เพราะถ้าปัดขึ้นได้ ร้านจะแจกแต้มเกินกว่าที่ตั้งใจทุกบิลที่ลงท้ายด้วย .50 ขึ้นไป

### Unicode และ UTF-8 — ทำไมตัวไทยถึง "หนักกว่า" ตัวอังกฤษ

**Unicode** คือ**ตารางเลขรหัส** (code point) ที่ครอบคลุมทุกตัวอักษรของทุกภาษาในโลก บวก emoji
ทุกตัวมี "หมายเลข" ประจำตัว เช่น `A` = U+0041, `ก` = U+0E01 Unicode บอกแค่ว่า "ตัวนี้คือเลขอะไร"
ไม่ได้บอกว่า "เก็บเป็นบิตยังไง" — หน้าที่นั้นเป็นของ **encoding** (วิธีเข้ารหัส)

**UTF-8** คือ encoding ที่ฮิตที่สุด (เว็บ, JSON, ไฟล์ text ส่วนใหญ่) กฎของมันคือ: ตัวอักษร
ASCII เดิม (a-z, 0-9, สัญลักษณ์พื้นฐาน) ใช้ **1 byte** เท่าเดิม (ย้อนกลับความเข้ากันได้กับระบบเก่า)
แต่ตัวอักษรนอกช่วงนั้น — รวมถึง**ตัวอักษรไทยทุกตัว** — ใช้ **3 byte** ต่อตัว (emoji บางตัวใช้ถึง 4 byte)

ผลที่ตามมาที่เจอบ่อยในงานจริง:

- **นับความยาว string ผิด** — บาง runtime นับ "ความยาว" เป็น byte ไม่ใช่ตัวอักษร ทำให้ข้อความไทย
  10 ตัวอักษร ถูกนับเป็น 30 (ต้องระวังเวลามี limit ความยาว เช่น ชื่อสินค้าจำกัด 50 ตัวอักษร แต่ไป
  จำกัดที่ 50 byte จริง จะพิมพ์ภาษาไทยได้แค่ ~16 ตัว)
- **ตัดสตริงกลางตัวอักษร** — ถ้า byte ของตัวอักษรไทยถูกตัดขาดกลางตัว (เช่น เอาแค่ byte แรกจาก 3)
  จะได้ตัวอักษรเพี้ยน/พัง แสดงเป็นสัญลักษณ์ `�`
- **font ไม่มี glyph** — ปัญหานี้เจอในบทนี้จริง ดูหัวข้อ "font fallback" ด้านล่าง

### พ.ศ. vs ค.ศ. และ time zone

ปีพุทธศักราช (พ.ศ.) = ปีคริสต์ศักราช (ค.ศ.) + 543 เสมอ — ใบเสร็จ/รายงานของร้านคนไทยต้องแสดง พ.ศ.
แต่**ฐานข้อมูลและตรรกะภายในต้องเก็บเป็น ค.ศ.** (มาตรฐานสากล ทุกไลบรารีวันที่เข้าใจ) แล้ว **แปลงเป็น
พ.ศ. เฉพาะตอนแสดงผล** เท่านั้น — ถ้าเผลอเก็บ พ.ศ. ลง database การคำนวณช่วงวันที่ (เช่น "ยอดขาย 7
วันที่แล้ว") จะพังทันทีเพราะไลบรารีวันที่ทั้งหมดคาดหวัง ค.ศ.

**Time zone**: server รันที่ไหนก็ได้ในโลก แต่ร้านอยู่ประเทศไทย (`Asia/Bangkok`, UTC+7) กฎทั่วไป:
**เก็บเวลาใน database เป็น UTC เสมอ** (`TIMESTAMPTZ` ของ Postgres ทำแบบนี้อัตโนมัติ) แล้วแปลงเป็น
เวลาไทยเฉพาะตอนแสดงผล ถ้าเก็บเป็นเวลาท้องถิ่นตรงๆ จะมีปัญหาตอนเซิร์ฟเวอร์ย้ายโซนเวลา หรือตอน
daylight saving (ไทยไม่มี DST แต่ถ้าระบบมีลูกค้าอยู่หลายประเทศจะพังทันที)

**Date-string key** (`yyyy-MM-dd`) ใช้เป็น "กุญแจ" ของรายงานรายวัน (เช่น สรุปยอดขายวันที่
2569-09-25) ต้องตัดจาก timestamp แบบ**เวลาท้องถิ่นของร้าน** ไม่ใช่ UTC ตรงๆ — เพราะถ้าร้านขาย
ตอน 23:30 น. ไทย (16:30 UTC) แล้วระบบตัดวันที่จาก UTC จะได้วันที่ผิดไปหนึ่งวัน

### i18n (แปลภาษา) vs "behaviour parity" (ทำตามระบบเดิมเป๊ะ)

**i18n (internationalization)** ทั่วไปหมายถึง: เขียน UI ให้รองรับหลายภาษา แล้ว**แปล**ข้อความ
เป็นภาษาปลายทางให้อ่านลื่นในภาษานั้น — งานแปลตามปกติ

โปรเจกต์นี้**ไม่ใช่งานแบบนั้น** มันคือการ**ย้ายระบบเดิม** (JS/localStorage) ไปเป็นระบบใหม่
(Flutter+NestJS) โดยพฤติกรรมต้อง**เหมือนเดิมทุกตัวอักษร** — ข้อความ error, ป้าย label, ชื่อปุ่ม
ภาษาไทยใน `db.js` เดิม ต้อง copy มาเป๊ะๆ ไม่ใช่ "แปลใหม่ให้เพราะดูดีกว่า" เหตุผล: ผู้ใช้จริง
(พนักงานร้าน) คุ้นเคยกับข้อความเดิม การเปลี่ยนคำแม้เจตนาดีก็ทำให้พนักงานงงหรือค้นหา error ใน
คู่มือ/ประวัติแชทเก่าไม่เจอ — CLAUDE.md เรียกกฎนี้ตรงๆ ว่า "Thai UI strings = behaviour parity"

ช่าง, และแต้มสะสม ถ้าตัวเลขเพี้ยนแม้แค่สตางค์เดียวต่อบิล — สะสมหลักร้อยบิลต่อวัน หลักหมื่นบิลต่อปี
— ยอดในระบบกับเงินสดในลิ้นชักจะไม่ตรงกัน แล้วไม่มีทางไล่หาว่าเพี้ยนตรงไหนเพราะความเพี้ยนแบบ
floating-point ไม่ทิ้ง log อะไรไว้เลย มันแค่ "ผิดนิดเดียว" ทุกครั้งที่บวก

### เก็บเงินยังไง: float vs integer minor-unit vs decimal library

| ทางเลือก | ข้อดี | ข้อเสีย | เลือกไหม |
|---|---|---|---|
| `float`/`double` ตรงๆ (บาท) | เขียนง่าย เข้าใจง่าย | เพี้ยนสะสมได้ (`0.1+0.2`) อันตรายกับเงิน | ❌ ไม่ใช้เก็บ ไม่ใช้คำนวณสะสม |
| **Integer หน่วยสตางค์ (satang)** | บวกลบคูณแม่นยำ 100% ไม่มีการปัดเศษกลางทาง | ต้องแปลงเข้า/ออกทุกจุดที่แสดงผล, เขียนโค้ดมากกว่านิดหน่อย | ✅ **server ใช้แบบนี้** |
| Decimal library (เช่น `decimal.js`, Dart `Decimal` package) | เขียนเป็นทศนิยมตรงๆ ไม่ต้องคิดหน่วยย่อย | เพิ่ม dependency, ช้ากว่า native number, ต้องมีวินัยใช้ให้ครบทุกจุดเหมือนกัน | ❌ ไม่จำเป็นเมื่อ integer แก้ปัญหาได้ตรงจุดกว่า |
| Postgres `NUMERIC` (แม่นยำ, เก็บฐาน 10 จริง) | ไม่มีปัญหา binary rounding เลย เหมาะเป็น "แหล่งความจริง" ใน DB | ช้ากว่า native integer ในการคำนวณเชิงตัวเลขจำนวนมาก | ✅ **ใช้เป็น column type ใน Postgres** (คำนวณจริงยังทำเป็น integer satang ใน service layer ก่อนเขียนลง) |

เหตุผล: **เพราะเงินต้องแม่นยำเป๊ะ → จึงต้องเลี่ยง binary float ทุกจุดที่คำนวณสะสม → ราคาที่จ่าย
คือโค้ดแปลงหน่วย (satang ↔ บาท) ที่ต้องเขียนทุกจุดเข้า-ออก** แลกมาด้วยความมั่นใจว่ายอดจะตรงกับ
เงินสดจริงเสมอ

### rounding: half-up ทุกที่ vs ต่างกันตามจุด

Dart (client) ใช้ `(v*100).round()/100` ซึ่งเป็น "half away from zero" (ปัดออกจากศูนย์เมื่อพอดีครึ่ง)
— ทำงานบน `double` เพี้ยนได้เล็กน้อยตามธรรมชาติของ float TypeScript (server, ต้นทุนถัวเฉลี่ย)
ใช้ integer satang กับ `BigInt` แล้วปัด half-up แบบ exact ไม่ผ่าน float เลย

**ทำไมไม่บังคับให้เหมือนกันทั้งระบบ:** เพราะ Dart repository (`sales_repository.dart` ฯลฯ) คือ
"behavioural reference" ของแอปเดิม (`pos/db.js`) ที่ยังต้องรันได้เหมือนเดิมเป๊ะทุกกรณีสำหรับร้านที่

ของร้านจริงจะเปลี่ยนเลข ส่วน server เป็นระบบใหม่ที่ไม่มีภาระต้องเหมือนของเก่าเป๊ะทุกบิต แต่ต้อง

### 1) `frontend/lib/core/utils/money.dart` — baht/round2/pointsFor/baht2

```dart
// frontend/lib/core/utils/money.dart:1-22
final NumberFormat _bahtFormat = NumberFormat('#,##0.##');
final NumberFormat _baht2Format = NumberFormat('#,##0.00');

/// Formats a number as a baht string, e.g. `฿1,250.5` / `฿85`.
String baht(num v) => '฿${_bahtFormat.format(v)}';

/// Baht with exactly 2 decimals, e.g. `฿1,250.50` / `฿85.00`.
String baht2(num v) => '฿${_baht2Format.format(v)}';

/// JS-exact 2-decimal rounding: `Math.round(v * 100) / 100`.
double round2(num v) => (v * 100).round() / 100;

/// Loyalty points granted for a sale total: `Math.floor(total / 10)`.
int pointsFor(num total) => (total / 10).floor();
```

- **ทำอะไร:** `baht()`/`baht2()` แปลงตัวเลขเป็น string แสดงผลแบบไทย (คั่นหลักพัน, สัญลักษณ์ ฿)
  `round2` ปัดทศนิยม 2 ตำแหน่งแบบเดียวกับ JS เดิม (`Math.round(v*100)/100`) `pointsFor` คำนวณแต้ม
- **เชื่อมกับอะไร:** ทุกหน้าจอที่แสดงราคา (ตะกร้า, ใบเสร็จ, รายงาน) เรียกผ่านฟังก์ชันนี้ทั้งหมด
  ไม่มีที่ไหนเขียน `'฿${...toStringAsFixed(...)}'` เอง (กฎใน Conventions ของ CLAUDE.md)
- **ทำไมเขียนท่านี้:** `round2` ทำงานบน `double` เพราะนี่คือ**ชั้นแสดงผล/ตรรกะฝั่ง client ที่ต้อง
  ตรงกับ `db.js` เดิมทุกบิต** — `Math.round` ของ JS คือ "ปัดออกจากศูนย์เมื่อพอดีครึ่ง" (half away
  from zero) Dart's `.round()` ให้ผลแบบเดียวกันสำหรับค่าบวก จึงพอร์ตตรงๆ ได้โดยไม่ต้องเขียน
  integer arithmetic เพิ่ม เพราะการคำนวณของ client เป็นเลขจำนวนน้อยต่อครั้ง (บิลเดียว) ความเสี่ยง
  สะสมจึงต่ำกว่าฝั่ง server ที่เป็น source of truth ของหลาย tenant
- **ถ้าไม่ทำจะพังยังไง:** ถ้าแต่ละหน้าจอเขียน `toStringAsFixed` เองแทน จะได้การปัดเศษคนละแบบ
  กระจายไปทั่วโค้ด (บางที่ half-up บางที่ truncate โดยไม่ตั้งใจ) วันหนึ่งใบเสร็จหน้าจอกับ PDF
  จะโชว์ตัวเลขไม่ตรงกันสำหรับบิลเดียวกัน

### 2) `server/src/purchasing/weighted-average.ts` — satang half-up แบบ exact integer

```ts
// server/src/purchasing/weighted-average.ts:23-37
export function weightedAverageCostSatang(
  oldStock: number,
  oldCostSatang: number,
  newQty: number,
  lineCostSatang: number,
): number {
  const effective = lineCostSatang > 0 ? lineCostSatang : oldCostSatang;
  const totalQty = oldStock + newQty;
  if (totalQty <= 0) return effective;
  const numerator =
    BigInt(oldStock) * BigInt(oldCostSatang) +
    BigInt(newQty) * BigInt(effective);
  const total = BigInt(totalQty);
  return Number((numerator * 2n + total) / (2n * total));
}
```

- **ทำอะไร:** คำนวณต้นทุนถัวเฉลี่ยถ่วงน้ำหนักตอนรับของเข้าสต็อก (`receivePO`) เป็นหน่วยสตางค์
  ล้วนๆ ไม่ผ่าน float เลย
- **เชื่อมกับอะไร:** `server/src/purchasing/purchase-orders.service.ts` เรียกฟังก์ชันนี้ทุกครั้งที่
  รับสินค้าเข้าคลัง แล้วอัปเดต `products.cost`
- **ทำไมเขียนท่านี้:** สูตรคูณ `oldStock × oldCost` เป็น**สตางค์**ได้ค่าใหญ่เกิน `2^53` (ขีดจำกัด
  ที่ JS number ยังแม่นยำ) เร็วกว่าที่คิด — ของในสต็อกจำนวนมาก × ต้นทุนสตางค์หลักพัน คูณกันทะลุ
  `Number.MAX_SAFE_INTEGER` ได้ไม่ยาก จึงต้องใช้ `BigInt` (จำนวนเต็มขนาดไม่จำกัดของ JS/TS) การปัด
  half-up ทำด้วยเลขคณิตจำนวนเต็มล้วน: `(numerator*2 + total) / (2*total)` คือสูตรบวกครึ่งหนึ่งของ
  ตัวหารก่อนหารเต็ม ๆ (integer division ปัดลงอัตโนมัติ) เท่ากับปัดขึ้นเมื่อเศษ ≥ ครึ่ง — ไม่มีจุด
  ไหนแตะ float เลยสักครั้ง
- **ทำไมต่างจาก Dart's `round2` โดยตั้งใจ:** คอมเมนต์ในซอร์ส (บรรทัด 17-21) บอกตรงๆ ว่า `round2`
  ของ Dart คือ "half away from zero" บน float ซึ่งที่ขอบครึ่งสตางค์พอดี (เช่น `1.005 * 100 =
  100.4999...`) ค่าที่ได้เป็น**สิ่งประดิษฐ์จากการปัดของ float** (artefact) ไม่ใช่กฎที่ตั้งใจ ฝั่ง
  server จึงคำนวณด้วย integer ล้วนเพื่อให้ผลลัพธ์ตรงกับเจตนาจริงเสมอ ไม่ใช่ตรงกับว่า float มัน
  ปัดยังไง
- **ถ้าไม่ทำจะพังยังไง:** ถ้าคำนวณด้วย `double` ธรรมดา ที่ค่าตัวเลขใหญ่ (สต็อกเยอะ × ต้นทุนสูง)
  ความแม่นยำของ float จะไม่พอ ต้นทุนถัวเฉลี่ยจะเพี้ยนไปเรื่อยๆ ทุกครั้งที่รับของ กระทบตัวเลข
  "กำไร" ที่รายงานให้เจ้าของร้านทุกใบ

### 3) `server/src/common/money.ts` — ทำไมเงินวิ่งผ่านสายเป็น string

```ts
// server/src/common/money.ts:1-58 (ย่อ)
export function toSatang(value: unknown, field: string): number {
  const satang = parse(value, field);
  if (Math.abs(satang) > MAX_SATANG) throw badMoney(field, value);
  return satang;
}

function parse(value: unknown, field: string): number {
  if (typeof value === 'number') {
    if (!Number.isFinite(value)) throw badMoney(field, value);
    const satang = value * 100;
    if (Math.abs(satang - Math.round(satang)) > 1e-6)
      throw badMoney(field, value);
    return Math.round(satang);
  }
  if (typeof value === 'string' && /^-?\d+(\.\d{1,2})?$/.test(value.trim())) {
    return Math.round(Number(value.trim()) * 100);
  }
  throw badMoney(field, value);
}

export function fromSatang(satang: number): string {
  const sign = satang < 0 ? '-' : '';
  const abs = Math.abs(satang);
  return `${sign}${Math.trunc(abs / 100)}.${String(abs % 100).padStart(2, '0')}`;
}

export function pointsFor(totalSatang: number): number {
  return Math.floor(totalSatang / 1000);
}
```

- **ทำอะไร:** `toSatang`/`parse` แปลง input จาก client (string หรือ number) เป็น integer satang
  พร้อมตรวจว่าเป็นเงินที่ "สมเหตุสมผล" (ไม่เกิน `NUMERIC(12,2)` ที่กว้างที่สุดในสคีมา, ทศนิยมไม่เกิน
  2 ตำแหน่ง) `fromSatang` แปลงกลับเป็น string `"1234.50"` `pointsFor` หาร 1000 (ไม่ใช่ 10) เพราะ
  หน่วยเป็นสตางค์ (`total/10` บาท = `totalSatang/1000`)
- **เชื่อมกับอะไร:** ทุก endpoint ที่รับ/คืนเงิน (`POST /sales`, `POST /returns`, ...) ผ่านคู่
  ฟังก์ชันนี้ทั้งหมด — คอมเมนต์บรรทัด 3-7 พูดตรงๆ ว่า "0.1+0.2 คือเหตุผลที่ยอดบิลเพี้ยนไปหนึ่ง
  สตางค์จากใบเสร็จกระดาษที่ลูกค้าถืออยู่"
- **ทำไมเขียนท่านี้:** เพราะ**JSON number เป็น IEEE-754 double** — ถ้า backend ส่ง `1234.5`
  (number) ตรงๆ ตัว JSON encoder/decoder ทั้งสองฝั่งต้องผ่าน double อย่างน้อยหนึ่งจุด เปิดช่องให้
  ค่าคลาดเคลื่อนแบบเดียวกับ `0.1+0.2` การส่งเป็น **string** ตัดปัญหานี้ทิ้งตั้งแต่ต้น: string ไม่มี
  การปัดเศษไปมา ฝั่งรับ (`parse`) แปลงเป็น integer satang ของตัวเองตรงๆ ครั้งเดียว
- **ถ้าไม่ทำจะพังยังไง:** ยอดขาย/ยอดคงเหลือที่ backend คำนวณได้ถูกต้อง อาจถูกทำให้เพี้ยนแค่เพราะ
  "ส่งผ่านสาย" — โดยไม่มีใครเปลี่ยนตรรกะธุรกิจเลย บั๊กแบบนี้จับยากที่สุดเพราะโค้ดคำนวณดูถูกทุกจุด

```ts
// server/src/returns/returns.service.ts:1042-1062
function refundAmounts(demands: Demand[], sale: LockedSale): RefundAmounts {
  const refundSubtotalSatang = demands.reduce(
    (s, d) => s + d.qty * d.priceSatang, 0,
  );
  const saleSubtotalSatang = satangOf(sale.subtotal);
  const refundDiscountSatang =
    saleSubtotalSatang > 0
      ? Math.round(
          (refundSubtotalSatang * satangOf(sale.discount)) / saleSubtotalSatang,
        )
      : 0;
  return {
    refundSubtotalSatang,
    refundDiscountSatang,
    refundTotalSatang: refundSubtotalSatang - refundDiscountSatang,
    saleTotalSatang: satangOf(sale.total),
  };
}
```

  (`34 × 0.25 = 8.5` → `floor` = 8) ใช้ `floor` ไม่ใช่ `round` เพื่อ**ไม่คืนแต้มเกิน**กว่าที่สัดส่วน
  จริงอนุญาต (ดูหลักการเดียวกับ `pointsFor` — ปัดลงเสมอฝั่งที่เอื้อประโยชน์ลูกค้า)
- **ทำไมต้องมี guard `> 0` ก่อนหาร:** กันหารด้วยศูนย์ (ถ้าบิลนำเข้าจากระบบเก่าไม่มียอดขายบันทึกไว้)
- **ถ้าไม่ทำแบบสัดส่วน:** ลูกค้าคืนของ 3 ครั้งจากบิลเดียว อาจได้คืนแต้ม/ส่วนลดรวมมากกว่าที่ซื้อจริง
  ถ้าคำนวณแบบ "หารเท่าๆ กันแล้วบวกสะสม" แทนที่จะคำนวณจากยอดขายจริงทุกครั้ง (จุดที่ 6.3.5 ธุรกิจ
  `assertRefundable` ป้องกันคืนเกินจำนวนที่ซื้อไว้แล้ว — เห็นในหัวข้อ "ปัญหาจริงของร้าน")

### 6) NUMERIC columns ใน migration — แหล่งความจริงของ scale

```ts
// server/src/db/migrations/1788652800000-InitialSchema.ts:160-161, 295-297

cost       NUMERIC(12,2) NOT NULL CHECK (cost  >= 0),
...
```

- **ทำอะไร:** ประกาศ column เงินเป็น `NUMERIC(12,2)` (สูงสุด 12 หลัก 2 ตำแหน่งทศนิยม) ไม่ใช่
  `FLOAT`/`REAL`
- **ทำไมเขียนท่านี้:** `NUMERIC` ของ Postgres เก็บเป็นเลขฐาน 10 แม่นยำเป๊ะ ไม่ผ่าน binary
  floating-point เลย ตรงกันข้ามกับ `FLOAT8` ที่เป็น IEEE-754 double เหมือนที่ทำให้ `0.1+0.2`
  เพี้ยนในโปรแกรม — ถ้าใช้ `FLOAT` เก็บราคา จะได้ปัญหาเดียวกันแต่ย้ายไปอยู่ใน DB แทน `toSatang`
  ใน `money.ts` อ้าง `MAX_SATANG` จาก scale นี้ตรงๆ (`NUMERIC(12,2)` = 10 หลักก่อนจุด → ค่าสูงสุด
  `9_999_999_999.99` บาท)
- **ถ้าไม่ทำ:** เก็บ `FLOAT` แล้วรัน query สรุปยอดขาย (`SUM(total)`) ข้ามหลายพันแถว ผลรวมจะเพี้ยน
  สะสมจาก floating-point error ของ Postgres เองตรงๆ

(`docs/Backend_design/adr/0007-receipt-numbering.md:13-22` — ยืนยันแล้วว่า `RC01-2569-08-0042`

  กันแค่ตำแหน่งขีด) — บทเรียน Unicode/string-parsing เล็กๆ: การ zero-pad ไม่ใช่แค่ความสวยงาม แต่

### 10) `csvSafe` — CSV injection (ความปลอดภัยที่ซ่อนอยู่ในเรื่อง encoding)

```dart
// frontend/lib/core/utils/csv_safe.dart:14-22
const _triggers = {'=', '+', '-', '@', '\t', '\r'};

String csvSafe(Object? v) {
  final s = v == null ? '' : v.toString();
  if (s.isNotEmpty && _triggers.contains(s[0])) {
    return "'$s";
  }
  return s;
}
```

- **ทำอะไร:** ถ้าค่าที่จะเขียนลง CSV ขึ้นต้นด้วย `= + - @ TAB CR` ให้เติม `'` (single quote) นำหน้า
- **ทำไมต้องมี:** Excel/Google Sheets ตีความเซลล์ที่ขึ้นต้นด้วยสัญลักษณ์เหล่านี้เป็น **formula**
  ไม่ใช่ข้อความ — ถ้าชื่อลูกค้าหรือชื่อสินค้าดันเป็น `=1+1` หรือแย่กว่านั้นคือ formula ที่เรียก
  โปรแกรมภายนอก (`=cmd|...`) พอ export CSV แล้วเปิดใน Excel มันจะ**รันสูตรนั้นทันที** — นี่คือช่อง
  โหว่ความปลอดภัยจริงชื่อ **CSV/Formula Injection** (โค้ดคอมเมนต์อ้างเป็น SEC-002) การเติม `'`
  นำหน้าบอก Excel ว่า "นี่คือ text เฉยๆ" ปิดช่องโหว่ทันที
- **เชื่อมกับ Unicode ยังไง:** เป็นตัวอย่างว่า "string ที่ดูเหมือนข้อมูลธรรมดา" อาจถูกโปรแกรม
  ปลายทางตีความเป็นคำสั่งได้เสมอ — บทเรียนเดียวกับที่การเข้ารหัสอักขระ (encoding) ต้องคิดถึง
  "ผู้บริโภคข้อมูล" ไม่ใช่แค่ "ผู้ผลิตข้อมูล"
- **ถ้าไม่ทำ:** export รายงานลูกค้า/สินค้าเป็น CSV แล้วเปิดใน Excel เจ้าของร้านอาจโดนรันโค้ด
  อันตรายโดยไม่รู้ตัว แค่เพราะเปิดไฟล์ที่ระบบตัวเอง export ออกมา

### เทคนิค 1: Integer minor-unit (satang) แทน float

**คืออะไร:** เก็บและคำนวณเงินเป็นจำนวนเต็มของหน่วยย่อยสุด (1 บาท = 100 สตางค์) แทนทศนิยม —
เหมือนร้านทองชั่งทองเป็น "สตางค์ทอง" แทนที่จะกะด้วยสายตา จะได้ตัวเลขที่ตรงกันทุกครั้ง

**ปัญหาที่มันแก้:** `double`/`float` เก็บเลขฐาน 2 โดยประมาณ ทศนิยมฐาน 10 หลายตัว (0.1, 0.2, 0.3, ...)
ไม่มีค่าตรงในฐาน 2 บวกสะสมหลายพันบิลจะเพี้ยนสะสมทีละนิดจนยอดในระบบไม่ตรงกับเงินสดจริง

**ทำไมเลือกท่านี้ (เทียบกับ decimal library):** ใช้ integer ธรรมดา (`number`/`BigInt` ใน TS) เร็ว
กว่า และไม่ต้องเพิ่ม dependency ภายนอกอย่าง `decimal.js` — ข้อแลกคือทุกจุดที่รับ/ส่งเงินต้องแปลง
หน่วยเอง (`toSatang`/`fromSatang`) ถ้าลืมแปลงจุดใดจุดหนึ่งจะปนกันระหว่าง "หน่วยบาท" กับ "หน่วย
สตางค์" ทันที (บั๊กเงียบ x100 หรือ /100) — decimal library ตัดความเสี่ยงนี้ได้แต่แลกด้วย
dependency และความเร็ว

**ดียังไง / ราคาที่จ่าย:** ดี — คำนวณแม่นยำ 100% ไม่มีการปัดเศษกลางทาง ราคา — เพิ่มโค้ดแปลงหน่วย
ทุกจุดเข้า-ออก ต้องมีวินัยไม่ผสมหน่วยกัน (guard ด้วย type ก็ช่วยได้ระดับหนึ่งแต่ TypeScript ไม่มี
"branded type" ในนี้ ดังนั้นต้องพึ่งชื่อฟังก์ชัน `xxxSatang` เป็นสัญญาแทน)

**อยู่ตรงไหนใน repo:** `server/src/common/money.ts` (แปลงหน่วย), `server/src/purchasing/weighted-average.ts`
(คำนวณด้วย `BigInt`), ทุก service ที่รับ `dto.totalSatang`/`priceSatang`

### เทคนิค 2: ส่งเงินผ่านสายเป็น string

**คืออะไร:** เมื่อ backend ตอบกลับยอดเงินผ่าน HTTP/JSON ส่งเป็น `"1234.50"` (ข้อความ) ไม่ใช่
`1234.50` (ตัวเลข JSON) — เหมือนเขียนตัวเลขบนเช็คด้วยตัวหนังสือ ไม่ใช่แค่ตัวเลข เพื่อไม่ให้ใคร
"อ่านผิด"

**ปัญหาที่มันแก้:** มาตรฐาน JSON กำหนดให้ number ทุกตัวเป็น IEEE-754 double — เหมือนกับ
`double`/`float` ในโปรแกรม ถ้าส่งเลขเงินเป็น JSON number ตรงๆ การ encode/decode ผ่านสายจะเสี่ยง
เพี้ยนแบบเดียวกับ `0.1+0.2` แม้ว่าตอนคำนวณฝั่ง server จะแม่นยำเป๊ะด้วย integer satang ก็ตาม —
ความเพี้ยนเกิด "ตอนส่ง" ไม่ใช่ "ตอนคำนวณ"

**ทำไมเลือกท่านี้ (เทียบกับส่งเป็น number แล้วปัดฝั่ง client อีกที):** การปัดฝั่ง client แก้ผลลัพธ์
ที่แสดงให้ดูถูก แต่ไม่ได้แก้ที่ต้นตอ — ถ้า client เอาค่านั้นไปคำนวณต่อ (เช่น รวมกับเลขอื่น) ความ
เพี้ยนที่ปัดไปแล้วอาจกลับมาโผล่ในผลลัพธ์รวม ส่ง string ตัดปัญหาตั้งแต่ประตูสายเข้า-ออก

**ดียังไง / ราคาที่จ่าย:** ดี — ไม่มีจุดไหนในทั้งระบบที่เงินผ่าน float โดยไม่ตั้งใจ ราคา — client
ต้อง parse string เป็น integer เองทุกครั้ง (เขียนโค้ดเพิ่ม), เขียน JSON schema/type ให้ตรงกันทั้ง
สองฝั่ง (field เงินเป็น `string` เสมอ ไม่ใช่ `number`)

**อยู่ตรงไหนใน repo:** `server/src/common/money.ts:1-8` (คอมเมนต์อธิบายเหตุผลตรงๆ),

### เทคนิค 3: การแบ่งสัดส่วน (proportional allocation) จากยอดต้นทางเสมอ ไม่ใช่หารสะสม

**ปัญหาที่มันแก้:** ถ้าหารเท่าๆ กันไว้ก่อน (เช่น ส่วนลด 10 บาท ÷ ของ 3 ชิ้น = 3.33 ต่อชิ้น) แล้วคืน

คลาดเคลื่อนสะสม

ทุกการคืนจะไม่มีวันเกินยอดเดิม" เพราะแต่ละครั้งคือสัดส่วนจริงของสิ่งที่เหลือ ณ ตอนนั้น ไม่ใช่ค่าคง
ที่ที่คำนวณไว้ล่วงหน้าแล้วอาจไม่ตรงกับสถานการณ์จริง (เช่น คืนซ้อนกันจากสองเครื่องพร้อมกัน)

[07_database.md](07_database.md) เรื่อง row lock)

### เทคนิค 4: เก็บวันที่เป็น ค.ศ./UTC เสมอ แปลงเป็น พ.ศ./เวลาไทยเฉพาะตอนแสดงผล

**คืออะไร:** database และตรรกะภายในเก็บวันที่แบบสากล (ค.ศ., UTC) ส่วน "พ.ศ." และ "เวลาไทย" เป็น
แค่**การแปลงหน้าจอ** ครั้งเดียวตอนจะแสดงให้คนอ่าน — เหมือนนาฬิกาสนามบินตั้งเป็น UTC ทุกเมืองใน
ห้องเดียวกัน แล้วแต่ละจอแปลงเป็นเวลาท้องถิ่นของเมืองนั้นตอนแสดงผล

**ปัญหาที่มันแก้:** ถ้าเก็บ พ.ศ. หรือเวลาท้องถิ่นตรงๆ ลง DB ทุกไลบรารีวันที่ (ที่คาดหวัง ค.ศ./UTC
เป็นมาตรฐาน) จะคำนวณช่วงวันที่/เปรียบเทียบวันที่ผิดทันที และถ้าระบบข้ามโซนเวลา (server ไม่ได้อยู่
ไทย) จะยิ่งสับสน

**ทำไมเลือกท่านี้ (เทียบกับเก็บ พ.ศ./เวลาไทยตรงๆ):** เก็บสากลแล้วแปลงตอนแสดงผล คือรูปแบบที่ทุก
ไลบรารีมาตรฐาน (`DateTime`, Postgres `TIMESTAMPTZ`) ออกแบบมาให้ใช้แบบนี้อยู่แล้ว — สลับข้างจะฝืน
เครื่องมือทุกตัว

**ข้อยกเว้นที่ตั้งใจ:** `dateKey`/`todayKey` (`frontend/lib/core/utils/dates.dart`) ใช้เวลา
**ท้องถิ่นของเครื่อง** ไม่ใช่ UTC เพราะมันเป็น "กุญแจของวันทำการร้าน" ไม่ใช่ timestamp ที่เก็บถาวร
— นี่คือจุดที่ต้องแยกให้ออกระหว่าง "เก็บถาวร" กับ "ใช้เป็นกุญแจกลุ่มข้อมูลของวันนั้น"

**ดียังไง / ราคาที่จ่าย:** ดี — คำนวณช่วงวันที่/เปรียบเทียบถูกต้องเสมอไม่ว่า server อยู่โซนไหน
ราคา — ต้องจำกฎ "แปลงตอนแสดงผลเท่านั้น" ให้ทุกจุดในโค้ด ถ้ามีจุดไหนแปลงแล้วเก็บกลับ (เช่น บวก 543
แล้ว save) จะพังทันที

**อยู่ตรงไหนใน repo:** `frontend/lib/presentation/widgets/thai_format.dart:12-35` (แปลงตอนแสดง),
`frontend/lib/core/utils/dates.dart:1-11` (กุญแจท้องถิ่น), Postgres `TIMESTAMPTZ` columns ใน
migration (เก็บ UTC อัตโนมัติ)

## ✅ สรุป

- เก็บเงินเป็น `float`/`double` ไม่ได้เด็ดขาด เพราะ IEEE-754 เก็บทศนิยมฐาน 10 หลายตัวไม่ตรงในฐาน 2
  (`0.1+0.2 != 0.3`) — โปรเจกต์นี้แก้ด้วย **integer หน่วยสตางค์** ฝั่ง server
- Dart (client) ใช้ `round2` แบบ float ตรงกับ `db.js` เดิม (behaviour parity ของ offline build)
  ส่วน TypeScript (server) คำนวณต้นทุนถัวเฉลี่ยด้วย `BigInt` integer ล้วน — **ต่างกันโดยตั้งใจ**
  เพราะคนละบทบาท (client = พอร์ตของเดิม, server = source of truth ใหม่)
- เงินวิ่งผ่าน HTTP/JSON เป็น **string** (`"1234.50"`) เสมอ เพราะ JSON number คือ IEEE-754 double
- แบ่งสัดส่วน (คืนของบางส่วน) ต้องคำนวณจากยอดต้นทางทุกครั้ง ไม่ใช่หารแบ่งไว้ล่วงหน้าแล้วบวกสะสม —
  กันเศษสตางค์หาย/เกิน
- Postgres ใช้ `NUMERIC(12,2)` เก็บเงิน (แม่นยำเป๊ะ ต่างจาก `FLOAT`)
- ค.ศ./UTC สำหรับเก็บถาวรและคำนวณ, พ.ศ./เวลาไทยแปลงเฉพาะตอนแสดงผล ยกเว้น `dateKey` ที่ตั้งใจใช้
  เวลาท้องถิ่นเพราะเป็นกุญแจของ "วันทำการร้าน"
- Thai UI strings = behaviour parity เสมอ — copy จาก `db.js`/`.jsx` เป๊ะ ไม่ใช่งานแปลภาษาใหม่
- UTF-8 เก็บตัวอักษรไทยด้วย 3 byte/ตัว (ASCII ใช้ 1 byte) — กระทบทั้งความยาว string, การตัด
  string, และ font/glyph fallback ที่ engine ต้องรู้จักชัดเจน
- เลขเอกสาร (ADR-0007) คือ `RC01-2569-08-0042` — เครื่อง+พ.ศ.เดือน+ลำดับ zero-padded ทั้งหมด กัน
  ความกำกวมตอน parse
- `csvSafe` ปิดช่องโหว่ CSV/Formula Injection — ตัวอย่างจริงว่า encoding/string handling เชื่อมกับ
  ความปลอดภัยโดยตรง
- ของยังไม่เสร็จ/ยังพัง: Flutter web engine ยัง fetch `fonts.gstatic.com` สำหรับ fallback-glyph
  (เช่น emoji), web service worker ยังไม่ precache อะไรเลย (บล็อกอยู่ที่ #241)

## ❓ Quiz

**1. ทำไม `0.1 + 0.2` ใน Dart/JavaScript ถึงไม่เท่ากับ `0.3` เป๊ะ ทั้งที่มนุษย์บวกเลขนี้ได้ตรงๆ?**

<details><summary>เฉลย</summary>

เพราะคอมพิวเตอร์เก็บทศนิยมแบบ IEEE-754 ซึ่งเป็นฐาน 2 เลขฐาน 10 บางตัว เช่น 0.1 และ 0.2 ไม่มีค่า
ตรงในฐาน 2 (เหมือน 1/3 ไม่มีค่าตรงในฐาน 10) จึงถูกตัดปัดเป็นค่าที่ใกล้เคียงที่สุดใน 64 bit พอบวก
ค่าที่ถูกตัดปัดสองตัวเข้าด้วยกัน ผลจึงคลาดเคลื่อนไปเล็กน้อยในหลักท้ายๆ (`0.30000000000000004`)

</details>

**2. ทำไม `server/src/purchasing/weighted-average.ts` ต้องใช้ `BigInt` แทนที่จะคูณเลขธรรมดา (`number`) ตรงๆ?**

<details><summary>เฉลย</summary>

เพราะการคูณ `oldStock × oldCostSatang` (สต็อกจำนวนมาก คูณต้นทุนเป็นหน่วยสตางค์) อาจได้ค่าใหญ่เกิน
`Number.MAX_SAFE_INTEGER` (2^53) ซึ่งเป็นขีดจำกัดที่ JS/TS number ยังแม่นยำ 100% เกินกว่านั้นตัวเลข
เต็มจะเริ่มเพี้ยนได้ (ปัดตัดบิตท้าย) `BigInt` เป็นจำนวนเต็มขนาดไม่จำกัด คำนวณได้แม่นยำเป๊ะไม่ว่าค่า
จะใหญ่แค่ไหน

</details>

**3. ทำไม `round2` ของ Dart (float, half-away-from-zero) กับต้นทุนถัวเฉลี่ยของ server (integer, half-up) ถึงปัดเศษไม่เหมือนกัน ทั้งที่เป็นระบบเดียวกัน? นี่คือบั๊กหรือตั้งใจ?**

<details><summary>เฉลย</summary>

ตั้งใจ Dart repository คือ "behavioural reference" ที่ต้องพอร์ต `db.js` เดิมให้เหมือนเป๊ะ (รวมถึง
artefact จากการปัดเศษ float ที่ `db.js` เดิมก็มี) เพราะร้านที่ยังใช้ offline build
(`POC_sample_offline_first`) ต้องได้ใบเสร็จหน้าตาเดียวกับที่คุ้นเคย ส่วน server เป็นระบบใหม่ที่ไม่มี
ภาระต้องเหมือนของเก่าเป๊ะทุกบิต แต่ต้องแม่นยำเป๊ะเพราะเป็น source of truth จึงคำนวณด้วย integer
ล้วนไม่ผ่าน float — คอมเมนต์ในซอร์สยืนยันเหตุผลนี้ตรงๆ

</details>

**4. ทำไมยอดเงินที่ backend ตอบกลับผ่าน HTTP ต้องเป็น `"1234.50"` (string) แทนที่จะเป็น `1234.50` (number ธรรมดาใน JSON)? ถ้าส่งเป็น number จะเกิดอะไร?**

<details><summary>เฉลย</summary>

เพราะมาตรฐาน JSON กำหนดให้ number ทุกตัวเป็น IEEE-754 double เดียวกับที่ทำให้ `0.1+0.2` เพี้ยน
ถ้าส่งเงินเป็น JSON number ตรงๆ ทั้งฝั่งเข้ารหัสและถอดรหัส JSON ต้องผ่าน double อย่างน้อยหนึ่งจุด
เปิดช่องให้ค่าคลาดเคลื่อนได้ แม้ว่าตัวเลขจะคำนวณถูกต้องแม่นยำอยู่แล้วในหน่วยสตางค์ก่อนส่งก็ตาม
ส่งเป็น string ตัดปัญหานี้ทิ้งตั้งแต่ต้นเพราะ string ไม่ผ่านการปัดเศษใดๆ

</details>

**5. ทำไมคืนของบางส่วนถึงต้องคำนวณส่วนลด/แต้มที่คืนจาก "ยอดขายเดิมทั้งบิล" ใหม่ทุกครั้ง แทนที่จะหารส่วนลดเท่าๆ กันไว้ล่วงหน้าตามจำนวนชิ้นแล้วบวกสะสมตอนคืน?**

<details><summary>เฉลย</summary>

เพราะการหารไว้ล่วงหน้า (เช่น ส่วนลด 10 บาท ÷ 3 ชิ้น = 3.33 ต่อชิ้น) แล้วบวกสะสมทีละครั้งที่คืน จะ
ได้ผลรวมไม่เท่าของเดิมเป๊ะ (3.33×3 = 9.99 ไม่ใช่ 10) เพราะการปัดเศษเกิดซ้ำหลายรอบ คำนวณจากฐานเดิม
ทุกครั้งรับประกันว่าผลรวมของทุกการคืนจะไม่มีวันเกินหรือขาดจากยอดเดิม เพราะแต่ละครั้งคือสัดส่วนจริง
ของสิ่งที่เหลือ ณ ตอนนั้น

</details>

**6. ทำไม path ที่มีตัวอักษรไทย (เช่น `ร้านศรี`) ถึงทำให้ `build_runner` ของ Dart พัง ทั้งที่ `flutter build`/`flutter test` รันได้ปกติบน path เดียวกัน? เกี่ยวอะไรกับ UTF-8?**

<details><summary>เฉลย</summary>

ตัวอักษรไทยใน UTF-8 ใช้ 3 byte ต่อตัว (ต่างจาก ASCII ที่ใช้ 1 byte) `build_runner` (และ AOT
compiler ที่มันเรียกใช้) มีจุดหนึ่งในเครื่องมือที่แปลง/ตีความ path เป็น byte ผิดพลาดเมื่อเจอ
ตัวอักษรนอกช่วง ASCII ทำให้ path ถูก mangle เป็น `???????` แล้วเขียนไฟล์ output ไม่ได้ เครื่องมืออื่น
(`flutter build`, `flutter test`) ไม่ได้พังเพราะไม่ได้เดินผ่านจุดเดียวกันในทางเทคนิค วิธีแก้จริงคือ
ย้าย repo ไป path ที่เป็น ASCII ล้วนก่อนรัน `build_runner`

</details>
