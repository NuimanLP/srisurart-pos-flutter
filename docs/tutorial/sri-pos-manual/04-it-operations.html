รันทั้งระบบบนเครื่องตัวเอง Run locally (dev only)

คำสั่งครบทุกขั้นอยู่ใน docs/tutorial/local-full-stack-tutorial.md — หน้านี้คือลำดับ SOP ย่อ ใช้ค่า placeholder และ cert self-signed เฉพาะ dev

  1. เปิด Docker Desktopรอจน docker ps ไม่ error
  2. เตรียม server/.env (ครั้งเดียว)cd server && cp .env.example .env — ไฟล์ตั้ง ALLOW_DEV_SECRETS=true ให้ (ไฟล์ .env เก่าก่อน #412 ต้องเติมบรรทัดนี้เอง)
  3. ขึ้นสแตก + monitoring 
    docker compose -f docker-compose.yml -f docker-compose.dev.yml -f ../deploy/compose/monitoring.yml up -d --build
    รอ ~30–40 วินาทีให้ docker ps --format '{{.Names}}: {{.Status}}' ไม่มี (health: starting)
  4. ตรวจ APIcurl -sk https://localhost/health/live และ /health/ready{"status":"success","data":{"status":"up",…}}
  5. รัน tlswrap (dev เท่านั้น)เพราะ Flutter web ใช้ fetch() กับ cert self-signed ไม่ได้ — คำสั่งอยู่ในบทเรียนข้อ 4 (ข้ามได้ถ้ารันอยู่แล้ว)
  6. สร้างผู้ดูแลแพลตฟอร์ม + ร้านแรกตามภาค 03 หัวข้อ 1–2
  7. รัน Flutter web ชี้ไปที่ backend 
    cd frontend && flutter pub get
flutter run -d web-server --web-port=8090 --web-hostname=127.0.0.1 \
  --dart-define=USE_API_WRITES=true --dart-define=API_BASE_URL=http://127.0.0.1:8081
    เปิด http://127.0.0.1:8090 (HTTP ธรรมดา ไม่ใช่ https://localhost) — สินค้า seed ของ Drift ปนกับของเซิร์ฟเวอร์ ไม่ใช่บั๊ก
  8. หยุด (เก็บข้อมูล)ใช้ stop ด้วยชุด -f เดิม และ docker stop tlswrap
ใส่ชุด -f เดิมทุกคำสั่งลืม -f ในคำสั่งตามหลัง (เช่น run migrate) → Compose สร้าง postgres ใหม่และพอร์ตของ dev overlay หาย · down -v ลบ volume ของทุก session บน daemon เดียวกัน
โฟลเดอร์ BeeStationถ้า docker build ล้มด้วย load build context: invalid file request — ไฟล์เป็น placeholder ของคลาวด์ ให้ build จาก git archive HEAD server ไปโฟลเดอร์ ASCII แล้ว up -d โดยไม่ใส่ --build

ตรวจสุขภาพระบบ Health checks

  1. ทุกคอนเทนเนอร์ healthydocker ps --format '{{.Names}}: {{.Status}}'ทุกตัว (healthy) — ยกเว้น etcd ที่อาจ (unhealthy) บนเครื่อง dev ที่มี volume เก่า (#365) ซึ่งไม่บล็อกอะไร
  2. GET /health/liveบอกแค่ว่า process ยังอยู่ ไม่แตะฐานข้อมูล (ตั้งใจ — ฐานข้อมูลล่มต้องไม่ทำให้ API ถูก restart ทั้งหมด)
  3. GET /health/readyเช็ก Postgres + Redis ทั้งสองตัว timeout 2 วินาที200 = พร้อม · 503 = มีรายละเอียดว่าตัวไหนล้ม (ไม่ได้เช็ก etcd โดยตั้งใจ)
  4. ดู log ของตัวที่มีปัญหาdocker compose logs <service> (ใส่ชุด -f เดิม)
  5. ดูแดชบอร์ดอัตราสำเร็จของ API และ p95 ใน Grafana (ภาค 05)
ทดสอบเข้าสู่ระบบของร้าน 
curl -sk https://localhost/api/v1/auth/token -H "Content-Type: application/json" \
  -d '{"username":"<owner>","password":"<รหัส>"}'
ครั้งแรกด้วยรหัสชั่วคราวจะได้ passwordChangeRequired: true + passwordChangeToken (10 นาที) ไม่ใช่ access token — ตั้งรหัสใหม่ผ่าน POST /api/v1/auth/change-password (ดูบทเรียนข้อ 5.3)
ทำไม SLI ไม่นับ health/metrics, /health/live, /health/ready ถูกตัดออกจากตัวเลขอัตราสำเร็จ — ถ้านับ การ scrape ทุก 15 วิ × 3 instance + healthcheck จะสร้าง 200 ปลอม ~36 ครั้ง/นาที จนวันที่ขายพังทั้งวันยังดูปกติ ~92%

Deploy ขึ้น mob04 · อนุมัติ · ย้อนเวอร์ชัน Deploy & rollback

อ่านก่อน — ยังไม่เคย deploy สำเร็จ Not yet deliveredขั้นตอนข้างล่างคือสิ่งที่ pipeline และ playbook ออกแบบไว้ · ยังไม่เคยมี release ขึ้น mob04 จริง: firewall ของคณะตอบ ghcr.io ด้วยใบรับรองไม่มี SAN (x509: certificate is not valid for any names) และ self-hosted runner ยังไม่ได้ติดตั้ง (0 ตัว) · docker save/load ด้วยมือเป็นแค่ทางกู้วันเดโม ไม่ใช่ CD

ลำดับที่ pipeline ทำ Pipeline

  1. PR ผ่าน CI (flutter-ci-status, server-ci-status) → merge เข้า main
  2. build + Trivy + push อิมเมจ server และ web ขึ้น GHCR (แท็ก SHA)
  3. workflow Deploy (demo) งาน resolve เช็กว่าอิมเมจทั้งสองของ SHA นั้นมีครบ
  4. งาน deploy ค้างที่ "Waiting for review" จนผู้อนุมัติ (NuimanLP) กด approveนี่คือกลไกเดียวที่กันไม่ให้ merge ระหว่างเดโมขึ้น VM
  5. runner บน VM เรียก pos-deploy → ansible-playbook deploy.ymlpull → web-sync → migrate (schema ก่อนโค้ดเสมอ) → etcd-init → restart api-1→api-2→api-3→worker/bull-board → ตรวจ nginx -t แล้วสร้าง nginx ใหม่ → /health/ready ต้อง 200 → เขียน /opt/pos/.current_sha → monitoring (ล้มได้แค่เตือน)
หลักฐานเดียวที่นับรัน Deploy (demo) ที่ขึ้น เขียว ไม่ได้แปลว่าขึ้นเครื่อง — ถ้าอิมเมจยังไม่ครบ งาน deploy ถูกข้ามแต่ workflow ยังรายงานสำเร็จ · ตรวจ /opt/pos/.current_sha บน VM เท่านั้น · ถ้ามีหลายรันรออนุมัติ การอนุมัติรันเก่าก่อนจะส่ง SHA เก่าขึ้นก่อน

ย้อนเวอร์ชัน Rollback

อัตโนมัติ: playbook ล้มหรือเกิน 20 นาที → pos-deploy redeploy SHA ใน .current_sha (รันยังขึ้นแดง ให้ตามดูสาเหตุ)

ด้วยมือ (release ใหม่ขึ้นแล้วแต่ใช้งานไม่ได้):

  1. หา SHA ที่จะถอยกลับต้อง (1) อยู่บน main (2) เป็น commit rollback floor (4f3a244) หรือใหม่กว่า — pos-deploy ปฏิเสธ SHA ที่เก่ากว่านั้น (3) มีอิมเมจทั้ง server และ web บน GHCR
  2. GitHub → Actions → Deploy (demo) → Run workflow → ใส่ image_tag = SHA นั้น
  3. ผู้อนุมัติ (NuimanLP) กด approve งาน deployถ้ามีรันอื่นรออนุมัติค้างอยู่ ให้ปฏิเสธ/ยกเลิกก่อน ไม่งั้นอาจส่ง SHA ผิดตัวขึ้นก่อน
  4. ยืนยันบน VMssh deploy@<vm> cat /opt/pos/.current_sha ต้องเท่ากับ SHA ที่เลือก · curl -sk https://localhost/health/ready บน VM ต้อง 200เขียวใน Actions อย่างเดียว ไม่นับ (ดูกล่องด้านบน)
schema ไม่ถอยหลังเด็ดขาดrollback ถอยแค่โค้ด ไม่ถอย migration — migration ต้องเป็นแบบ expand/contract เพราะโค้ดเก่าต้องรันบน schema ใหม่ได้ (ระหว่าง rolling restart และหลัง rollback)

Section 5

สำรองข้อมูล · etcd Backup & etcd

ข้อจำกัดปัจจุบัน — ยังไม่มี backup ออกนอก VM No offsite backup
  • ไม่เคยมี backup ออกจาก VM เลย และไม่เคยพิสูจน์การกู้จากสำเนานอก VM — ดิสก์ mob04 เสีย = ข้อมูลร้าน demo หาย
  • ตาม README.md (หัวข้อ Deployment → Operations) cron backup ยังไม่ได้ถูก apply บน mob04 (crontab ว่าง ไม่มีโฟลเดอร์ backups) — บน VM จึงยังไม่มี backup รันเลย
  • งาน offsite (#363/#288) พักไว้จนหลังเดโม · ปลายทางตัดสินแล้วคือ NAS ของร้าน แต่โปรโตคอลยังไม่ได้เลือก (BeeStation ไม่มี SFTP — เหลือ smb ของ rclone หรือซื้อ NAS ที่เป็น DSM)
  • ห้ามเขียนว่า "backup พร้อมแล้ว" ที่ไหนก็ตาม

backup-db.sh ทำอะไร (เมื่อติดตั้งแล้ว) What the script does

  1. cron ของ user deploy เวลา 03:00
  2. pg_dump --create → gzip → checksum → /opt/pos/backups (0700)เก็บ BACKUP_KEEP_DAYS วัน (ค่าเริ่มต้น 7)
  3. offsite ผ่าน rclone (ถ้าตั้งค่า)BACKUP_RCLONE_REMOTE ว่าง → เตือน ::warning:: 1 บรรทัด แล้ว exit 0 · ตั้งไว้แต่พัง → ::error:: + exit ไม่เป็น 0
อ่าน log ให้ถูกbackup-cron.log ที่ไม่มี error ไม่ได้พิสูจน์ ว่าสำเนาออกจาก VM — ต้องอ่านบรรทัด ::warning::/::error:: · วันที่เปิดใช้ offsite ครั้งแรก ให้ upload ไฟล์เก่าที่ไม่มี marker .uploaded ด้วยมือหนึ่งครั้ง

กู้คืนจาก dump ในเครื่อง: deploy/scripts/restore-db.sh <ไฟล์.sql.gz> [ฐานข้อมูล] — ตรวจ checksum และตรวจค่า timeout ของ pos_app หลังกู้

etcd Runtime config

  • เก็บเฉพาะค่าตั้งไม่ลับ วันนี้มีคีย์เดียว /pos/config/log_level
  • etcd-init สร้าง root เปิด RBAC แล้ว ตรวจ ว่า root เข้าได้และผู้ไม่ระบุตัวถูกปฏิเสธ
  • รหัส root ถูกฝังตอนบูตครั้งแรกเท่านั้น — แก้ ETCD_ROOT_PASSWORD ใน .env ภายหลังไม่เปลี่ยนรหัสจริง อาการคือ "ไม่ green" ไม่ใช่ข้อความเรื่องรหัส
  • รีเซ็ตให้ใช้ etcdctl user passwd root ห้าม down -v — แต่ลำดับคำสั่งที่รันได้จริงยังไม่มี

เปิด log ละเอียดชั่วคราว (ไม่ต้อง restart)

  1. ตั้งเป็น debug(ใส่ชุด -f เดิมของเครื่องนั้นหลัง docker compose) 
    docker compose exec etcd etcdctl --endpoints=http://127.0.0.1:2379 put /pos/config/log_level debug
docker compose exec etcd etcdctl --endpoints=http://127.0.0.1:2379 get /pos/config/log_level
    ภายในไม่กี่วินาที log ของ API (docker compose logs -f api-1) ละเอียดขึ้น
  2. เก็บข้อมูลที่ต้องการแล้ว ตั้งกลับเป็น infoคำสั่งเดิม เปลี่ยน debug เป็น info — log debug ใช้ดิสก์เร็ว

ถ้ายังไม่เคยตั้งคีย์นี้ get จะไม่คืนอะไรเลย และระบบใช้ LOG_LEVEL ใน .env · ถ้า etcd ล่มหรือรหัสไม่ตรง API ยังทำงานต่อด้วยค่าใน .env (fail-open) — คำสั่งละเอียดและวิธีพิสูจน์ว่า etcd ปฏิเสธผู้ไม่ระบุตัว อยู่ใน server/README.md หัวข้อ Dynamic config

ข้อจำกัดปัจจุบัน Current limitationsบน mob04 etcd ยังไม่เคยเปิด auth (#365) — etcd-init.sh บน VM เป็นโฟลเดอร์ว่างของ root ต้องทำพร้อมรอบขึ้น VM ของ #343 และพิสูจน์ทั้งสองทาง (ใส่รหัสผ่านได้ / ไม่ใส่ถูกปฏิเสธ)

ความลับ · กฎ .env Secrets

  • ALLOW_DEV_SECRETS=true ให้ api/worker/bull-board บูตด้วยค่า dev-only-* ได้ — dev/CI เท่านั้น · vm.override.yml บังคับให้ว่างบน mob04
  • ตัวแปรที่จำเป็นใช้รูป ${VAR:?…} — ขาดตัวไหน docker compose ล้มทันทีแบบเสียงดัง
  • ความลับจริงทั้งหมดอยู่ใน GitHub environment demo (DEMO_SSH_*, DEMO_ENV_FILE) ไม่มีใน repo · DEMO_ENV_FILE คือเนื้อหา server/.env ทั้งไฟล์ที่ provision.yml เขียนลง VM (0600)
