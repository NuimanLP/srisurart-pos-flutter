Jobเก็บจากสถานะที่ถูกต้อง
nodenode-exporter:9100UP — ป้อนแผง CPU/Memory/Disk
api-metrics/metrics ของ api-1..3:3000 (ภายในเท่านั้น)UP ทั้ง 3 — ป้อนแผง API ทั้งหมด
api-readiness/health/ready ของ api-1..3DOWN — ปกติ! endpoint ตอบ JSON ซึ่ง Prometheus อ่านไม่ได้ (เก็บไว้เป็นตัวยึดตำแหน่ง)
  1. ดูว่า node และ api-metrics ครบ 3 ตัวเป็น UPถ้า api-N ของ api-metrics DOWN = instance นั้นมีปัญหา → ดู docker compose logs api-N

Section 3

Bull-Board Queues & DLQ

เปิด http://127.0.0.1:3100 (Basic Auth) — แสดง 6 คิว: 5 คิวมี worker ของตัวเอง (ไม่แย่งงานกัน) ส่วน dlq ไม่มี worker

คิวใครใส่งานทำอะไร
sale-postหลังขาย/คืนสำเร็จงานเบื้องหลังหลังขาย ไม่บล็อกการตอบลูกค้า
inventoryต่อจาก sale-postตรวจสต็อก (inventory.check)
maintenanceตั้งเวลาทุกชั่วโมง (idem-cleanup-global) + งาน purgeล้าง idempotency key หมดอายุ, ใบเสนอราคาเก่า, ไฟล์ export เก่า
backupPOST /backup/exportส่งออกข้อมูลร้าน (tenant.export)
tenant-importPOST /platform/tenants/:id/importนำเข้าข้อมูลร้านใหม่ (tenant.import)
dlqงานที่ลองครบ 3 ครั้งแล้วยังล้มที่พักงานเสียให้คนดู — "No workers" เป็นเรื่องปกติ ไม่มีใครประมวลผลอัตโนมัติ

จัดการงานที่ล้ม Failed jobs

  1. คลิกคิวที่มี FAILED → คลิกงานอ่านข้อความผิดพลาดเต็ม
  2. แก้สาเหตุก่อนเช่น งาน tenant-import ล้มเพราะร้านมีบิลอยู่แล้ว หรือไฟล์ผิดรูปแบบ
  3. กด Retry ที่งานนั้นอย่ากด Retry ซ้ำ ๆ โดยไม่แก้สาเหตุ
  4. งานใน dlqอ่าน บันทึกสาเหตุ และตัดสินใจร่วมกับทีม — ไม่มี worker มาหยิบไปทำเอง

Section 4

"ปกติ" คืออะไร · ทำอะไรเมื่อผิดปกติ Healthy & response

เช็กลิสต์ระบบปกติ Healthy checklist

  • /health/ready ตอบ 200 และทุกคอนเทนเนอร์ (healthy)
  • Prometheus: node + api-metrics ×3 เป็น UP (api-readiness DOWN ได้)
  • Grafana: API success rate ใกล้ 100% · 5xx เป็น 0 · p95 นิ่ง · Memory ต่ำกว่างบ
  • Bull-Board: ไม่มี FAILED ใหม่ · dlq ว่าง

เมื่อเห็นความผิดปกติ What to do

เห็นทำ
success rate ตก / 5xx ขึ้นดูแผง error by status code ว่ารหัสอะไร → docker compose logs api-1 (…2, 3) → ตรวจ /health/ready ว่า Postgres/Redis ตัวไหนล้ม
p95 พุ่งดู CPU/Memory · มีงานหนักในคิวไหม · ธุรกรรมที่นานเกิน 25 วินาทีจะถูก rollback เอง
4xx 429 เยอะมีเครื่องยิงถี่เกิน rate limit (30 r/s ต่อ IP) — ร้านหลัง NAT เดียวกันแชร์ bucket เดียว
Memory ใกล้ 6 GBดูคอนเทนเนอร์ที่กินเกินงบด้วย docker stats — ห้ามเพิ่มบริการใหม่บน VM นี้
Disk ใกล้เต็มตรวจ /opt/pos/backups และ log · ห้ามลบ volume
Idempotent replays พุ่งเครื่องหน้าร้านลองส่งซ้ำบ่อย = เน็ตร้านไม่เสถียร — ระบบกันขายซ้ำให้แล้ว
FAILED ใน Bull-Boardตามหัวข้อ 3
ข้อจำกัดปัจจุบัน Current limitations
  • ไม่มี alert อัตโนมัติ — ต้องมีคนเปิดดู
  • monitoring ยังไม่เคยรันบน mob04 (ยัง deploy ไม่สำเร็จ) — ทุกอย่างในภาคนี้ดูได้บนเครื่อง dev
  • แผง k6 ว่างจนกว่าจะรันทดสอบโหลด 3 เครื่อง (#380)
  • แผง Disk ว่างบน Docker Desktop
