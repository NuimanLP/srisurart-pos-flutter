# ทฤษฎีและความรู้พื้นฐาน

## บทนำ

บทนี้รวบรวมทฤษฎี แนวคิด และเทคโนโลยีที่โครงงานอาศัยเป็นฐาน โดยจัดลำดับจากโดเมนธุรกิจ (ระบบขายหน้าร้าน) ไปสู่สถาปัตยกรรมฝั่งไคลเอนต์ (offline-first, Flutter, Drift) ต่อด้วยฝั่งเซิร์ฟเวอร์ (ธุรกรรม การแยกข้อมูลผู้เช่า การยืนยันตัวตน) และปิดท้ายด้วยโครงสร้างพื้นฐานและกระบวนการส่งมอบ บทนี้ไม่ทบทวนเทคโนโลยีทั้งหมดอย่างครอบคลุม แต่เลือกเฉพาะแนวคิดที่มีผลต่อการตัดสินใจเชิงออกแบบ ส่วนวิธีที่โครงงานนำแนวคิดเหล่านี้ไปสร้างจริงอธิบายไว้ในบทที่ 3

## แนวคิดของระบบขายหน้าร้านและโดเมนอะไหล่รถยนต์

ระบบขายหน้าร้าน (Point of Sale: POS) คือระบบที่บันทึกการขายสินค้า ณ จุดชำระเงิน พร้อมปรับปรุงสต็อก ยอดลูกค้า และสมุดบัญชีเงินสดของร้านให้สอดคล้องกัน ร้านอะไหล่รถยนต์มีลักษณะเฉพาะ เช่น สินค้าจำนวนมากที่ค้นด้วยเลขอะไหล่ (part number) ลูกค้าประจำที่เป็นช่างซึ่งซื้อเป็นเครดิต และการเสนอราคาก่อนขาย แนวคิดหลักที่ระบบต้องรักษาให้ถูกต้องมีดังนี้

### การขายและค่าคงที่ของสต็อก

การขายหนึ่งครั้งประกอบด้วยหัวบิลและรายการสินค้า และต้องทำหลายอย่างพร้อมกันหรือไม่ทำเลย ได้แก่ ตรวจว่าสต็อกพอ ตัดสต็อก บันทึกบิลและเลขที่ใบเสร็จ สะสมคะแนนสะสม (แต้ม) ของลูกค้า และปรับยอดของช่างเมื่อชำระด้วยเครดิต ค่าคงที่ (invariant) ที่สำคัญที่สุดคือสต็อกห้ามติดลบจากการขาย หากสต็อกไม่พอต้องปฏิเสธบิลทั้งใบ ลักษณะ "ทำทั้งหมดหรือไม่ทำเลย" นี้ตรงกับคุณสมบัติความเป็นอะตอม (atomicity) ของธุรกรรมฐานข้อมูลที่กล่าวในหัวข้อการควบคุมภาวะพร้อมกัน

### การคืนสินค้าและใบลดหนี้

การคืนสินค้าสร้างเอกสารใบลดหนี้ (credit note: CN) ที่อ้างอิงบิลเดิม หลักสำคัญคือห้ามคืนเกินจำนวนที่ขายหักด้วยจำนวนที่เคยคืนไปแล้ว และต้องย้อนส่วนลด แต้ม และยอดสะสมของช่างตามสัดส่วนของสินค้าที่คืน

### การรับสินค้าเข้าและต้นทุนถัวเฉลี่ยถ่วงน้ำหนัก

ใบสั่งซื้อ (Purchase Order: PO) เมื่อรับสินค้าจะเพิ่มสต็อกและปรับต้นทุนต่อหน่วยด้วยวิธีถัวเฉลี่ยถ่วงน้ำหนัก (weighted-average cost) ซึ่งคำนวณจากสูตร

ต้นทุนใหม่ = (จำนวนเดิม × ต้นทุนเดิม + จำนวนที่รับ × ต้นทุนที่รับ) / (จำนวนเดิม + จำนวนที่รับ)

วิธีนี้ทำให้ต้นทุนสะท้อนราคาที่ซื้อในหลายรอบโดยไม่ต้องติดตามล็อตของสินค้าทีละชิ้น อย่างไรก็ตาม หากรายงานกำไรคำนวณจากต้นทุนปัจจุบัน กำไรของบิลเก่าจะเปลี่ยนไปเมื่อต้นทุนเปลี่ยน ระบบจึงควรบันทึกต้นทุน ณ เวลาขาย (cost at sale) ไว้กับบรรทัดบิล

### กะ ลิ้นชักเงินสด และเครดิตช่าง

กะ (shift) คือช่วงเวลาที่พนักงานรับผิดชอบลิ้นชักเงินสดชุดหนึ่ง เริ่มด้วยเงินสดตั้งต้น มีรายการนำเงินเข้า-ออก และปิดกะด้วยการนับเงินเทียบกับยอดที่ระบบคาดหวัง ซึ่งต้องคำนวณด้วยวิธีเดียวทุกจุด มิฉะนั้นหน้าจอสองแห่งจะแสดงยอดคาดหวังไม่ตรงกัน ส่วนเครดิตช่างคือบัญชีลูกหนี้ของช่างแต่ละราย ประกอบด้วยยอดค้าง วงเงิน และประวัติการชำระ การขายเกินวงเงินควรต้องได้รับการยืนยันจากผู้ใช้อย่างชัดแจ้ง

### เลขที่เอกสาร

เลขที่ใบเสร็จ (RC) และใบลดหนี้ (CN) ต้องไม่ซ้ำและเรียงต่อเนื่อง เพื่อให้ตรวจสอบทางบัญชีได้ เมื่อหลายเครื่องออกเลขได้ รูปแบบเลขต้องรวมหมายเลขเครื่องและงวดเวลา เช่น `RC01-2569-08-0042` ตาม ADR-0007 ของโครงงาน การให้เครื่องที่ออฟไลน์ออกเลขเองโดยไม่ชนกับเซิร์ฟเวอร์จึงเป็นโจทย์เชิงระบบกระจาย

### เหตุที่ไม่ใช้ระบบ POS สำเร็จรูป

คณะผู้จัดทำยังไม่ได้สำรวจเปรียบเทียบผลิตภัณฑ์ POS สำเร็จรูปอย่างเป็นระบบ จึงไม่อ้างคุณสมบัติของผลิตภัณฑ์รายใด เหตุผลที่พัฒนาเองมีสองข้อ ข้อแรก กติกาเฉพาะของร้าน เช่น เครดิตช่างพร้อมวงเงิน ราคาช่าง การย้อนส่วนลดและแต้มตามสัดส่วนเมื่อคืนสินค้า และข้อความภาษาไทยที่พนักงานคุ้นเคย อยู่ในไฟล์ `pos/db.js` ซึ่งโครงงานต้องคงพฤติกรรมไว้ทุกข้อ ข้อที่สอง รายวิชากำหนดให้สร้างเซิร์ฟเวอร์หลายผู้เช่าด้วยชุดเทคโนโลยีที่กำหนด ซึ่งการซื้อระบบสำเร็จรูปไม่ตอบโจทย์นี้ การเปรียบเทียบกับผลิตภัณฑ์ในตลาดด้านการขายออฟไลน์ เครดิตช่าง ใบเสร็จภาษาไทย และค่าใช้จ่าย เป็นงานที่ควรเพิ่มในรายงานฉบับสมบูรณ์

## สถาปัตยกรรมออฟไลน์เป็นหลัก (offline-first)

### แนวคิด local-first และ offline-first

ระบบ offline-first ออกแบบให้แอปทำงานได้เต็มที่กับข้อมูลในเครื่องเป็นหลัก แล้วซิงโครไนซ์กับเซิร์ฟเวอร์เมื่อมีเครือข่าย ต่างจากแอปแบบ online-first ที่ทุกการกระทำต้องรอเซิร์ฟเวอร์ Kleppmann และคณะ [1] เสนอแนวคิด local-first software พร้อมอุดมคติเจ็ดข้อ เช่น การตอบสนองเร็วเพราะไม่ต้องรอเครือข่าย การทำงานได้ขณะออฟไลน์ และผู้ใช้เป็นเจ้าของข้อมูลของตน บทความชี้ว่าความท้าทายหลักคือการรวมการแก้ไขจากหลายอุปกรณ์ ซึ่งงานของคณะผู้เขียนแก้ด้วยโครงสร้างข้อมูลแบบ CRDT (Conflict-free Replicated Data Type) สำหรับร้านค้าปลีก เหตุผลเชิงปฏิบัติคืออินเทอร์เน็ตของร้านอาจขัดข้อง แต่เคาน์เตอร์ต้องขายต่อได้

### เหตุที่ไม่ใช้ CRDT หรือการทำสำเนา (replicate) ฐานข้อมูลโดยตรง

CRDT เหมาะกับข้อมูลที่ผสานได้โดยไม่ขัดแย้ง เช่น เอกสารร่วมแก้ไข แต่ข้อมูลการเงินและสต็อกมีค่าคงที่ที่ต้องรักษา เช่น สต็อกห้ามติดลบและเลขที่ใบเสร็จห้ามซ้ำ การผสานอัตโนมัติอาจทำให้ขายเกินสต็อกโดยไม่มีใครถูกปฏิเสธ ADR-0012 ของโครงงานพิจารณาข้อเสนอให้ใช้ CouchDB ที่ replicate ได้ในตัวแทน PostgreSQL แล้วมีมติไม่ใช้ เพราะการสลับฐานข้อมูลเพียงอย่างเดียวทำให้เสียธุรกรรมข้ามตาราง การล็อกแถว คีย์นอก และ RLS โดยไม่ได้สิ่งทดแทน และการป้องกันการขายเกินสต็อกที่แท้จริงมาจากการจำกัดให้มีเครื่องที่เขียนออฟไลน์ได้ (writer) เพียงเครื่องเดียวต่อร้าน ไม่ใช่จากชนิดของฐานข้อมูล ผลลัพธ์คือสถาปัตยกรรมที่เซิร์ฟเวอร์เป็นแหล่งความจริง ส่วนฐานข้อมูลในเครื่องเป็นแคชและเปลือกสำหรับใช้งานออฟไลน์ (offline shell) ที่บันทึกคำสั่งไว้ส่งทีหลัง

### รูปแบบกล่องขาออก (outbox pattern)

เมื่อแอปเขียนข้อมูลขณะออฟไลน์ ต้องบันทึกทั้งผลลัพธ์ในเครื่องและ "ความตั้งใจที่จะส่งเซิร์ฟเวอร์" ในธุรกรรมเดียวกันของฐานข้อมูลในเครื่อง แล้วให้ตัวส่งอ่านคิวนั้นไปส่งภายหลัง รูปแบบนี้เรียกว่า outbox pattern ข้อสำคัญคือการบันทึกผลกับการบันทึกคำสั่งในคิวต้องอะตอมิกด้วยกัน มิฉะนั้นอาจเกิดกรณีที่สต็อกถูกตัดแล้วแต่ไม่มีคำสั่งให้ส่ง หรือมีคำสั่งแต่ผลในเครื่องไม่ตรงกัน แต่ละแถวของคิวมีสถานะ เช่น รอส่ง ติดขัด หรือถูกปฏิเสธ และฝั่งรับต้องรองรับการได้รับคำสั่งเดิมซ้ำ ซึ่งเชื่อมโยงกับแนวคิด idempotency ในหัวข้อถัดไป

### ความสอดคล้องในที่สุด

ระบบกระจายที่ยอมให้สำเนาต่างกันชั่วคราวเรียกว่ามีความสอดคล้องในที่สุด (eventual consistency) คือหากไม่มีการเขียนใหม่ สำเนาทั้งหมดจะลู่เข้าสู่ค่าเดียวกัน [2] ในระบบแบบนี้ ยอดสต็อกและยอดลูกค้าในเครื่องขณะออฟไลน์เป็นค่าประมาณจากข้อมูลล่าสุดที่ดึงมาบวกด้วยผลของคำสั่งที่ค้างในคิว เมื่อซิงก์สำเร็จจึงถูกแทนด้วยค่าจากเซิร์ฟเวอร์ ข้อควรระวังคือการดึงข้อมูลจากเซิร์ฟเวอร์ต้องไม่ทับค่าในเครื่องที่ยังมีคำสั่งค้างอ้างอิงอยู่ มิฉะนั้นยอดจะกระโดดกลับก่อนคำสั่งถูกส่ง

### ความล้มเหลวระหว่างทางและผลลัพธ์ที่ไม่ทราบแน่ชัด

การเรียกผ่านเครือข่ายล้มได้สามรูปแบบที่ต่างกัน คือ ส่งไม่ถึง ส่งถึงแต่คำตอบไม่กลับ และเซิร์ฟเวอร์ตอบข้อผิดพลาด รูปแบบที่สองอันตรายที่สุด เพราะผู้ส่งไม่ทราบว่าการเขียนสำเร็จหรือไม่ หากผู้ส่งตีความว่าล้มเหลวแล้วเขียนซ้ำหรือเขียนลงเครื่องแทน อาจตัดสต็อกสองครั้ง ไคลเอนต์จึงต้องแยกคำตอบที่เป็น "คำตัดสิน" ของเซิร์ฟเวอร์ (เช่น รหัส 4xx ที่บอกว่าคำขอผิด) ออกจากคำตอบที่บอกเพียงว่าเซิร์ฟเวอร์มีปัญหา (5xx) หรือไม่มีคำตอบเลย

## เทคโนโลยีฝั่งไคลเอนต์

### Flutter และ Dart

Flutter เป็นชุดเครื่องมือสร้างส่วนติดต่อผู้ใช้ของ Google ที่คอมไพล์รหัสเดียวไปยังแอป Android, iOS และเว็บ [3] เขียนด้วยภาษา Dart ซึ่งเป็นภาษาแบบมีชนิดข้อมูล รองรับการทำงานแบบอะซิงโครนัสด้วย `Future` และ `Stream` ส่วนติดต่อผู้ใช้ประกอบจากวิดเจ็ต (widget) ที่ไม่เปลี่ยนค่า และเฟรมเวิร์กสร้างต้นไม้วิดเจ็ตใหม่เมื่อสถานะเปลี่ยน โครงงานเลือก Flutter เพราะต้องการฐานรหัสเดียวสำหรับเคาน์เตอร์ที่อาจเป็นแท็บเล็ตหรือเว็บเบราว์เซอร์

### SQLite, Drift และการรันบนเว็บ

SQLite เป็นฐานข้อมูลเชิงสัมพันธ์แบบฝังตัวในไฟล์เดียว รองรับธุรกรรมแบบ ACID (ความเป็นอะตอม ความสอดคล้อง การแยกจากกัน และความคงทน ดูหัวข้อคุณสมบัติ ACID ในบทนี้) [4] Drift เป็นไลบรารีแมปวัตถุกับฐานข้อมูล (Object-Relational Mapping: ORM) แบบมีชนิดข้อมูลสำหรับ Dart ที่สร้างรหัสจากการประกาศตาราง และเรียกใช้ SQLite ได้ทั้งบนอุปกรณ์เคลื่อนที่และเว็บ [5] บนเว็บ Drift ใช้ SQLite ที่คอมไพล์เป็น WebAssembly ทำงานร่วมกับ web worker และเลือกที่เก็บตามความสามารถของเบราว์เซอร์ เช่น Origin Private File System (OPFS) หรือ IndexedDB

### การจัดการสถานะด้วย BLoC และการนำทางด้วย go_router

การจัดการสถานะ (state management) คือการกำหนดว่าข้อมูลที่หน้าจอใช้เก็บที่ใดและเปลี่ยนแปลงอย่างไร รูปแบบ BLoC (Business Logic Component) แยกตรรกะธุรกิจออกจากวิดเจ็ต โดยรับเหตุการณ์และปล่อยสถานะเป็นสตรีม Cubit เป็นรูปแบบย่อยที่เรียกเมธอดแล้วปล่อยสถานะโดยตรง ไลบรารี `flutter_bloc` มี `BlocProvider` และ `RepositoryProvider` สำหรับฉีดการพึ่งพา (dependency injection) ลงต้นไม้วิดเจ็ต [6] การฉีด repository ผ่าน provider ทำให้สลับ implementation ได้โดยหน้าจอไม่ต้องแก้ ส่วน `go_router` เป็นไลบรารีการนำทางแบบประกาศ (declarative routing) ที่แมป URL ไปยังหน้าจอ และมี `ShellRoute` ที่ห่อหน้าจอย่อยด้วยโครงร่างร่วม [7]

## การสื่อสารไคลเอนต์-เซิร์ฟเวอร์

REST (Representational State Transfer) เป็นรูปแบบสถาปัตยกรรมที่ใช้ทรัพยากรที่ระบุด้วย URL และเมธอด HTTP เช่น GET, POST, PATCH ตามความหมายของแต่ละเมธอด โดยเซิร์ฟเวอร์ไม่เก็บสถานะของเซสชันระหว่างคำขอ ทำให้เพิ่มจำนวนอินสแตนซ์ของเซิร์ฟเวอร์ได้ตรงไปตรงมา การห่อผลลัพธ์ด้วยโครงสร้างคงที่ (envelope) ที่มีรหัสข้อผิดพลาดแบบข้อความ ช่วยให้ไคลเอนต์ตัดสินได้ว่าข้อผิดพลาดใดเป็นคำตัดสินและแปลเป็นข้อความสำหรับผู้ใช้ได้ ส่วนจำนวนเงินควรส่งเป็นสตริงทศนิยมเพื่อเลี่ยงความคลาดเคลื่อนของเลขทศนิยมแบบลอยตัว

แคชแบบเขียนผ่าน (write-through cache) คือรูปแบบที่การเขียนทุกครั้งไปยังแหล่งความจริงก่อน แล้วจึงนำผลที่แหล่งความจริงตอบกลับมาปรับแคช แคชจึงไม่มีข้อมูลที่แหล่งความจริงไม่ได้ยอมรับ รูปแบบนี้คือแนวทางที่ ADR-0010 ของโครงงานใช้กับฐานข้อมูล Drift ในเครื่อง

## ธุรกรรมฐานข้อมูลและการควบคุมภาวะพร้อมกัน

### คุณสมบัติ ACID และระดับการแยกจากกัน

ธุรกรรม (transaction) คือหน่วยงานที่ฐานข้อมูลรับประกันคุณสมบัติ ACID ได้แก่ ความเป็นอะตอม (Atomicity) คือทำครบหรือไม่ทำเลย ความสอดคล้อง (Consistency) คือข้อจำกัดของข้อมูลยังคงอยู่หลังธุรกรรม การแยกจากกัน (Isolation) คือธุรกรรมที่ทำพร้อมกันไม่เห็นผลครึ่งทางของกันและกัน และความคงทน (Durability) คือเมื่อยืนยัน (commit) แล้วข้อมูลไม่สูญหาย [8] มาตรฐาน SQL นิยามระดับการแยกจากกันตามความผิดปกติที่ยอมให้เกิด เช่น dirty read, non-repeatable read และ phantom read PostgreSQL ใช้ระดับ Read Committed เป็นค่าเริ่มต้น ซึ่งแต่ละคำสั่งเห็นข้อมูลที่ยืนยันแล้วในขณะเริ่มคำสั่งนั้น [8] ในระดับนี้ การอ่านค่าแล้วคำนวณแล้วเขียนกลับ (read-modify-write) เช่นอ่านสต็อกแล้วลบแล้วเขียน อาจเสียการปรับปรุงของธุรกรรมอื่นที่แทรกกลาง (lost update) เว้นแต่จะล็อกแถวไว้ก่อน

### การล็อกระดับแถว เดดล็อก และลำดับการล็อก

PostgreSQL ใช้ MVCC (Multi-Version Concurrency Control) ทำให้ผู้อ่านไม่บล็อกผู้เขียน แต่ผู้เขียนที่แก้แถวเดียวกันต้องรอกัน เมื่อต้องการกันธุรกรรมอื่นแก้แถวระหว่างที่ตัวเองตรวจเงื่อนไขอยู่ ใช้ `SELECT … FOR UPDATE` เพื่อล็อกแถวแบบเขียน หรือ `FOR SHARE` เพื่อล็อกแบบแบ่งปัน [8] เดดล็อก (deadlock) เกิดเมื่อธุรกรรมสองรายการถือล็อกที่อีกฝ่ายต้องการและรอกันเป็นวงกลม PostgreSQL ตรวจพบแล้วยกเลิกธุรกรรมหนึ่งรายการ [8] วิธีป้องกันที่เชื่อถือได้คือกำหนดลำดับการล็อกให้ตรงกันทุกเส้นทางโค้ด ถ้าทุกธุรกรรมล็อกทรัพยากรตามลำดับเดียวกัน วงกลมจะไม่เกิด

### ธุรกรรมกับกลุ่มการเชื่อมต่อ

การเชื่อมต่อฐานข้อมูลเป็นทรัพยากรจำกัดที่จัดสรรผ่านกลุ่มการเชื่อมต่อ (connection pool) หากคำขอหนึ่งถือการเชื่อมต่อแรกไว้แล้วขอการเชื่อมต่อที่สองจาก pool เดียวกัน เมื่อจำนวนคำขอพร้อมกันเท่ากับขนาด pool ทุกคำขอจะรอกันเองโดยไม่มีใครได้ไปต่อ (pool starvation) นอกจากนี้ธุรกรรมที่ยาวเกินจำเป็นจะถือทั้งการเชื่อมต่อและล็อกไว้นาน งานที่ช้าแต่ไม่ต้องอยู่ในธุรกรรม เช่น การแฮชรหัสผ่าน จึงควรทำนอกธุรกรรม

## การแยกข้อมูลผู้เช่าหลายราย (multi-tenancy)

ระบบหลายผู้เช่า (multi-tenant) ให้องค์กรหลายราย (ผู้เช่า) ใช้ระบบเดียวกันโดยข้อมูลต้องไม่ปะปนกัน มีแนวทางหลักสามแบบที่ต่างกันที่ระดับการแยกและต้นทุนการดูแล ดังตารางที่ {tab:tenancy}

TABLE: เปรียบเทียบแบบจำลองการแยกผู้เช่าในฐานข้อมูล {#tab:tenancy}
| แบบจำลอง | การแยกข้อมูล | ต้นทุนการดูแล | ข้อสังเกตต่อโครงงาน |
|---|---|---|---|
| ฐานข้อมูลแยกต่อผู้เช่า | แยกสูงสุดระดับฐานข้อมูล | สูง: ต้องจัดการหลายฐานข้อมูล ย้าย schema หลายชุด | ไม่เหมาะกับทรัพยากรของเครื่องสาธิตเครื่องเดียว |
| Schema แยกต่อผู้เช่า | แยกระดับ schema ในฐานข้อมูลเดียว | ปานกลาง: migration ต้องทำซ้ำทุก schema | จำนวนออบเจ็กต์โตตามจำนวนผู้เช่า |
| ตารางร่วมกับคอลัมน์ `tenant_id` | แยกระดับแถว ต้องบังคับด้วยกติกา | ต่ำ: schema เดียว migration ครั้งเดียว | โครงงานเลือกแบบนี้ร่วมกับ Row-Level Security |

ความเสี่ยงของแบบที่สามคือ หากโค้ดลืมใส่เงื่อนไข `tenant_id` ในคำสั่งใดคำสั่งหนึ่ง ข้อมูลของผู้เช่าอื่นจะรั่วไหล จึงต้องมีกลไกที่ไม่พึ่งความระมัดระวังของนักพัฒนา PostgreSQL มีคุณสมบัติ Row-Level Security (RLS) ที่ให้กำหนดนโยบาย (policy) ต่อตาราง ซึ่งฐานข้อมูลจะเติมเป็นเงื่อนไขกรองแถวให้ทุกคำสั่งโดยอัตโนมัติ [9] นโยบายมีสองส่วน คือ `USING` ที่กรองแถวที่มองเห็นหรือแก้ได้ และ `WITH CHECK` ที่ตรวจแถวที่กำลังจะเขียน โดยทั่วไปนโยบายเทียบ `tenant_id` กับตัวแปรเซสชันที่แอปตั้งไว้ในธุรกรรม ดังรูปที่ {fig:rls} ข้อควรระวังคือเจ้าของตารางและผู้ใช้ระดับ superuser ได้รับการยกเว้นจาก RLS โดยปริยาย แอปจึงต้องเชื่อมต่อด้วยบทบาทที่ไม่ใช่เจ้าของตาราง หรือบังคับด้วย `FORCE ROW LEVEL SECURITY`

FIGURE: แนวคิด Row-Level Security: คำขอของผู้เช่าหนึ่งเห็นเฉพาะแถวของผู้เช่านั้น {#fig:rls} | diagram:rls-concept

ผู้ดูแลแพลตฟอร์มที่สร้างและดูแลผู้เช่าหลายรายต้องข้ามขอบเขตผู้เช่าได้ แนวทางที่ปลอดภัยคือแยก "ระนาบผู้ดูแล" (admin plane) ออกจากระนาบผู้เช่าทั้งในระดับบัญชี โทเค็น และเส้นทางเครือข่าย เพื่อไม่ให้ความผิดพลาดของฝั่งหนึ่งเปิดทางเข้าอีกฝั่ง

## การทำซ้ำคำขออย่างปลอดภัยและรหัสกำกับการเขียน (idempotency)

การดำเนินการเป็น idempotent เมื่อทำซ้ำกี่ครั้งก็ให้ผลต่อสถานะเท่ากับทำครั้งเดียว ใน HTTP เมธอด GET, HEAD, PUT, DELETE ถูกนิยามให้ idempotent แต่ POST ซึ่งใช้สร้างบิลไม่เป็น [10] เมื่อไคลเอนต์ส่ง POST แล้วเครือข่ายหมดเวลา ไคลเอนต์ไม่ทราบว่าเซิร์ฟเวอร์ทำสำเร็จหรือไม่ การส่งซ้ำอาจทำให้ขายซ้ำสองบิล แนวทางที่กำลังถูกกำหนดเป็นมาตรฐานคือให้ไคลเอนต์สร้างรหัสสุ่มหนึ่งค่าต่อหนึ่งเจตนา แนบในส่วนหัว `Idempotency-Key` [11] เซิร์ฟเวอร์บันทึกคีย์พร้อมค่าสรุปของคำขอ (request fingerprint) และผลลัพธ์ หากได้รับรหัสเดิมกับคำขอเดิมจะตอบผลเดิมโดยไม่ทำซ้ำ หากรหัสเดิมมากับคำขอที่ต่างไปจะปฏิเสธ กลไกนี้ได้ผลก็ต่อเมื่อไคลเอนต์ใช้รหัสเดิมทุกครั้งที่ลองส่งเจตนาเดิมซ้ำ และการจดรหัสอยู่ในธุรกรรมเดียวกับการเขียน

## การยืนยันตัวตนและการรักษาความปลอดภัย

### JSON Web Token และอายุของโทเค็น

JWT ตามมาตรฐาน RFC 7519 [12] เป็นรูปแบบโทเค็นแบบกะทัดรัดที่ประกอบด้วยส่วนหัว เพย์โหลดที่มี claim เช่น `iss`, `sub`, `exp`, `aud` และลายเซ็น ผู้รับตรวจลายเซ็นด้วยกุญแจโดยไม่ต้องถามฐานข้อมูล การเซ็นด้วยกุญแจอสมมาตร เช่น RS256 ทำให้ผู้ตรวจถือเพียงกุญแจสาธารณะ ระบบทั่วไปแยกโทเค็นเข้าถึง (access token) อายุสั้นเพื่อจำกัดความเสียหายเมื่อรั่ว ออกจากโทเค็นต่ออายุ (refresh token) ที่อายุยาวกว่าและใช้ขอ access token ใหม่ การเพิกถอนทำได้ที่จังหวะต่ออายุ ซึ่งตรวจฐานข้อมูลอีกครั้ง บนเว็บ โทเค็นที่เก็บใน `localStorage` อ่านได้จากสคริปต์ใด ๆ ในหน้า จึงเสี่ยงต่อการโจมตีแบบ Cross-Site Scripting (XSS)

### การแฮชรหัสผ่านด้วย Argon2

รหัสผ่านต้องไม่เก็บเป็นข้อความตรง แต่เก็บค่าแฮชจากฟังก์ชันที่ออกแบบให้ช้าและใช้หน่วยความจำมาก เพื่อต้านการเดาแบบเหมารวม Argon2 ผู้ชนะการแข่งขัน Password Hashing Competition ถูกกำหนดใน RFC 9106 [13] มีพารามิเตอร์จำนวนหน่วยความจำ จำนวนรอบ และระดับขนาน ข้อควรระวังสำหรับข้อความภาษาไทยคือสตริงเดียวกันอาจเข้ารหัสยูนิโคดได้หลายรูป การทำให้เป็นรูปมาตรฐาน (normalization) ก่อนแฮชจึงมีผลต่อการตรวจรหัสผ่าน

### การผูกอุปกรณ์และการจำกัดอัตราคำขอ

ระบบที่ต้องจำกัดสิทธิ์ตามเครื่อง เช่น ให้มีเครื่องขายเพียงเครื่องเดียวต่อร้าน มักใช้รหัสลงทะเบียนแบบใช้ครั้งเดียวที่ผู้มีสิทธิ์ออกให้ แล้วนำไปแลกเป็นโทเค็นของอุปกรณ์ ทำให้ตัวตนของเครื่องมาจากเซิร์ฟเวอร์ ไม่ใช่จากค่าที่ไคลเอนต์ส่งเอง ส่วนการจำกัดอัตราคำขอ (rate limiting) ช่วยลดการเดารหัสผ่านและการใช้ทรัพยากรเกินควร มักทำหลายชั้น เช่น ต่อ IP ที่พร็อกซีหน้าระบบ และต่อผู้เช่าในแอปพลิเคชัน

## เทคโนโลยีฝั่งเซิร์ฟเวอร์

NestJS เป็นเฟรมเวิร์กฝั่งเซิร์ฟเวอร์บน Node.js ที่เขียนด้วย TypeScript จัดโครงสร้างเป็นโมดูล คอนโทรลเลอร์ และผู้ให้บริการ (provider) พร้อมระบบฉีดการพึ่งพา (dependency injection) และกลไก guard, interceptor และ middleware [14] โครงสร้างที่บังคับให้แยกชั้นชัดเจนเหมาะกับทีมสามคนที่แบ่งงานตามโดเมน PostgreSQL เป็นระบบจัดการฐานข้อมูลเชิงสัมพันธ์โอเพนซอร์สที่รองรับ ACID, MVCC, RLS, ข้อจำกัดเชิงซ้อน และดัชนีบางส่วน [8]

Redis เป็นที่เก็บข้อมูลแบบคีย์–ค่า (key-value store) ในหน่วยความจำ ใช้เป็นแคช ตัวนับ และคิว [15] BullMQ เป็นไลบรารีคิวงานบน Redis ที่มีการลองซ้ำและตารางเวลา [16] เหมาะกับงานเบื้องหลังที่ไม่ควรทำในคำขอ HTTP เช่น การส่งออกข้อมูล ข้อควรสังเกตคือแคชกับคิวต้องการนโยบายหน่วยความจำที่ตรงข้ามกัน แคชทิ้งข้อมูลได้เมื่อเต็ม แต่คิวห้ามทิ้งงานที่ยังไม่ทำ

พร็อกซีย้อนกลับ (reverse proxy) รับคำขอจากภายนอกแล้วส่งต่อไปยังเซิร์ฟเวอร์ภายใน ทำหน้าที่ยุติ Transport Layer Security (TLS) จำกัดอัตรา และซ่อนโครงสร้างภายใน Nginx ทำหน้าที่นี้ได้ด้วยคำสั่ง `proxy_pass` และ `limit_req_zone` [17] เมื่อมีพร็อกซี แอปจะอ่าน IP ผู้เรียกจากส่วนหัว `X-Forwarded-For` จำนวนชั้นของพร็อกซีจึงต้องแน่นอน หากมีพร็อกซีหรือ Content Delivery Network (CDN) ซ้อนเพิ่ม ผู้ใช้ทุกคนอาจถูกมองเป็น IP เดียว

## คอนเทนเนอร์และการจัดวาง

คอนเทนเนอร์เป็นการแยกโปรเซสด้วยฟีเจอร์ของเคอร์เนล (namespace และ cgroup) ที่บรรจุแอปพร้อมไลบรารีที่ต้องใช้เป็นอิมเมจ ทำให้รันได้เหมือนกันทุกเครื่อง [18] Docker Compose ประกาศชุดบริการหลายตัว เครือข่าย และเพดานทรัพยากรในไฟล์เดียว [19] การตรึงอิมเมจด้วย digest แทนป้ายชื่อทำให้สร้างสภาพแวดล้อมเดิมซ้ำได้ เพราะป้ายชื่ออย่าง `latest` อาจชี้ไปยังอิมเมจคนละตัวในเวลาต่างกัน

## การบูรณาการและการส่งมอบอย่างต่อเนื่อง (CI/CD)

การบูรณาการต่อเนื่อง (Continuous Integration: CI) คือการรวมโค้ดเข้าสาขาหลักบ่อยครั้งพร้อมสร้างและทดสอบอัตโนมัติ เพื่อพบข้อผิดพลาดแต่เนิ่น การส่งมอบต่อเนื่อง (Continuous Delivery: CD) ต่อยอดโดยทำให้ผลงานที่ผ่านการทดสอบพร้อมนำขึ้นใช้งาน (deploy) ได้ตลอดเวลา ไปป์ไลน์ที่ดีให้ผลลัพธ์ที่ทำซ้ำได้และมีประตูตรวจคุณภาพก่อนถึงสภาพแวดล้อมจริง

GitHub Actions เป็นบริการรันเวิร์กโฟลว์ที่นิยามเป็น YAML ประกอบด้วยงาน (job) ที่ทำงานบนตัวรัน (runner) ทั้งแบบที่ GitHub จัดให้และแบบติดตั้งเอง (self-hosted) [20] สาขาหลักสามารถบังคับให้ต้องผ่านการตรวจสอบสถานะ (status check) ที่กำหนดก่อนรวมโค้ด ซึ่งมีเงื่อนไขว่าการตรวจสอบนั้นต้องรายงานผลทุกครั้ง GitHub Container Registry (GHCR) เป็นที่เก็บอิมเมจคอนเทนเนอร์ [21] Trivy เป็นเครื่องมือสแกนช่องโหว่ของอิมเมจและการพึ่งพา [22] และ gitleaks ตรวจหาความลับที่เผลอคอมมิต เช่น คีย์ API [23] เมื่อพบความลับจริงในประวัติ วิธีที่ถูกต้องคือหมุนเปลี่ยนความลับนั้น ไม่ใช่ใส่ไว้ในรายการยกเว้น

Ansible เป็นเครื่องมือจัดการคอนฟิกที่สั่งงานเครื่องปลายทางผ่าน Secure Shell (SSH) ด้วย playbook และโมดูลส่วนใหญ่ออกแบบให้ idempotent [24] เมื่อเครื่องปลายทางอยู่ในเครือข่ายปิดที่ตัวรันของ GitHub เข้าไม่ถึง ต้องใช้ตัวรันแบบติดตั้งเองภายในเครือข่ายนั้น และควรมีประตูอนุมัติโดยผู้ตรวจที่กำหนดก่อนงานติดตั้งเริ่ม

## การสังเกตการณ์ระบบ (observability)

การสังเกตการณ์คือความสามารถในการอนุมานสถานะภายในของระบบจากข้อมูลที่ระบบปล่อยออกมา โดยทั่วไปประกอบด้วยตัวชี้วัด (metrics) บันทึก (logs) และร่องรอย (traces) Prometheus เก็บอนุกรมเวลาด้วยการดึง (scrape) จาก endpoint ที่แสดงตัวชี้วัดในรูปแบบข้อความ และมีภาษาสืบค้น PromQL [25] Grafana แสดงผลเป็นแดชบอร์ด [26] ป้ายกำกับ (label) ของตัวชี้วัดควรมีค่าที่เป็นไปได้จำนวนจำกัด เช่น ใช้รูปแบบเส้นทางแทนเส้นทางจริง มิฉะนั้นจำนวนอนุกรม (cardinality) จะพุ่งสูง

ตัวชี้วัดระดับบริการ (Service Level Indicator: SLI) คือการวัดเชิงปริมาณของพฤติกรรมบริการ เช่น สัดส่วนคำขอที่สำเร็จ และเปอร์เซ็นไทล์ที่ 95 (p95) ของเวลาตอบ การเลือกว่าคำขอใดถูกนับมีความสำคัญเท่ากับการนับ เพราะคำขอที่ระบบสร้างเอง เช่น การตรวจสุขภาพ อาจทำให้อัตราสำเร็จดูดีเกินจริง ส่วนการทดสอบโหลดใช้เครื่องมือเช่น k6 ที่เขียนสถานการณ์เป็นสคริปต์ JavaScript เพื่อวัดพฤติกรรมของระบบภายใต้ปริมาณคำขอที่กำหนด

## การบันทึกการตัดสินใจเชิงสถาปัตยกรรม (ADR)

Nygard [27] เสนอให้บันทึกการตัดสินใจทางสถาปัตยกรรมเป็นเอกสารสั้นหนึ่งฉบับต่อหนึ่งการตัดสินใจ ประกอบด้วยบริบท การตัดสินใจ สถานะ และผลที่ตามมา เหตุผลคือโค้ดบอกว่าระบบทำอะไร แต่ไม่บอกว่าทำไมจึงเลือกทางนั้นและทางใดถูกปฏิเสธ เมื่อสมาชิกเปลี่ยนหรือเวลาผ่านไป ความรู้นี้จะหายถ้าไม่จด ADR ที่ปฏิเสธข้อเสนอพร้อมเหตุผลมีประโยชน์เท่ากับ ADR ที่ยอมรับ เพราะป้องกันการถกเถียงเดิมซ้ำ
