# ความก้าวหน้าการดำเนินงาน

บทนี้รายงานผลการดำเนินงาน ณ วันที่ 1 ตุลาคม พ.ศ. 2569 โดยส่วนแรกครอบคลุมงานฝั่งไคลเอนต์ Flutter ได้แก่ การย้ายระบบเดิม หน้าจอ ชั้นเขียนข้อมูลผ่าน API ระบบทำงานออฟไลน์ฝั่งอุปกรณ์ และผลการทดสอบ ส่วนที่สองครอบคลุมเซิร์ฟเวอร์ CI/CD การ deploy และเกณฑ์ตรวจรับของเฟส 1 การออกแบบอยู่ในบทที่ 3 บทนี้จึงเน้นสิ่งที่ทำได้จริงและหลักฐาน

ตัวเลข วันที่ และสถานะทุกรายการตรวจสอบย้อนกลับได้จากประวัติ git ตั๋วงาน หรือผลการรันชุดทดสอบ งานที่ยังไม่เสร็จระบุว่ายังไม่เสร็จ คำว่า "ผ่านการรวมโค้ด" (merged) หมายถึงคำขอรวมโค้ด (pull request: PR) ถูกรวมเข้าสาขา `main` แล้ว และ "ปิดตั๋ว" หมายถึงตั๋วงานมีสถานะ closed บน GitHub

การย้ายไลบรารีจัดการสถานะจาก Riverpod เป็น flutter_bloc ดำเนินการครบ 12 ขั้นตอนตามแผน เนื่องจากชั้น repository ไม่ได้ผูกกับ Riverpod การย้ายจึงกระทบเฉพาะชั้นการแสดงผล ขณะนั้นชุดทดสอบ 122 กรณีผ่านทั้งหมด

### การนำเข้าข้อมูลสำรองและฐานข้อมูลบนเว็บ

`importLegacyBackup()` นำเข้าไฟล์ JSON ที่ส่งออกจากระบบ JavaScript เดิมในธุรกรรมเดียว พร้อมแปลงข้อมูลโซนเป็นหมวดหมู่ ร้านจึงย้ายข้อมูลเดิมได้โดยไม่ต้องป้อนข้อมูลใหม่ บนบิลด์ที่ใช้เซิร์ฟเวอร์ยังมี `purgeDemoSeed()` ที่ลบข้อมูลตัวอย่าง (seed data) ซึ่งระบบสร้างไว้ตอนเริ่มต้นออกหนึ่งครั้ง โดยข้ามเมื่อยังมีงานค้างในคิวส่ง และลบเฉพาะแถวตัวอย่างที่ไม่เคยถูกแก้ไขและไม่มีระเบียนใดอ้างอิง

ฐานข้อมูลบน Flutter Web ทำงานผ่าน SQLite ที่คอมไพล์เป็น WebAssembly [1] ปัญหาที่พบคือเบราว์เซอร์ที่ไม่รองรับความสามารถ `dedicatedWorkersInSharedWorkers` เกิดข้อผิดพลาด `LinkError` เมื่อ Drift ถอยไปใช้โหมดสำรอง (#266) ซึ่งแก้ด้วย PR #310 (รวมโค้ด 17 กันยายน พ.ศ. 2569 ปิดตั๋ว 19 กันยายน พ.ศ. 2569)

### ผลเพิ่มเติมที่เกิดจากการแก้ข้อบกพร่อง

งานหลังจากตารางข้างต้นเกิดจากข้อบกพร่องที่พบระหว่างทาง ดังนี้

- **การทิ้งรายการในคิว (#473, #488)** การทิ้งรายการขายหรือคืนที่ค้างเดิมไม่ย้อนสต็อกและยอดในเครื่อง PR #483 จึงย้อนสต็อก ลูกหนี้ และสถานะยกเลิกบิลในธุรกรรมเดียวกับการทิ้ง แต่การคำนวณย้อนไม่แม่นยำเมื่อการเขียนครั้งแรกถูกปัดค่าที่ศูนย์ (เช่น เครดิตช่าง 50 บาทกับใบลดหนี้หักเครดิต 180 บาท) PR #495 จึงเพิ่มตาราง `op_effects` ที่เก็บผลต่างที่ใช้จริง และปฏิเสธการทิ้งเมื่อสต็อกที่เกี่ยวข้องถูกขายต่อไปแล้วตามการตัดสินของเจ้าของโครงงาน (รายละเอียดในบทที่ 5)
- **เลขเอกสารซ้ำ (#489)** เลขที่เซิร์ฟเวอร์ออกไม่ถูกบันทึกลงตัวนับในเครื่อง แก้แล้วตามตาราง (บทที่ 5)
- **การดึงข้อมูลกับยอดเงินในคิว (PR #544, 1 ตุลาคม พ.ศ. 2569)** การดึงข้อมูลต้องไม่ทับยอดลูกค้าและช่างที่คำสั่งทางการเงินในคิวยังอ้างอิงอยู่ จึงคุ้มครองเฉพาะคำสั่งที่ย้ายเงินสี่ชนิด (`sale.create`, `sale.void_offline`, `return.create`, `credit_payment.create`)
- **แคชหลายร้าน (PR #539 และ #541, 1 ตุลาคม พ.ศ. 2569)** เครื่องหนึ่งเครื่องอาจถูกใช้กับหลายร้าน จึงผูกแคชในเครื่องกับรหัสร้านและปฏิเสธการสลับร้านเมื่อยังมีงานที่ไม่ได้ส่ง ส่วน PR #541 แก้กรณีบิลด์เก่าที่ยังไม่มีรหัสร้าน ข้อจำกัดที่ยอมรับแล้วคือคำตอบของการเขียนออนไลน์ที่กำลังส่งอยู่ไม่ถูกกั้นด้วยรุ่นของแคช
