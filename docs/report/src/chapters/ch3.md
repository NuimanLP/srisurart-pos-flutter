# รายละเอียดการดำเนินงาน

## ภาพรวมของโครงงาน

บทนี้อธิบายการออกแบบและการสร้างระบบ Srisurart Autopart POS ตามสถานะของโค้ดบนสาขา `main` ณ วันที่ 1 ตุลาคม พ.ศ. 2569 ได้แก่ สถาปัตยกรรม ส่วนประกอบ ฝั่งไคลเอนต์ ฝั่งเซิร์ฟเวอร์ การซิงก์ข้อมูลในเฟส 2 ความปลอดภัย การนำระบบขึ้นใช้งาน (deploy) เทคโนโลยีที่ใช้ และวิธีการทำงานของทีม การตัดสินใจที่สำคัญอ้างอิงบันทึกการตัดสินใจเชิงสถาปัตยกรรม (Architecture Decision Record: ADR) ในโฟลเดอร์ `docs/Backend_design/adr/` เพื่อบอกเหตุผลของการเลือก ส่วนผลที่ได้และหลักฐานรายงานไว้ในบทที่ 4

### หลักการของสถาปัตยกรรม

ตามที่กล่าวในบทที่ 1 โครงงานเลือก Architecture C (ไฮบริด) ร่วมกับโมเดลผู้เช่าแบบ T1 (ฐานข้อมูลและสคีมาเดียว คอลัมน์ `tenant_id` และ Row-Level Security) โดยเฟส 1 คือ Architecture A หรือ online-first modular monolith ที่ให้ PostgreSQL เป็นแหล่งความจริงเพียงแหล่งเดียว และเฟส 2 เพิ่มความสามารถทำงานออฟไลน์กลับเข้ามา เอกสาร `03_ARCHITECTURE.md` ระบุว่า หากเวลาไม่พอ ให้ทำ A กับ T1 ให้สมบูรณ์ดีกว่าทำส่วนเสริมไม่ครบ หลักการนี้กำหนดลำดับงานของทีม คือเฟส 1 ต้องทำงานได้จริงและทดสอบได้ก่อน ทั้งไคลเอนต์ เซิร์ฟเวอร์ และไปป์ไลน์อยู่ในที่เก็บโค้ดเดียว (monorepo) ตาม ADR-0011 เพื่อให้การแก้ API หนึ่งครั้งแก้ได้ทั้งสองฝั่งในคอมมิตเดียว

### สถาปัตยกรรมโดยรวม

ไคลเอนต์ Flutter (ปัจจุบันสร้างและทดสอบเฉพาะบนเว็บ; เวิร์กโฟลว์สร้างไฟล์ติดตั้ง Android เพิ่มเมื่อ 3 ตุลาคม พ.ศ. 2569 แต่ยังไม่เคยรัน) สื่อสารกับเซิร์ฟเวอร์ผ่าน HTTPS ทุกคำขอเข้าสู่ Nginx ซึ่งเป็น reverse proxy ตัวเดียวหน้าระบบ แล้วกระจายไปยังอินสแตนซ์ NestJS [1] สามตัว (`api-1` ถึง `api-3`) ที่ใช้อิมเมจเดียวกัน ข้อมูลธุรกิจเก็บใน PostgreSQL ส่วน Redis แบ่งเป็นสองอินสแตนซ์ตามหน้าที่ งานเบื้องหลังประมวลผลโดยโปรเซส `worker` แยกต่างหาก ค่าตั้งที่ปรับขณะรันได้เก็บใน etcd และการเฝ้าสังเกตระบบใช้ Prometheus กับ Grafana ดังรูปที่ {fig:architecture} ตารางที่ {tab:phases} สรุปความต่างระหว่างเฟส 1 และเฟส 2 ในมุมที่กระทบการออกแบบ ตามเอกสาร `03_ARCHITECTURE.md` และ `08_PHASE2_SPEC.md`

## รายละเอียดฝั่งไคลเอนต์

### โครงสร้างแบบสามชั้น

ไคลเอนต์ Flutter [4] อยู่ในโฟลเดอร์ `frontend/lib/` และแบ่งตามหลัก data → domain → presentation ดังรูปที่ {fig:client-layers} ชั้น `core/` เก็บสิ่งที่ใช้ร่วมกัน ได้แก่ตัวกำหนดเส้นทาง `go_router` ธีมพร้อมฟอนต์ Sarabun และ Barlow และฟังก์ชันช่วยเรื่องเงินและเลขเอกสาร (`baht`, `round2`, `newId`, `docNo`, `csvSafe`) กติกาที่ใช้ทั้งโปรเจกต์คือหน้าจอต้องเรียกใช้ repository ผ่าน provider เท่านั้น ห้ามเข้าถึงฐานข้อมูลโดยตรง การจัดการสถานะใช้ `flutter_bloc` โดยมี Cubit สำหรับโหมดธีม ขนาดฟอนต์ ใบเสนอราคาที่รอ ตะกร้าสินค้า และสถานะการเข้าสู่ระบบ ส่วน repository และบริการทั้งหมดลงทะเบียนผ่านต้นไม้ `RepositoryProvider` 21 รายการ (repository 17 ตัว และบริการ `ApiClient`, `BootstrapService`, `DocCounterSeeder`, `SyncFacade`)

FIGURE: โครงสร้างชั้นของไคลเอนต์ Flutter และเส้นทางไปยังเซิร์ฟเวอร์ {#fig:client-layers} | diagram:client-layers

### ฐานข้อมูลภายในเครื่อง (Drift)

ฐานข้อมูลภายในเครื่องใช้ Drift [5] กำหนดไว้ใน `data/db/tables.dart` มี 26 ตาราง และ `schemaVersion` เท่ากับ 13 แบ่งเป็นสามกลุ่ม กลุ่มแรก 20 ตารางพอร์ตมาจากที่เก็บข้อมูล `sa_*` ของแอปเดิม เช่น `Products`, `Customers`, `Mechanics`, `Sales`, `SaleItems`, `Returns`, `Shifts` และ `DocCounters` กลุ่มที่สองเป็นคิวและตารางสนับสนุนการซิงก์ ได้แก่ `PendingCreditPayments` (#24) และตารางของเฟส 2 `DocCounterSeeds`, `OutboxOps`, `SyncCursors` และ `OpEffects` กลุ่มที่สามคือ `AppMeta` สำหรับค่าเมตาดาต้า เช่น รหัสผู้เช่าที่แคชนี้เป็นเจ้าของ การยกระดับสคีมาที่เกี่ยวข้องกับรายงานนี้ ได้แก่ เวอร์ชัน 7 ที่ลบคอลัมน์ `offlineOk` เวอร์ชัน 12 ที่เพิ่มดัชนี และเวอร์ชัน 13 ที่เพิ่มตาราง `op_effects` เพื่อเก็บผลต่างที่คำสั่งออฟไลน์ใช้จริง

ไฟล์ `database.g.dart` ที่ Drift สร้างอัตโนมัติถูกคอมมิตไว้ในที่เก็บโค้ด เพราะเครื่องมือ `build_runner` ทำงานบนพาธที่มีอักขระนอกชุด ASCII ไม่ได้ (รายละเอียดในบทที่ 5) และ CI มีงาน `codegen-check` ตรวจว่าไฟล์ที่สร้างตรงกับของที่คอมมิตไว้ สำหรับเว็บ ไฟล์ `web/sqlite3.wasm` และ `web/drift_worker.js` ต้องมีเวอร์ชันตรงกับแพ็กเกจ `sqlite3` และ `drift` ที่ล็อกไว้ CI จึงทำให้บิลด์ล้มเหลวเมื่อเวอร์ชันไม่ตรง เพราะความไม่ตรงกันเปลี่ยนพฤติกรรมของแกน SQLite หรือการยกเลิกงานของ worker

### Repository ที่พอร์ตมาจาก db.js และกติกาที่คงไว้

ชั้น `data/repositories/` มี repository หนึ่งตัวต่อโดเมน กฎธุรกิจถอดมาจากไฟล์ `pos/db.js` ของแอปเดิม แต่เปลี่ยนกลไกจาก snapshot/rollback ใน JavaScript มาเป็น `transaction(() async {...})` ของ Drift ซึ่งหากเกิดข้อผิดพลาดกลางทางจะยกเลิกทั้งชุด ตารางที่ {tab:invariants} สรุปกติกาสำคัญ

TABLE: กติกาธุรกิจของ repository ที่ทำธุรกรรม {#tab:invariants}
| กระบวนการ | กติกาที่คงไว้ |
|---|---|
| `saveSale` | ตรวจสต็อกล่วงหน้า (ข้อความผิดพลาดภาษาไทย `สต็อกไม่พอ…`); ตัดสต็อกแบบเข้มงวด ไม่ปัดค่าติดลบเป็นศูนย์; แต้มที่ได้ = `floor(total/10)`; อัปเดตยอดสะสมและแต้มลูกค้า รวมทั้งสถิติช่าง เมื่อชำระด้วย `เครดิตช่าง` |
| `createReturn` | กันคืนเกินจำนวน (คืนได้ไม่เกินจำนวนที่ขายลบจำนวนที่คืนไปแล้ว); ย้อนส่วนลด แต้ม และยอดช่างตามสัดส่วน; ลดยอดเครดิตเฉพาะกรณี `หักจากเครดิต`; ยกเลิกบิลแม่อัตโนมัติเมื่อคืนครบทั้งบิล |
| `receivePO` | ต้นทุนถัวเฉลี่ยถ่วงน้ำหนัก `round2((oldQty·oldCost + newQty·newCost)/total)` |
| `openShift` | เปิดได้หลายกะต่อวัน (แตกต่างจาก db.js โดยตั้งใจ); ถ้า `id` มีอยู่แล้วคืนกะเดิม มิฉะนั้นจัดเก็บ (archive) กะที่ยังเปิดอยู่ก่อนหน้าก่อนเปิดกะใหม่; บันทึกรายการลิ้นชักไม่ได้หลังปิดกะ |
| ใบเสนอราคา และบิลที่พัก | ไม่แตะสต็อกเลย |
| `adjustStock` | ปรับสต็อกด้วยมือ และปัดค่าติดลบเป็น 0 (ต่างจากการขาย) |

การแยกให้การขาย "ตัดสต็อกแบบเข้มงวด" แต่การปรับด้วยมือ "ปัดที่ศูนย์" เป็นการแยกความหมายโดยตั้งใจ เพราะการขายที่ทำให้สต็อกติดลบหมายถึงข้อมูลคลาดเคลื่อนที่ควรยกเลิกทั้งธุรกรรม (rollback) เพื่อให้เห็นชัด ส่วนการปรับด้วยมือเป็นการแก้ตัวเลขโดยผู้ใช้ นอกจากนี้ฟังก์ชัน `planReturn()` และ `refundedQtyOf()` ในไฟล์ `return_plan.dart` เป็นกฎที่ไม่มีผลข้างเคียง (pure function) ที่ทั้ง `ReturnsRepository` และ `ApiReturnsRepository` ใช้ร่วมกัน และยอดเงินสดที่คาดหวังในลิ้นชักคำนวณจากฟังก์ชันเดียว `ShiftsRepository.cashCountFrom(shift)` ทั้งในหน้าลิ้นชักและรายงานปิดร้าน เพื่อไม่ให้มีกติกาเดียวกันสองชุดที่เบี่ยงจากกัน ส่วน `SnapshotRepository` มี `exportSnapshot()` และ `importLegacyBackup()` ที่นำเข้าไฟล์สำรองของแอป JavaScript เดิมแบบอะตอมมิก ซึ่งเป็นเส้นทางย้ายข้อมูลของร้านจริง

### Repository แบบ API (USE_API_WRITES)

เมื่อคอมไพล์ด้วย `--dart-define=USE_API_WRITES=true` ต้นไม้ provider จะสลับไปใช้ repository ชุดที่เรียกเซิร์ฟเวอร์ เช่น `ApiSalesRepository`, `ApiReturnsRepository` และ `ApiShiftsRepository` ตามที่ ADR-0010 กำหนดว่า `ApiRepository` คือ implementation ใหม่ของ interface เดิมที่เขียนผลที่เซิร์ฟเวอร์ตอบลง Drift (write-through) เหตุผลคือ interface เดิมอยู่ใต้หน้าจอทั้งหมด การสลับ implementation จึงไม่ต้องแก้หน้าจอ และสคีมาของ Drift กับของ PostgreSQL วิวัฒนาการแยกกันได้ กติกาของชั้นนี้มีห้าข้อ

1. ค่า `id` ของบิลและ `Idempotency-Key` สร้างครั้งเดียวต่อตะกร้า ไม่ใช่ต่อการเรียก โดย `PendingWrites` เก็บความพยายามที่ยังไม่ทราบผล มิฉะนั้นการลองใหม่จะได้รหัสใหม่และทำให้บิลซ้ำ
2. เฉพาะรหัส 4xx เท่านั้นที่เป็นคำตัดสิน ส่วน 5xx, 429 หรือคำตอบที่หายไปหมายถึงไม่ทราบว่าการเขียนสำเร็จหรือไม่ ห้ามถอยไปเขียนในเครื่อง ยกเว้นความล้มเหลวของการส่งผ่านเครือข่ายจริง (transport failure) ไฟล์ `api_repository_contract_test.dart` บังคับข้อนี้กับโค้ดทั้งโฟลเดอร์ และเมื่อวันที่ 27 กันยายน พ.ศ. 2569 เจ้าของโครงงานตัดสินเพิ่มว่า 5xx หรือ 429 ไม่เข้าคิวออฟไลน์ แต่เก็บความพยายามไว้พร้อมแสดงข้อผิดพลาด
3. `ApiRepository` ห้ามเรียกบริการธุรกรรมของ Drift เพราะจะตัดสต็อกซ้ำสองรอบ
4. `ApiException` ห้ามหลุดถึงหน้าจอ ต้องแปลงเป็นข้อความภาษาไทยผ่าน `rethrowThai` หรือ `rethrowServerRefusal`
5. ความยินยอม เช่น `overrideCreditLimit` ต้องส่งต่อจากกล่องโต้ตอบที่ผู้ใช้เห็นจริง ไม่ใช่สรุปเองจากการตรวจในเครื่องที่อาจล้าสมัย

### การแยกข้อมูลผู้เช่าด้วย RLS และ TenantService.runTx

ทุกตารางธุรกิจมีคอลัมน์ `tenant_id` และเปิด Row-Level Security แบบ `ENABLE` พร้อม `FORCE` [6] ตามแนวคิดในรูปที่ {fig:rls} แอปเชื่อมต่อในฐานะบทบาท `pos_app` ที่ไม่ใช่ superuser และไม่ใช่เจ้าของตาราง นโยบาย `tenant_isolation` อ่านค่า `current_setting('app.tenant_id', true)` ที่ตั้งด้วย `set_config` ภายในธุรกรรมของคำขอ และห่อด้วย `NULLIF(…, '')` เพื่อให้ค่าว่างให้ผลเป็นศูนย์แถวแทนข้อผิดพลาด ดังนั้นแม้โค้ดแอปลืมใส่เงื่อนไข `WHERE tenant_id` ฐานข้อมูลก็ยังคืนเฉพาะแถวของร้านนั้น

หัวใจของการบังคับใช้คือ `TenantService.runTx(fn)` ซึ่งไม่รับรหัสผู้เช่า (tenant id) เป็นอาร์กิวเมนต์ จึงปลอดภัยโดยโครงสร้าง เพราะผู้เช่ามาจาก JWT ที่ guard ตรวจแล้วเท่านั้น ภาคผนวกของ ADR-0003 แบ่งหน้าที่ว่า guard เป็นผู้ตัดสินสถานะของร้าน ส่วน `runTx` ซึ่งอยู่ใน handler เป็นผู้เปิดธุรกรรมและตั้งค่าตัวแปรเซสชัน แทนแบบเดิมที่ middleware เปิดธุรกรรมให้ทุกคำขอ กติกาที่ผูกพันกับส่วนนี้มีสี่ข้อ

1. ธุรกรรมอยู่ใน handler ไม่ใช่ middleware, guard หรือ interceptor
2. ไม่มีส่วนใดขอการเชื่อมต่อที่สองจาก pool ในคำขอเดียว (รวมถึง `Promise.all` ของ `runTx` หลายตัว) เพราะเคยทำให้ connection pool เต็มจนระบบหยุดตอบสนองมาแล้ว (บทที่ 5)
3. งานที่ช้าแต่ไม่ต้องอยู่ในธุรกรรมทำก่อนเข้าธุรกรรม เช่น การตรวจ PIN ผู้จัดการด้วย argon2 สำหรับการยกเลิกบิลในเฟส 1 (เฟส 2 ตัด PIN ออกและให้ระบุเหตุผลแทน)
4. มีตัวคุมเพดานเวลา 25 วินาทีที่ย้อนธุรกรรมก่อน `COMMIT` พร้อมตั้ง `statement_timeout=25s` ให้ `pos_app`

ไฟล์ทดสอบเชิงสถาปัตยกรรมสามไฟล์คือ `tenant-door.spec.ts`, `tenant-wrapper.spec.ts` และ `idempotency-routes.spec.ts` บังคับข้อแรกและข้อที่สองในระดับโครงสร้างโค้ด ส่วนเพดานเวลาทดสอบใน `tx-ceiling.e2e-spec.ts` ลำดับการประมวลผลคำขอเขียนหนึ่งคำขอแสดงดังรูปที่ {fig:request-flow}

FIGURE: ลำดับการประมวลผลคำขอเขียนหนึ่งคำขอผ่านชั้นการแยกผู้เช่าและ idempotency {#fig:request-flow} | diagram:request-flow

### Idempotency และลำดับการล็อก

ระบบบังคับ `Idempotency-Key` กับคำสั่งเขียน ตาราง `idempotency_keys` เก็บคีย์และค่าสรุปของคำขอ (fingerprint) โดย fingerprint คือ method บวกพาธจริงของคำขอ (ไม่ใช่ pattern ของ route) บวกแฮชของเนื้อหา เพื่อไม่ให้คีย์เดียวถูกใช้กับสองบิลที่ต่างกันแล้วชนกัน คำขอซ้ำที่คีย์ตรงกันได้คำตอบเดิม คีย์เดิมกับเนื้อหาต่างกันถูกปฏิเสธ และคีย์ที่คำขอแรกยังประมวลผลอยู่ได้ `503 IDEMPOTENCY_KEY_IN_FLIGHT` การบันทึกคีย์อยู่ในธุรกรรมเดียวกับการเขียน และตัวนับการตอบซ้ำเพิ่มค่าเฉพาะเมื่อธุรกรรมยืนยันแล้ว

เพื่อกันเดดล็อก ทีมกำหนดลำดับล็อกเดียวสำหรับงานด้านการเงินและสต็อก คือ `sales` → ช่าง → `products` → `doc_counters` → ลูกค้า โดยการยกเลิกบิลและการคืนสินค้าอ่าน `shifts` แบบ `FOR SHARE` แทรกระหว่างล็อกบิลกับล็อกช่าง ส่วนการรับใบสั่งซื้อล็อกแถว PO ก่อนแล้วล็อกสินค้าเรียงตาม id และคำนวณต้นทุนถัวเฉลี่ยแบบปัดสตางค์ครึ่งขึ้น (ต่างจาก `round2` แบบทศนิยมลอยตัวฝั่ง Dart โดยตั้งใจ) โค้ดใหม่ที่เขียนเกินหนึ่งตารางในกลุ่มนี้ต้องคงลำดับเดิม

### การยืนยันตัวตนและการผูกเครื่อง

ตาม ADR-0009 โทเค็นเข้าถึงมีอายุ 15 นาที และโทเค็นต่ออายุหมดอายุเวลา 04:00 น. ของทุกวัน ไม่ใช่ 24 ชั่วโมงนับจากการเข้าสู่ระบบ เพราะร้านเปิดปิดกะทุกวันอยู่แล้ว เครื่องหน้าเคาน์เตอร์มีคนเดินผ่านจึงไม่ควรค้างเซสชันหลายวัน และการเพิกถอนทำได้โดยไม่ต้องมีรายการห้ามใช้ใน Redis เพราะเมื่อปิด `users.is_active` การต่ออายุครั้งถัดไปจะไม่ผ่าน เวลา 04:00 อยู่นอกเวลาทำการ พนักงานจึงไม่ถูกบังคับออกจากระบบขณะลูกค้ายืนรอ ภาคผนวกของ ADR-0009 กำหนดลายเซ็น RS256 [7] และบนเว็บให้เก็บโทเค็นเข้าถึงในหน่วยความจำเท่านั้น ส่วนโทเค็นต่ออายุและโทเค็นอุปกรณ์เก็บใน IndexedDB โดยห้ามมี `localStorage` เป็นทางสำรอง

ADR-0004 แบ่งเครื่องตามบทบาท คือ `pos` ได้เพียงเครื่องเดียวต่อร้าน (แตะลิ้นชัก ออกเลขเอกสาร และเขียนออฟไลน์ได้) และ `backoffice` ได้หลายเครื่อง (สต็อกและรายงาน ออนไลน์เท่านั้น) เส้นแบ่งคือ "แตะลิ้นชักหรือไม่" ไม่ใช่ "แตะสต็อกหรือไม่" เจ้าของร้านออก `enrolCode` ผ่าน `POST /devices` แล้วเครื่องนำรหัสไปแลกเป็น device token ที่ `POST /auth/device` และดัชนีไม่ซ้ำ `one_pos_per_tenant` บังคับกติกาเครื่อง `pos` เดียวที่ระดับฐานข้อมูล ในเฟส 2 เจ้าของโครงงานกำหนดเพิ่มว่าร้านมีบทบาทผู้ใช้ `owner` เพียงบทบาทเดียว และการถอดถอนเครื่อง การ enrol และการ export ต้องมี device token ที่ enrol แล้ว รหัสผ่านอย่างเดียวไม่พอ

การตรวจรหัสผ่านใช้ argon2 โดยลองรูปแบบยูนิโคด Normalization Form C (NFC) ก่อนแล้วลองสตริงดิบเป็นทางสำรอง เพราะ NFC จัดเรียงสระและวรรณยุกต์ภาษาไทยใหม่ ขณะที่แฮชที่สร้างไว้ก่อนหน้าเป็นแฮชของสตริงดิบ หากตัดทางสำรองออก เจ้าของร้านที่ตั้งรหัสไว้ก่อนจะเข้าระบบไม่ได้ ความยาวรหัสผ่านขั้นต่ำกำหนดไว้ที่เดียวใน `src/common/password.ts` และเมื่อสร้างร้านใหม่ ระบบออกรหัสผ่านชั่วคราวอายุ 7 วันให้เจ้าของร้าน และเมื่อเข้าสู่ระบบด้วยรหัสนี้ต้องตั้งรหัสใหม่ภายใน 10 นาที

### ระนาบผู้ดูแลแพลตฟอร์ม

ADR-0001 กำหนดให้ผู้ดูแลแพลตฟอร์มสร้างร้านใหม่ผ่าน `POST /platform/tenants` ในธุรกรรมเดียว ได้ผู้เช่า เจ้าของ การตั้งค่า และข้อมูลเริ่มต้นพร้อมกัน ADR-0002 แยกผู้ดูแลเป็นตาราง `platform_admins` ต่างหาก ใช้ JWT ที่มีกลุ่มผู้รับ (`aud`) ต่างกัน ใช้การเชื่อมต่อฐานข้อมูลที่ข้าม RLS แยกต่างหาก และบันทึกตรวจสอบทุกครั้ง เหตุผลคือถ้าบัญชีผู้ดูแลอยู่ในตาราง `users` เดียวกับร้าน ขอบเขตของ RLS จะพร่าเลือน Nginx อนุญาตเส้นทาง `/api/v1/platform/` เฉพาะ loopback และ IP ที่ระบุใน `PLATFORM_ADMIN_IPS` และหน้าจอเว็บ `platform-ui` ผูกกับ `127.0.0.1:3200` ซึ่งเข้าถึงผ่านอุโมงค์ SSH เท่านั้น

### การจำกัดอัตรา งานเบื้องหลัง และ etcd

ADR-0006 บังคับการจำกัดอัตราสองชั้น ชั้นนอกคือ Nginx ใช้ `limit_req_zone` ต่อ IP (30 คำขอต่อวินาที burst 60) ป้องกันการท่วมจากภายนอก ชั้นในคือ guard ของ NestJS กับ Redis ต่อ `tenant_id` กันไม่ให้ร้านเดียวกินทรัพยากรจนร้านอื่นช้า เหตุผลที่ไม่ทำต่อร้านที่ Nginx คือ Nginx รุ่นฟรีอ่าน JWT ไม่ได้ และการให้ไคลเอนต์ส่งรหัสร้านในส่วนหัวมาเองฝ่าฝืนกติกาว่าผู้เช่าต้องมาจาก JWT เท่านั้น การเข้าสู่ระบบนับความพยายามด้วยคำสั่ง Lua แบบอะตอมิกบน Redis ก่อนทราบผล เพื่อให้ทุกการปฏิเสธถูกนับ หาก Redis ล่ม ตัวนับทำงานแบบ fail-open เพราะร้านหยุดขายไม่ได้ แต่การตรวจสถานะร้านไม่ fail-open ร้านที่ถูกระงับจึงยังถูกปฏิเสธทันที

งานเบื้องหลังใช้ BullMQ [8] บน `redis-queue` โดย `TenantJobRunner` ใช้เพดานเวลาคอมมิตเดียวกับ `runTx` และมีคิวงานล้มเหลว (dead-letter queue) การ export ข้อมูลรายร้านเขียนไฟล์ลงโวลุ่มที่ใช้ร่วมกันระหว่าง `worker` กับ `api` แทนการฝังข้อมูลทั้งชุดลงในงานของคิว เพราะ `redis-queue` จำกัดหน่วยความจำไว้ที่ 192 MB แบบ `noeviction` ส่วน etcd เก็บเฉพาะค่าตั้งขณะรันที่ปรับได้โดยไม่ต้อง deploy ใหม่ เช่น `log_level` ตามที่ ADR-0013 กำหนด

### การวัดผลและสังเกตการณ์

`GET /metrics` คืนข้อความรูปแบบ Prometheus [9] และ Nginx ตอบ 404 ต่อภายนอกสำหรับเส้นทางนี้ ตัวชี้วัดหลักคือ `http_requests_total` และ `http_request_duration_seconds` ซึ่งชื่อถูกอ้างโดยแผงใน Grafana หากเปลี่ยนชื่อ แผงจะว่างโดยไม่มีข้อผิดพลาด การนับทำใน middleware เพื่อให้คำขอที่ guard ปฏิเสธ (401 และ 429) ถูกนับด้วย และ label `route` เป็น pattern ไม่ใช่พาธจริง เส้นทาง `/metrics`, `/health/live` และ `/health/ready` ถูกตัดออกจาก SLI เพราะการ scrape และ healthcheck สร้างคำขอที่สำเร็จแน่นอนราว 36 ครั้งต่อนาที ซึ่งทำให้วันที่ทุกบิลจริงล้มเหลวยังอ่านอัตราสำเร็จได้ราวร้อยละ 92 (เจ้าของโครงงานอนุมัติเมื่อ 21 กันยายน พ.ศ. 2569) ตัวนับ `pos_idempotency_replay_total` ไม่มี label `tenant_id` เพื่อควบคุมจำนวนอนุกรม

### POST /sync/push

เมื่อเครือข่ายกลับมา `SyncService` ส่ง op เป็นชุดละไม่เกิน 50 รายการด้วยส่วนหัว `X-Device-Token` ฝั่งเซิร์ฟเวอร์ประมวลผลทีละ op ตามลำดับดังนี้

1. เรียก `runIdempotent` ด้วยคีย์และ fingerprint เดียวกับเส้นทางออนไลน์ ถ้าเคยทำแล้วตอบ `applied`
2. ตรวจซ้ำด้วยรหัสที่ไคลเอนต์สร้าง (เช่น `sales.id`) ในธุรกรรมเดียวกัน ถ้า id ซ้ำแต่เนื้อหาไม่ตรง ตอบ `rejected`
3. เรียกบริการเดียวกับ controller ออนไลน์ด้วยลำดับล็อกเดิม ถ้าบริการปฏิเสธ ตอบ `rejected`
4. ทำผลพลอยได้ในธุรกรรมเดียวกัน เช่น การตั้งธงว่าขายออฟไลน์ การปรับวันที่ที่ผิดปกติ และการสร้างรายการตรวจ

ทุก op มี `runTx` ของตัวเองต่อกันทีละตัว เมื่อ op ใดได้ผลที่ไม่แน่นอน (คำขอเดิมยังค้าง เกินเพดานเวลา หรือ 5xx) เซิร์ฟเวอร์ตอบ `retry` แล้วหยุดชุดนั้น

ฝั่งไคลเอนต์ส่งทีละคำขอ เมื่อได้ `retry` จะนับ `attempts` และเมื่อครบ 3 ครั้ง op จะเป็น `stuck` และปรากฏในหน้ารายการรอเจ้าของร้านตรวจ op ที่อยู่ใน aggregate เดียวกับ op ที่ติดจะรอต่อเนื่องกันตามลำดับ ส่วน op อื่นยังไปต่อได้

ตัวอย่างเช่น คิว [เปิดกะ S] [ขาย A] [ยกเลิก A] [ขาย B] ถ้าขาย A ติด การยกเลิก A จะรอ แต่ขาย B ส่งต่อได้ ทว่าถ้าการเปิดกะ S ติด ทุก op ในกะ S จะรอ

เจ้าของร้านเลือกส่งใหม่ด้วยคีย์เดิมหรือทิ้งพร้อมหมายเหตุผ่าน `POST /sync/discards` และการทิ้งใช้ตาราง `op_effects` ย้อนผลเฉพาะที่ได้ใช้จริง การปิดกะต้องรอให้คิวว่างทั้งหมด `ApiShiftsRepository.closeShift` จึงส่งคิวที่ส่งได้ก่อน แล้วปฏิเสธด้วย `OUTBOX_NOT_EMPTY` เมื่อยังมีแถวใน `outbox_ops` ไม่ว่าสถานะหรือชนิดใด การตรวจนี้ทำที่ไคลเอนต์เท่านั้นเพราะเซิร์ฟเวอร์มองไม่เห็นคิวในเครื่อง

### เลข RC และ CN ที่ออกบนเครื่อง

ADR-0007 กำหนดเลขเอกสารแบบเรียงต่อเครื่องและรีเซ็ตรายเดือน รูปแบบ `RC01-2569-08-0042` คือ prefix ตามชนิดเอกสาร (RC ใบเสร็จ, CN ใบลดหนี้, PO ใบสั่งซื้อ, QT ใบเสนอราคา, CP ใบรับชำระเครดิตช่าง) ตามด้วยหมายเลขเครื่องสองหลัก ปี พ.ศ. เดือน และลำดับสี่หลัก การเติมศูนย์ให้หมายเลขเครื่องทำให้ `RC1-` กับ `RC12-` ไม่อ่านกำกวม ในเฟส 1 เซิร์ฟเวอร์ออกเลขทั้งหมดด้วย `UPDATE doc_counters … RETURNING` ใต้ row lock ในธุรกรรมเดียวกับการขาย ในเฟส 2 เครื่อง `pos` ออก RC และ CN เองทั้งออนไลน์และออฟไลน์ ส่วน PO, QT และ CP เซิร์ฟเวอร์ยังออกให้เสมอ เพราะเครื่อง `backoffice` ออนไลน์เสมอและไม่ได้ประโยชน์จากการออกเลขเอง

เซิร์ฟเวอร์ตรวจว่า prefix ตรงกับชนิดเอกสาร และหมายเลขเครื่องตรงกับเครื่องจากโทเค็น เก็บ high-water mark ด้วย `INSERT … ON CONFLICT … DO UPDATE SET last_no = GREATEST(…)` และข้อจำกัด UNIQUE บน `receipt_no` และ `cn_no` เป็นด่านสุดท้ายกันเลขซ้ำ เมื่อออฟไลน์ข้ามเดือน เลขเริ่มที่ 0001 ใหม่ตามนาฬิกาเครื่อง ส่วนเครื่องที่ยังไม่เคยเตรียมตัวนับ (เพิ่ง enrol หรือเพิ่งอัปเกรด) ถูกห้ามออกเลขออฟไลน์ด้วยรหัส `OFFLINE_SEED_REQUIRED` กติกาสำคัญอีกข้อคือเลข RC หรือ CN ที่เซิร์ฟเวอร์ออก ทั้งในคำตอบออนไลน์และจากการเล่นซ้ำของ `/sync/push` ต้องถูกบันทึกลงตัวนับในเครื่องผ่าน `DocNumberService.commitServerIssued` มิฉะนั้นเครื่องอาจออกเลขซ้ำกับที่เซิร์ฟเวอร์เคยให้

### การดึงข้อมูลแบบ keyset

หลังส่งคิวหมด ไคลเอนต์ดึงข้อมูลใหม่จากเซิร์ฟเวอร์ (push ก่อน pull เสมอ) โดยใช้ `meta.nextCursor` ของเซิร์ฟเวอร์ที่เก็บในตาราง `SyncCursors` ต่อชนิดข้อมูล เหตุผลที่ต้องเป็น keyset แทน offset หรือ timestamp เปล่า คือหลายแถวอาจมี `updated_at` เท่ากันจาก `now()` ของธุรกรรมเดียว และ timestamp ระดับมิลลิวินาทีจะข้ามหรือซ้ำแถวที่ใช้ค่าเดียวกัน cursor จึงมีความละเอียดระดับไมโครวินาทีร่วมกับ `afterId` ส่วนหน้าแรกของแต่ละรอบ ไคลเอนต์ถอย cursor กลับ 30 วินาทีและไม่ส่ง `afterId` เพื่อรองรับธุรกรรมที่ commit ช้ากว่าที่ cursor ผ่านไปแล้ว ซึ่งปลอดภัยเพราะเพดานเวลา 25 วินาทีทำให้ไม่มีธุรกรรมใดค้างนานกว่านั้น แถวที่ถูกลบเป็นสัญลักษณ์ลบ (tombstone) ให้ไคลเอนต์ซ่อน การดึงข้อมูลไม่ทับสต็อกของสินค้าที่ยังมี op ค้าง และไม่ทับยอดลูกค้าหรือช่างที่ถูกอ้างโดย op ทางการเงินที่ยังไม่ส่ง ตามหลักความสอดคล้องในที่สุดที่กล่าวในบทที่ 2

### โครงสร้างการ deploy และระดับของ CI/CD

สภาพแวดล้อมจริงเพียงแห่งเดียวคือเครื่องเสมือนของคณะชื่อ `mob04` (สภาพแวดล้อม `demo`) ตาม ADR-0013 ซึ่งอยู่ในเครือข่ายมหาวิทยาลัย Docker Compose ประกอบจากสามไฟล์ คือ `server/docker-compose.yml` (ฐาน), `deploy/compose/vm.override.yml` (สลับเป็นอิมเมจจาก GHCR ตามแท็กของคอมมิต) และ `deploy/compose/monitoring.yml` (Prometheus, Grafana, Node Exporter) ไปป์ไลน์ทั้งหมดแสดงดังรูปที่ {fig:cicd}

FIGURE: ภาพรวมไปป์ไลน์ CI/CD ของโครงงาน ตั้งแต่คำขอรวมถึงการติดตั้งบนเครื่องสาธิต {#fig:cicd} | diagram:cicd-pipeline

CI/CD บน GitHub Actions [10] แบ่งเป็นสี่ระดับ ระดับ 1 คือ Flutter CI (`flutter.yml`: `analyze-and-test`, `deps-audit`, `codegen-check`, `build-web`) ระดับ 2 คือ backend CI (`server.yml`: `secrets`, `lint`, `audit`, `unit`, `nginx-check`, `integration`, `build-image`) ระดับ 3 คือการสร้างอิมเมจลง GHCR พร้อม Trivy ที่บล็อกเมื่อพบช่องโหว่ระดับสูง และระดับ 4 คือการ deploy ด้วย Ansible (`deploy.yml`) นอกจากสี่ระดับนี้ยังมีเวิร์กโฟลว์ `android-apk.yml` ที่สั่งรันด้วยมือเท่านั้น (รายละเอียดในหัวข้อถัดไป) ทั้งสองเวิร์กโฟลว์แรกถูกเรียกทุก push และ pull request โดยไม่กรองพาธที่ชั้นนอก แต่มีงาน `changes` ภายในตัดสินว่าจะรันงานใด และลงท้ายด้วยงานสถานะที่รายงานผลเสมอ (`flutter-ci-status`, `server-ci-status`) ซึ่งเป็นเงื่อนไขบังคับของสาขา `main` เพียงสองรายการ เหตุผลคือการตรวจสอบสถานะที่บังคับต้องรายงานผลทุกครั้ง หากกรองพาธที่ชั้นนอก PR ที่แก้เฉพาะ `server/` จะไม่มีสถานะของ Flutter CI ให้ผ่าน push ที่แก้เฉพาะเอกสาร (`*.md` หรือ `docs/**`) ข้ามการทดสอบและการสร้างอิมเมจ เครื่องเสมือนจึงอยู่ที่ SHA ของโค้ดล่าสุดเสมอ

### Ansible และ self-hosted runner

playbook `deploy.yml` ของ Ansible [11] ทำตามลำดับ ตรวจ SHA ที่รันอยู่และออกก่อนเมื่อซ้ำ ซิงก์ไฟล์ Compose และ Nginx ดึงอิมเมจจาก GHCR รัน migrations ผ่านคอนเทนเนอร์ `migrate` (สคีมาก่อนโค้ด) รีสตาร์ตแบบหมุนเวียน `api-1` → `api-2` → `api-3` พร้อมตรวจสุขภาพ รีสตาร์ต worker และ bull-board อัปเดตไฟล์เว็บแล้วสร้าง Nginx ใหม่ ตรวจ `GET /health/ready` ผ่าน Nginx บันทึก SHA ลง `/opt/pos/.current_sha` และสุดท้ายเริ่มชุดมอนิเตอร์ ซึ่งหากล้มเหลวจะเพียงแจ้งเตือน migration รันเป็นงานครั้งเดียวก่อน api ทุกตัว ไม่ใช่ตอนบูต เพราะอินสแตนซ์สามตัวจะแย่งกัน เมื่อ readiness ล้มเหลว สคริปต์ deploy จะติดตั้งรุ่นก่อนหน้ากลับอัตโนมัติ

เครื่องเสมือนอยู่หลังเครือข่ายมหาวิทยาลัยที่ตัวรันของ GitHub เข้าไม่ถึง ทีมจึงติดตั้ง self-hosted runner บน `mob04` และสภาพแวดล้อม `demo` กำหนดให้ผู้ตรวจที่ระบุอนุมัติก่อนงาน `deploy` จะแตะเครื่อง (ภาคผนวกของ ADR-0013) การ trigger อัตโนมัติทุกครั้งที่ `main` ผ่านยังคงอยู่ แต่งานจะค้างในสถานะรออนุมัติ ซึ่งเป็นกลไกเดียวที่กันการ merge ไม่ให้ไปทับเครื่องระหว่างการสาธิต ผลการ deploy จริงรายงานในบทที่ 4

### TLS ด้วย CA ส่วนตัวและการสร้างไฟล์ติดตั้ง Android

แอปบน Android ที่สร้างด้วยบิลด์ API เรียก `https://172.30.58.20` ซึ่ง `HttpClient` ของ Dart จะปฏิเสธเมื่อใบรับรองไม่เชื่อมโยงถึง root ที่เชื่อถือหรือไม่มี IP นั้นใน Subject Alternative Name (SAN) โครงงานยังไม่มีชื่อ DNS จึงขอใบรับรองสาธารณะไม่ได้ ทีมจึงเลือกใช้ Certificate Authority (CA) ส่วนตัว (PR #552) แทนการตั้งให้แอปข้ามการตรวจใบรับรอง คอนเทนเนอร์ครั้งเดียว `certgen` (`server/docker/certgen/certgen.sh`) สร้าง CA ไว้ในวอลุ่ม `certs-ca` เพียงครั้งเดียวและไม่แทนที่อีก เพราะทุกไฟล์ติดตั้งที่สร้างแล้วฝังส่วนสาธารณะของ CA นี้ไว้ จากนั้นออกใบรับรองเซิร์ฟเวอร์ที่มี SAN เป็น `localhost`, `127.0.0.1` และ `172.30.58.20` ให้ Nginx ใช้ และออกใหม่เมื่อใบเดิมหาย ไม่ได้ลงนามโดย CA นี้ มี SAN ต่างไป หรือใกล้หมดอายุภายใน 30 วัน ส่วนกุญแจของ CA ไม่ออกจากวอลุ่ม ไม่เข้า git และไม่เข้า CI playbook `deploy.yml` รัน `certgen` ด้วย `docker compose run` ก่อนสร้าง Nginx ใหม่ เพื่อให้การออกใบรับรองที่ล้มเหลวทำให้การ deploy ล้มเหลวด้วย (`up -d` ไม่รอคอนเทนเนอร์ครั้งเดียว) และงาน `nginx-check` ของ `server.yml` รันสคริปต์ทดสอบ `deploy/scripts/test/certgen.test.sh` ฝั่งแอป `frontend/lib/core/network/pos_trust_io.dart` อ่านใบรับรอง CA จากแอสเซตแล้วตั้ง `HttpOverrides` ให้ทุก `HttpClient` เชื่อถือ CA นี้ควบคู่กับ root ของระบบ การตรวจชื่อโฮสต์ยังทำงานตามเดิม และถ้าแอสเซตว่างหรือเสียแอปจะไม่หยุดทำงาน เพียงใช้ root ของระบบ

เวิร์กโฟลว์ `.github/workflows/android-apk.yml` (PR #551) สั่งรันด้วยมือเท่านั้น (`workflow_dispatch`) และทำงานเฉพาะบนสาขา `main` สร้างไฟล์ติดตั้ง Android Package Kit (APK) ชนิดเดียว คือบิลด์ API (`USE_API_WRITES=true`, `API_BASE_URL=https://172.30.58.20`) ลงนามด้วยกุญแจถาวรจากความลับ `ANDROID_KEYSTORE_B64` เพื่อให้รุ่นถัดไปติดตั้งทับได้ แล้วเผยแพร่เป็น pre-release บน GitHub ชื่อ `apk-<sha7>` เวิร์กโฟลว์ปฏิเสธการสร้างหากไม่มีความลับดังกล่าว (ไม่ใช้กุญแจชั่วคราว) หรือ release ชื่อเดิมมีอยู่แล้ว ไม่มี APK แบบออฟไลน์ล้วนจาก `main` เพราะค่าเริ่มต้นของบิลด์คือโหมด API และแอปต้องเพิ่มสิทธิ์ `INTERNET` ใน `AndroidManifest.xml` เนื่องจากบิลด์ release ไม่มีสิทธิ์นี้โดยปริยาย

ณ วันที่ 3 ตุลาคม พ.ศ. 2569 ทั้งสองส่วนรวมโค้ดแล้วแต่ **ยังไม่ถูกพิสูจน์บนระบบจริง** เวิร์กโฟลว์ APK ยังไม่เคยรัน และ CA ยังไม่ถูกติดตั้งใช้งานบน `mob04` แอสเซต `frontend/assets/certs/pos-ca.crt` ยังว่างอยู่ใน git จนกว่าเจ้าของโครงงานจะ deploy `certgen` ขึ้น `mob04` คัดลอก `ca.crt` ออกมา แล้วคอมมิตเข้าที่ตามขั้นตอนใน `07_CICD_DEPLOY.md` §5 "TLS" APK ที่สร้างก่อนขั้นตอนนี้เชื่อมต่อเซิร์ฟเวอร์ไม่ได้ และการเปลี่ยน IP ของ VM ต้องแก้ SAN ใน `certgen.sh` ด้วย

## วิธีการทำงานของทีม

### การแบ่งงานและการติดตามงาน

ทีมสามคนแบ่งเลนตามตารางที่ {tab:lanes} ในบทที่ 1 และติดตามงานด้วยตั๋วงานบน GitHub (issue) ตั๋วงานหลัก (parent issue) ไม่ถูกลงมือโดยตรง และตั๋วงานที่เป็นการตัดสินใจของเจ้าของโครงงานไม่ถูกตัดสินใน pull request สำหรับเฟส 2 เอกสาร `09_PHASE2_LANES.md` แบ่งตั๋วงาน 35 ตั๋วเป็นสามเลน โดยเลน B ดูแลกลไกฝั่งเครื่องทั้งหมด เลน C ดูแลเซิร์ฟเวอร์ หน้าจอใหม่ และงานปฏิบัติการ ส่วนเลน A มีตั๋วงานปลดล็อกสามตั๋ว หลักสำคัญคือ "การรอกันไม่ข้ามเลน" กล่าวคือความต้องการข้ามเลนต้องกำหนดเป็นสัญญา (contract) เช่น ไฟล์ตัวอย่างคำขอ `/sync/push` และอินเทอร์เฟซ `SyncFacade` ไม่ใช่การรอคิวกัน ตั๋วงานที่ถูกแบ่งเป็นสองส่วน (ไคลเอนต์กับเซิร์ฟเวอร์) ไม่ถือว่าทำงานกับของจริงได้จนกว่าอีกส่วนจะรวมโค้ด แต่ละฝั่งจึงทดสอบกับตัวจำลอง (fake) ของฝั่งตนเอง

### ADR และลำดับความสำคัญของเอกสาร

การตัดสินใจเชิงสถาปัตยกรรมบันทึกเป็น ADR หนึ่งไฟล์ต่อหนึ่งเรื่องตามแนวทางของ Nygard [12] ปัจจุบันมี 13 หมายเลข (0001 ถึง 0013) ครอบคลุมการสร้างผู้เช่า ระนาบผู้ดูแล วงจรชีวิตผู้เช่า บทบาทอุปกรณ์ การส่งออกข้อมูล ขีดจำกัดอัตรา เลขที่ใบเสร็จ ต้นทุน ณ เวลาขาย อายุเซสชัน การเขียนผ่านแคช โมโนรีโป CouchDB (ถูกปฏิเสธ) และชุดเครื่องมือ CI/CD กติกาของทีมคือ เมื่อเอกสารขัดกับ ADR ให้ยึด ADR และ ADR ที่เปลี่ยนใจภายหลังใช้ภาคผนวกลงวันที่แทนการเขียนทับประวัติ

### ขั้นตอนการพัฒนาและการตรวจ

ทุกงานเข้า `main` ผ่าน pull request ที่ต้องผ่านการตรวจสอบสถานะบังคับสองรายการ การป้องกันสาขาตั้งแต่ 15 กันยายน พ.ศ. 2569 ห้าม force-push และห้ามลบสาขา แต่ไม่ได้กำหนดจำนวนผู้อนุมัติขั้นต่ำ (ตั้งไว้ 0 คน) ที่เก็บโค้ดมีสาขายาวสองสาขาคือ `main` และ `POC_sample_offline_first` ตั๋วงานแต่ละตั๋วเริ่มด้วยการทบทวนแนวทางจากมุมคนนอก (ตั้งคำถามว่าเจตนาถูกหรือไม่และมีทางที่ง่ายกว่าหรือไม่ แล้วตามรอยเส้นทางโค้ดจริง) แก้โค้ดเท่าที่จำเป็นพร้อมเกณฑ์ที่ตรวจได้ และปิดด้วยการทบทวนโค้ดสองแกน คือมาตรฐานของที่เก็บโค้ด และความตรงกับสเปกของตั๋วงานต้นทาง บทเรียนจากกระบวนการนี้ถูกบันทึกกลับเป็นกติกาของโครงงาน ซึ่งกรณีสำคัญสรุปไว้ในบทที่ 5
