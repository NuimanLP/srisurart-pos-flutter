# ผลการดำเนินงาน

## สรุปผลการดำเนินงาน

ตารางที่ {tab:objectives} เทียบวัตถุประสงค์ทั้งเจ็ดข้อในบทที่ 1 กับผลที่ได้ หลักฐาน และสถานะ ณ วันที่ 4 ตุลาคม พ.ศ. 2569 (ตัวเลขสถิติยังเป็นค่าที่วัดเมื่อ 1 ตุลาคม พ.ศ. 2569)

TABLE: ผลการดำเนินงานเทียบกับวัตถุประสงค์ {#tab:objectives}
| วัตถุประสงค์ | ผลที่ได้ | หลักฐาน | สถานะ |
|---|---|---|---|
| 1. แอป Flutter offline-first ที่คงกติกาเดิม | พอร์ตกฎธุรกรรมครบ หน้าจอ 14 ไฟล์ รายงานยอดขาย กำไร และสินค้าขายดี ชุดทดสอบ 820 กรณีผ่านทั้งหมด (1 ต.ค. 2569) | ตารางที่ {tab:invariants} และ {tab:ptrace} | เสร็จบนเว็บ สร้าง APK ได้แล้ว (#551, #560) แต่ยังไม่มีบันทึกการทดสอบบนอุปกรณ์ Android/iOS จริง |

## ปัญหาและอุปสรรค

หัวข้อนี้เลือกเฉพาะปัญหาที่เกิดขึ้นจริงและมีบันทึกในเอกสารของโครงงาน แต่ละข้อแสดงเป็นลำดับ ปัญหา สาเหตุ วิธีแก้ และบทเรียน

### พาธที่มีอักษรไทยทำให้ build_runner ล้มเหลว

**ปัญหา** ที่เก็บโค้ดอยู่ในโฟลเดอร์ชื่อภาษาไทยที่ซิงก์ผ่าน BeeStation คำสั่ง `build_runner` [1] สำหรับสร้างโค้ดของ Drift และคำสั่ง `flutter analyze` ล้มเหลวด้วยข้อความว่าเขียนไฟล์ `build.dart.aot` ไม่ได้ **สาเหตุ** คอมไพเลอร์ AOT ของ Dart แปลงพาธที่มีอักษรนอก ASCII เป็นเครื่องหมายคำถาม และ Windows junction แก้ไม่ได้เพราะ `build_runner` ใช้พาธจริง **วิธีแก้** คัดลอกที่เก็บโค้ดไปยังพาธ ASCII เพื่อรัน `build_runner` แล้วคอมมิตไฟล์ `*.g.dart` ที่สร้างใหม่ และใช้ `dart analyze` แทน `flutter analyze` เสมอ **บทเรียน** ข้อจำกัดของเครื่องมือเชิงพาธต้องบันทึกเป็นกฎของโครงงานตั้งแต่แรก และงาน `codegen-check` ใน CI ช่วยตรวจว่าไฟล์ที่สร้างตรงกับสคีมา

### ไฟร์วอลล์ของคณะปิดกั้นการดึงอิมเมจจาก ghcr.io

**ปัญหา** การ deploy อัตโนมัติไปยัง `mob04` ถูกปิดกั้น เครื่องดึงอิมเมจจากรีจิสทรีภายนอกไม่ได้และเกิดข้อผิดพลาด `x509: certificate is not valid for any names` **สาเหตุ** ไฟร์วอลล์ FortiGate ของคณะตรวจและแทนที่ใบรับรองของการเชื่อมต่อ TLS ด้วยใบรับรองที่ไม่มีชื่อตรงกับโดเมนปลายทาง **วิธีแก้** แก้ได้เมื่อ 29–30 กันยายน พ.ศ. 2569 หลังทีมเครือข่ายเพิ่มชื่อทางเลือก (Subject Alternative Name: SAN) ในใบรับรอง หากอาการกลับมา ทางแก้ที่ถูกคือให้ทีมเครือข่ายยกเว้นรีจิสทรีเหล่านี้สำหรับ IP ของ VM ส่วนการคัดลอกอิมเมจด้วยมือเป็นเพียงทางแก้ฉุกเฉินในวันสาธิต ไม่ใช่ CD **บทเรียน** การออกแบบการ deploy ต้องรวมความเสี่ยงของเครือข่ายที่ทีมไม่ได้ควบคุม และกำหนดขอบเขตของทางสำรองไว้ล่วงหน้า

### pool ฐานข้อมูลหมดเมื่อมีคำขอพร้อมกัน (#162)

**ปัญหา** เมื่อมีคำขอพร้อมกันเท่ากับขนาด pool ระบบหยุดตอบสนอง **สาเหตุ** guard แบบ global ที่ทำงานกับทุกคำขอและอ่านแผนของร้านตอนแคชว่าง ขอการเชื่อมต่อจาก pool เป็นครั้งที่สองภายในคำขอที่ถือการเชื่อมต่อแรกอยู่แล้ว ทุกคำขอจึงรอกันเอง **วิธีแก้** กำหนดเป็นกฎว่าไม่มีส่วนประกอบใดขอการเชื่อมต่อที่สองในคำขอเดียว และรวม `runTx` ที่ทำพร้อมกันเป็นตัวเดียว พร้อมสเปกสถาปัตยกรรมที่บังคับจุดเชื่อมนี้ **บทเรียน** ความผิดพลาดของทรัพยากรที่จำกัดไม่ปรากฏเมื่อทดสอบทีละคำขอ ต้องมีการทดสอบที่ใช้จำนวนคำขอพร้อมกันเท่าขนาด pool (เช่น `rate-limit-pool.e2e-spec.ts` และ `health-pool.e2e-spec.ts`)

### การทิ้งรายการในคิวย้อนผลไม่ตรง (#473, #488)

**ปัญหา** เมื่อเจ้าของร้านทิ้งรายการขายหรือคืนที่ค้างในคิว สต็อกและยอดในเครื่องไม่ถูกย้อน และเมื่อแก้ให้ย้อนแล้ว ยอดที่ย้อนยังไม่ตรงในบางกรณี **สาเหตุ** การย้อนคำนวณจากข้อมูลปัจจุบัน แต่การเขียนครั้งแรกอาจถูกปัดค่าที่ศูนย์ เช่น ช่างมีเครดิตค้าง 50 บาทแต่ใบลดหนี้หักเครดิต 180 บาท ยอดจึงถูกปัดเป็น 0 และการย้อนคืนยอดเป็น 180 บาท ซึ่งสร้างหนี้ 130 บาทที่ไม่มีอยู่จริง **วิธีแก้** PR #483 ย้อนผลในธุรกรรมเดียวกับการทิ้ง และ PR #495 เก็บผลต่างที่ใช้จริงในตาราง `op_effects` (Drift schema v13) แล้วย้อนตามค่านั้น **บทเรียน** การย้อนผลที่ถูกต้องต้องบันทึกสิ่งที่เกิดขึ้นจริง ณ เวลาเขียน ไม่ใช่คำนวณกลับจากสถานะปัจจุบัน

### เลขที่เอกสารซ้ำระหว่างการออกเลขออนไลน์กับออฟไลน์ (#489)

**ปัญหา** เครื่องอาจออกเลขใบเสร็จหรือใบลดหนี้แบบออฟไลน์ซ้ำกับเลขที่เซิร์ฟเวอร์เคยออกให้ **สาเหตุ** เลข RC หรือ CN ที่เซิร์ฟเวอร์ออกในคำตอบออนไลน์ไม่ถูกบันทึกลงตัวนับ `DocCounters` ในเครื่อง ตัวนับในเครื่องจึงไม่รู้เลขสูงสุดที่ใช้ไปแล้วจริง **วิธีแก้** บันทึกเลขที่เซิร์ฟเวอร์ออกผ่าน `DocNumberService.commitServerIssued` ทั้งในคำตอบออนไลน์ (PR #491, #492) และในการเล่นซ้ำของ `/sync/push` (PR #494) **บทเรียน** เมื่อมีผู้ออกเลขสองฝ่าย ทุกเลขที่ฝ่ายหนึ่งออกต้องไหลกลับไปยังอีกฝ่าย กรณีนี้ยังเผยปัญหาด้านกระบวนการในหัวข้อการควบคุมการรวมโค้ดด้านล่าง

### การควบคุมการรวมโค้ดและหลักฐาน

**ปัญหา** พบสามกรณี กรณีแรก ครึ่งหนึ่งของการแก้ #489 (การบันทึกเลขเมื่อ `/sync/push` เล่นซ้ำ) ไม่เข้า `main` ทั้งที่ PR #491 และ #492 รวมแล้ว และคอมมิตแก้ตามการทบทวนของ PR #486 ก็หายในลักษณะเดียวกัน กรณีที่สอง ลิงก์ PR ที่ GitHub แสดงบนตั๋วงานให้ข้อสรุปผิดว่าบางตั๋วไม่มีงานส่งมอบ และตั๋ว #184 ถูกปิดและเปิดใหม่สามครั้ง ทั้งที่เกณฑ์ด้านการวัด latency และหน่วยความจำของตั๋วไม่เคยมีผลวัด กรณีที่สาม สองสาขาที่ไม่มี PR เก็บสำเนาเดียวของเอกสารวิจัย (424 บรรทัด) ขณะกำลังจะถูกลบพร้อมสาขาเก่า 44 สาขาเมื่อ 22 กันยายน พ.ศ. 2569 **สาเหตุ** คอมมิตถูก push หลังกดรวม PR แล้ว [2] GitHub ไม่ผูก PR ที่ไม่มีคำหลักปิดตั๋วหรือมีคำหลักเฉพาะในชื่อ PR (93 จาก 201 PR ที่รวมแล้ว ณ 22 กันยายน) และการตัดสินว่าสาขารวมแล้วจากชื่อสาขาเป็นการเดา **วิธีแก้** cherry-pick คอมมิตที่ตกหล่นไปยัง PR #494 กู้การแก้ของ PR #486 ด้วย PR #521 ตรวจงานส่งมอบด้วย `git log --all --grep` และตัวทดสอบเอง และรวมเอกสารวิจัยผ่าน PR #386 ก่อนลบ โดยตรวจทุกสาขาด้วย `git merge-base --is-ancestor` **บทเรียน** ก่อนรวมต้องตรวจว่า head SHA ของ PR ตรงกับที่ทบทวน สถานะของตั๋วไม่ใช่หลักฐาน (การนับเกณฑ์ตรวจรับในรายงานนี้จึงอ้างไฟล์ทดสอบ) และการลบที่ย้อนกลับไม่ได้ต้องพิสูจน์ก่อนว่ารวมแล้ว

### การทดสอบที่ผูกกับเดือนปัจจุบัน (#525)

**ปัญหา** เมื่อขึ้นเดือนใหม่ `main` กลายเป็นสีแดง ซึ่งทำให้ไม่มีอิมเมจบน GHCR และทุกการรัน deploy ถูกข้าม **สาเหตุ** ไฟล์ `sync-push.e2e-spec.ts` ฝังเลขที่ใบเสร็จของเดือนกันยายนไว้ตายตัว แต่เซิร์ฟเวอร์ประทับวันที่ตามเวลาจริง เมื่อเดือนเปลี่ยน เซิร์ฟเวอร์จึงตั้งธงวันที่ผิดปกติตามสเปก **วิธีแก้** PR #525 คำนวณงวดของเลขเอกสารจากเวลาปัจจุบันในเขตเวลา `Asia/Bangkok` **บทเรียน** การทดสอบที่พึ่งเวลาต้องอ้างเวลาเดียวกับระบบที่ทดสอบ และสีแดงของ `main` ปิดกั้นการส่งมอบทั้งสาย ไม่ใช่แค่เรื่องของการทดสอบ

### ค่า 0 เป็นเท็จในนิพจน์ของ GitHub Actions

**ปัญหา** เงื่อนไขข้ามการทดสอบเมื่อ push เป็นเอกสารล้วนไม่เคยทำงาน **สาเหตุ** ในนิพจน์ของ GitHub Actions [3] ตัวเลข `0` เป็นเท็จ นิพจน์รูปแบบ `cond && 0 || 1` จึงได้ `1` เสมอ ทำให้ขั้นตอน checkout ดึงประวัติเพียงคอมมิตเดียว ขั้นจำแนกประเภทของ push จึงมองไม่เห็นคอมมิตก่อนหน้า **วิธีแก้** ใช้สตริง `'0'` และ `'1'` แทนตัวเลข (PR #548 รวมเมื่อ 1 ตุลาคม พ.ศ. 2569) **บทเรียน** ชนิดข้อมูลในภาษานิพจน์ของเครื่องมือ CI ทำงานต่างจากภาษาโปรแกรมทั่วไป และการข้ามการทดสอบแบบเงียบต้องมีหลักฐานจากการรันที่สังเกตได้ว่าเงื่อนไขทำงานจริง

## งานที่จะดำเนินการต่อไป

1. **การสาธิตครบวงจรบน `mob04` (#344)** รันตามรายการตรวจ `docs/handoff_log/demo-344-checklist-2026-09-30.md` โดยต้องจัดการข้อติดขัดที่ระบุไว้ก่อน ได้แก่ รหัสผ่านชั่วคราวของเจ้าของร้านที่ต้องตั้งรหัสใหม่ภายใน 10 นาทีหลังเข้าสู่ระบบครั้งแรก ร้านใหม่ที่ยังไม่มีสินค้า การที่แอปยังส่ง `Idempotency-Key` เดิมซ้ำไม่ได้ และเกณฑ์ย่อยสามข้อที่พิสูจน์บน VM ไม่ได้ (ตั๋ว #476 ที่เคยเป็นข้อติดขัดปิดแล้วเมื่อ 3 ตุลาคม พ.ศ. 2569) นอกจากนี้ยังไม่มีผู้ดูแลแพลตฟอร์มคนใดเข้าสู่ระบบ `platform-ui` จริง
