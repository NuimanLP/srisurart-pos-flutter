# ADR-0007 — เลขเอกสารแบบเรียงต่อเครื่อง รีเซ็ตรายเดือน

* **สถานะ:** Accepted — 2026-09-04
  ⚠️ **ต้องให้เจ้าของร้านเห็นตัวอย่างใบเสร็จจริงก่อนพิมพ์ใบแรก** — ADR นี้ปลดล็อกให้เริ่ม
  implement ได้ แต่ไม่ได้แทนการยืนยันหน้าตาใบเสร็จ
* **ปิดข้อค้าง:** `00_INDEX.md` "ตัดสินใจแทนไม่ได้" ข้อ 1 / `04_QA_SCRUTINY.md` ข้อ 1
* **เกี่ยวข้อง:** `01_DATABASE.md §7.2`, ADR-0004 (device roles), `CONTRACT.md §7` (`docNo()`)

## การตัดสินใจ

เปลี่ยนจาก `docNo(prefix)` แบบสุ่ม (`RC12345678ABCD`) เป็น **เลขเรียงต่อเครื่อง รีเซ็ตรายเดือน**

```
RC01-2569-08-0042
│ │  │       │
│ │  │       └── ลำดับในเดือนนั้นของเครื่องนั้น 4 หลัก (0001..9999)
│ │  └────────── พ.ศ.-เดือน  = doc_counters.period
│ └───────────── device_no ซีโร่แพด 2 หลัก
└─────────────── prefix ตาม doc_type: RC ใบเสร็จ / CN ใบลดหนี้ / PO ใบสั่งซื้อ / QT ใบเสนอราคา
                / **CP ใบรับชำระเครดิตช่าง** (เพิ่ม 2026-09-04 — ฉบับแรกตกไป ทั้งที่
                `mechanics_repository.dart` ใช้ `docNo('CP')` และ `credit_payments.receipt_no` มี UNIQUE)
```

### ⚠️ แก้จากตัวอย่างในเอกสารเดิม: `device_no` ต้องซีโร่แพด 2 หลัก

`01_DATABASE.md §7.2` เขียนตัวอย่างเป็น `RC1-2569-08-0042` — **ใช้ไม่ได้** เพราะ
`devices.device_no` เป็น 1..99 ถ้าไม่แพด เครื่องที่ 1 กับเครื่องที่ 12 จะอ่านกำกวม
(`RC1-` กับ `RC12-` ต่างกันแค่ตัวคั่น พาร์สย้อนกลับพลาดง่าย) → ใช้ `RC01`, `RC12` เสมอ

## ใครออกเลข — แก้ 2026-09-04 (scrutinize รอบ 3): แยกตามเฟสและตามบทบาทเครื่อง

ฉบับแรกเขียนว่า *"เครื่องเป็นคนออกเลข server ไม่ออกให้"* กับทุก doc type ทุกเฟส ด้วยเหตุผลว่า
"ถ้า server ออก = ออฟไลน์ออกบิลไม่ได้" — เหตุผลนี้**จริงเฉพาะเครื่อง `pos` ในเฟส 2** เท่านั้น
เฟส 1 ออนไลน์ล้วน และเครื่อง `backoffice` ออนไลน์เสมอทุกเฟส (ADR-0004) การให้เครื่องพวกนั้น
ออกเลขเองคือจ่ายค่า seed/retry โดยไม่ได้อะไรกลับมา และทำให้ PO/QT ของ `backoffice` seed ไม่ได้
(`GET /doc-counters` เป็น `pos` เท่านั้น) กับ CP ไม่มี counter เลย

| | RC / CN (เครื่อง `pos`) | PO / QT / CP (ทุกเครื่อง) |
|---|---|---|
| **เฟส 1** (ออนไลน์ล้วน) | **server ออก** — `UPDATE doc_counters … RETURNING` ใต้ row lock ใน transaction เดียวกับ `POST /sales` ใช้ `device_no` ของ `did` ใน JWT → ได้ series เดียวกับที่เครื่องจะออกเองในเฟส 2 | **server ออก** |
| **เฟส 2** (มี offline shell) | **เครื่อง `pos` ออกเอง** จาก counter ใน Drift ต่อ `(device_no, doc_type, period)` server ยังเก็บ high-water mark + `UNIQUE` | **server ออกตลอดไป** — เครื่องเหล่านี้เขียนออฟไลน์ไม่ได้อยู่แล้ว (ADR-0004) |

* client ในเฟส 1 **ไม่ส่ง `receiptNo` มาใน body** — server คืนให้ใน 201 (`02_API_SCREENS.md §3.1`)
  เฟส 2 เครื่อง `pos` ส่งมาได้ และ server ตรวจว่า prefix/`device_no` ตรงกับ `did` ของ token
* `GET /doc-counters` และเส้นทาง "ชน UNIQUE แล้วขยับเลข" **เลื่อนไปเฟส 2** ไม่อยู่ใน critical path
  ของเฟส 1 และไม่อยู่ในเป้า k6
* โค้ดฝั่ง server ที่ออกเลขในเฟส 1 **ไม่ใช่งานทิ้ง** — เฟส 2 ยังใช้ตัวเดียวกันออก PO/QT/CP ต่อ
* ✅ **สอดคล้องกับ ADR-0004** — series `RC{device_no}` ผูกกับเครื่อง `pos` เครื่องเดียว และเครื่อง
  แทนที่ได้ `device_no` ใหม่ ไม่ใช้เลขเดิมซ้ำ → ชุดเลขไม่มีวันชนกัน
* รูปแบบเลขไม่เปลี่ยนระหว่างเฟส — ร้านเห็นใบเสร็จหน้าตาเดียวตั้งแต่วันแรก

## 🔴 ช่องพังที่ต้องปิดก่อนเฟส 2: counter ในเครื่องหายได้

แอปรันบน **Flutter Web** — Drift เก็บใน IndexedDB/OPFS ซึ่ง **ผู้ใช้หรือเบราว์เซอร์ล้างได้**
(ล้างข้อมูลเว็บไซต์, เปลี่ยนเบราว์เซอร์, โหมดส่วนตัว, ลง Windows ใหม่)

ถ้า counter รีเซ็ตเป็น 0 → เลขที่ออกใหม่จะ**ชนกับใบเสร็จเดิมทั้งเดือน** →
`UNIQUE (tenant_id, receipt_no)` เด้งทุกบิล → **ขายไม่ได้เลยจนกว่าจะมีคนแก้ให้**

> **แก้ความเข้าใจ (2026-09-04):** ฉบับแรกคิดว่า "seed counter กลับจาก server" แก้เคสนี้ได้
> แต่ device token (ADR-0004 "การผูกเครื่อง") อยู่ใน IndexedDB ก้อนเดียวกับ counter —
> **ล้าง IndexedDB = เครื่องนั้นหายไปทั้งเครื่อง ไม่ใช่แค่ counter หาย** ร้านต้อง enrol ใหม่และได้
> `device_no` ใหม่ ซึ่งชุดเลขไม่ชนกับของเก่าโดยธรรมชาติ seed จึงกลายเป็นตาข่ายรอง ไม่ใช่ทางหลัก

**ในเฟส 2 ต้องมี 3 อย่างนี้ ไม่ใช่ทางเลือก:**

1. **seed counter จาก server ทุกครั้งที่เปิดแอป/ล็อกอิน** — `GET /doc-counters` คืน high-water
   mark ของ `(device_id, doc_type, period)` แล้วตั้ง `local = max(local, server)`
   (ครอบเคส counter เพี้ยนโดยที่ device token ยังอยู่ เช่น restore Drift จากไฟล์เก่า)
2. **ห้ามออกเลขออฟไลน์ถ้า period ปัจจุบันยังไม่เคยได้ seed จาก server** — เครื่องที่เพิ่ง enrol
   หรือเพิ่งขึ้นเดือนใหม่ตอนเน็ตล่ม ให้ปฏิเสธด้วย `OFFLINE_NOT_ALLOWED` แทนที่จะออกเลขที่อาจชน
3. **ใบเสร็จที่พิมพ์ไปแล้วห้ามเปลี่ยนเลข** — "ชน UNIQUE แล้วขยับเลขแล้วลองใหม่" ใช้ได้เฉพาะ**ก่อน**
   server ตอบ 201 (ออนไลน์) ถ้าบิลออฟไลน์ที่พิมพ์แล้วมาชนตอน `POST /sync/push` server ต้องตอบ
   `rejected` + code `RECEIPT_NO_CONFLICT` แล้วบิลนั้นเข้าคิว reconciliation ให้เจ้าของร้านเคลียร์
   (งาน `q3`) เพราะเลขบนกระดาษที่ลูกค้าถือไปแล้วคือเอกสารทางบัญชี

## ผลที่ตามมา

* `GET /doc-counters` อยู่ใน API catalogue แล้ว (`02_API_SCREENS.md §4`) — **ติดป้ายเฟส 2**
* `doc_counters.doc_type` ต้องรับ `'cp'` เพิ่ม (`01_DATABASE.md §5`) — แก้แล้ว
* `02_API_SCREENS.md §8` ต้องมี `409 RECEIPT_NO_CONFLICT` (เดิมโผล่แค่ใน §3.1) — แก้แล้ว
* **ห้ามแก้เลขของบิลเก่า** — บิลที่ import มาจากแอปเดิมยังเป็น `RC12345678ABCD` ต่อไป
  ทั้งสองรูปแบบอยู่ร่วมกันได้ เพราะ `UNIQUE (tenant_id, receipt_no)` ไม่สนรูปแบบ
  → ต้องบอกร้านว่า "บิลก่อนวันขึ้นระบบเป็นเลขแบบเก่า" ไม่ใช่บั๊ก
* **ตรวจเลขขาดช่วงได้แล้ว** — high-water mark เทียบกับจำนวนบิลจริงในเดือนนั้น
  ช่องว่าง = บิลหาย/เครื่องพัง ควรทำเป็นรายงานให้ owner เห็น (ของใหม่ที่แอปเดิมไม่มี)
* 4 หลัก = 9,999 บิล/เดือน/เครื่อง — เกินพอ แต่ต้องมี guard ว่าถ้าเกินให้ error ชัด ๆ ไม่ใช่วนกลับ 0001
* `CONTRACT.md §7` (`docNo()`) ต้องอัปเดต — ปัจจุบันผูกรูปแบบเดิมไว้เป็นสเปค
