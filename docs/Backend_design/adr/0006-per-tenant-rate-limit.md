# ADR-0006 — จำกัดอัตราต่อ tenant ที่ NestJS guard + Redis (ไม่ใช่ที่ Nginx)

* **สถานะ:** Accepted — 2026-09-04 (จุดบังคับต่างจากที่เลือกไว้ตอนแรก — เหตุผลด้านล่าง)
* **ผู้ตัดสิน:** เจ้าของโปรเจกต์ (เลือก "rate limit ต่อ tenant") + แก้จุดบังคับตามข้อจำกัดทางเทคนิค
* **เกี่ยวข้อง:** `03_ARCHITECTURE.md §5` (ตาราง T1 แถว noisy neighbor), `§8` (หมายเหตุ Nginx ฟรี)

## บริบท

ตารางเปรียบเทียบ multi-tenant ระบุข้อเสียของ T1 ไว้เองว่า **"noisy neighbor — ร้านใหญ่
ทำร้านเล็กช้าได้"** แต่ทั้งเอกสารไม่มีมาตรการรองรับสักข้อ

## การตัดสินใจ — บังคับ 2 ชั้น คนละหน้าที่

| ชั้น | ที่ไหน | key | กันอะไร |
|---|---|---|---|
| นอก (หยาบ) | Nginx `limit_req_zone` | **IP** | flood จากภายนอก, request ที่ยังไม่ผ่าน auth |
| ใน (แม่น) | NestJS guard + Redis | **`tenant_id`** | ร้านเดียวกินทรัพยากรจนร้านอื่นช้า |

* Redis key ตามกติกาเดิมของระบบ: **`t:{tid}:rl:{route}:{window}`** (`03_ARCHITECTURE.md §5` ข้อ 4)
* เกินโควตา → `429` + header `Retry-After`
* **ยกเว้น `/health/live` และ `/health/ready`** — ไม่งั้น LB จะเข้าใจว่า instance ตาย

## เหตุผล — ทำไมไม่ทำที่ Nginx อย่างที่ตั้งใจไว้ตอนแรก

**Nginx ตัวฟรีอ่าน JWT ไม่ได้** (`auth_jwt` เป็นฟีเจอร์ของ NGINX Plus) → Nginx ไม่มีทางรู้ว่า
request นี้เป็นของ tenant ไหน จะ key `limit_req_zone` ต่อ tenant จึงทำไม่ได้จริง

ทางเลือกที่พอทำได้แต่ **ไม่ควรทำ**: ให้ client ส่ง `X-Tenant-Id` มาใน header แล้วให้ Nginx
key จาก header นั้น — **ผิดกติกาข้อ 1 ของ multi-tenant ที่เอกสารตั้งไว้เอง**
(*"`tenant_id` มาจาก JWT เท่านั้น ห้ามมาจาก request"*) และเปิดช่องให้ปลอม header
เพื่อกินโควตาของร้านอื่น

เป็นข้อจำกัดชนิดเดียวกับที่เอกสารเตือนไว้แล้วว่า *"Nginx ฟรีมีแค่ passive health check"*

## ผลที่ตามมา

* 🔴 **ต้องปิดหรือขยาย limit ให้ tenant ที่ใช้ทำ k6 load test** ไม่งั้นผลการทดสอบจะกลายเป็น
  **การวัด rate limiter ของตัวเอง ไม่ใช่การวัดระบบ** — ทำให้ตัวเลขที่ส่งอาจารย์ไม่มีความหมาย
  → เก็บ limit ไว้ใน config ต่อ tenant (คอลัมน์ `tenants.plan` ที่มีอยู่แล้วแต่ยังไม่มีใครใช้
  เป็นที่เก็บที่เหมาะที่สุด: `basic` = โควตาปกติ, `loadtest` = ไม่จำกัด)
* Redis ที่ใช้ต้องเป็น **`redis-cache`** (`allkeys-lru`) ไม่ใช่ `redis-queue` — ตัวนับหายได้ ไม่เสียหาย
* ถ้า Redis ล่ม guard ต้อง **ปล่อยผ่าน (fail-open)** ไม่ใช่บล็อกทั้งระบบ — POS หยุดขายไม่ได้
* ได้ metric ต่อ tenant มาฟรี ใช้ตอบคำถาม "ร้านไหนหนัก" ตอน tuning

## ยังไม่เคาะ

* [ ] ตัวเลขโควตาจริง (req/นาที ต่อ tenant) — ต้องดูจากผล k6 ก่อน ตั้งมั่วตอนนี้ไม่มีความหมาย
* [ ] แยกโควตาตามชนิด endpoint ไหม (เช่น `POST /sales` ใจกว้าง แต่ `/tenant/export` เข้มมาก)
