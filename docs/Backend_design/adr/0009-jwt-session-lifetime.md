# ADR-0009 — ล็อกอินใหม่ทุกวัน: access 15 นาที + refresh หมดอายุตี 4

* **สถานะ:** Accepted — 2026-09-04
* **ผู้ตัดสิน:** เจ้าของโปรเจกต์
* **ปิดข้อค้าง:** `03_ARCHITECTURE.md §8` — *"JWT ต้องระบุ TTL + revoke ให้ชัด … ข้อเสนอ: access 15 นาที + refresh rotation"* (เป็นแค่ข้อเสนอ ไม่เคยมีใครเคาะ)
* **เกี่ยวข้อง:** ADR-0003 (tenant status), ADR-0004 (device roles), assignment ของอาจารย์ (JWT stateless ห้าม in-memory session)

## บริบท

เอกสารมี `/auth/token` และ `/auth/refresh` แต่ **ไม่เคยบอกอายุ token** และ §8 เขียนไว้เองว่า
"ข้อเสนอ" — ทั้งที่เป็นข้อที่อาจารย์ตรวจ และเป็นเรื่องความปลอดภัยจริงของร้าน
(ไล่พนักงานออกแล้ว token ต้องใช้ไม่ได้ — JWT เปล่า ๆ revoke ไม่ได้)

ข้อเสนอเดิมคือ refresh อายุยาว (30 วัน) + rotation เก็บใน Redis ซึ่งเป็นแพตเทิร์นเว็บทั่วไป
**แต่ไม่ได้ดูบริบทร้าน**

## การตัดสินใจ

| | อายุ |
|---|---|
| access token | **15 นาที** |
| refresh token | **หมดอายุเวลา 04:00 ของทุกวัน** (ไม่ใช่ "24 ชม. นับจากล็อกอิน") |

→ พนักงาน **ล็อกอินใหม่ทุกเช้าตอนเปิดร้าน**

## เหตุผล

1. **ร้านมีพิธีกรรมรายวันอยู่แล้ว** — เปิดกะ/ปิดกะ (`shifts`) "เปิดร้าน = ล็อกอิน" ไม่ใช่ภาระใหม่
   มันทับกับสิ่งที่ทำอยู่ทุกเช้าพอดี ต่างจาก session 30 วันที่ไม่ตรงกับจังหวะอะไรเลย
2. **เครื่องหน้าเคาน์เตอร์เป็นเครื่องสาธารณะ** ใครเดินมาก็กดได้ — ค้าง session ไว้ 30 วัน
   คือความเสี่ยงจริง ไม่ใช่ทฤษฎี
3. **revoke ง่ายลงมาก และไม่ต้องมี state เพิ่ม** — ปิด `users.is_active` แล้วรอ ≤15 นาที
   ต่อ refresh ไม่ผ่านเพราะ endpoint เช็ค `users.is_active` + `tenants.status` (ADR-0003)
   ในฐานข้อมูล → **ไม่ต้องมี denylist ใน Redis เลย** ยังตรงข้อ "JWT stateless" ของอาจารย์

### ⚠️ ทำไมต้อง "ตี 4" ไม่ใช่ "24 ชั่วโมงนับจากล็อกอิน"

แบบนับ 24 ชม. → พนักงานล็อกอินบ่ายวันจันทร์ token จะหมดอายุ **บ่ายวันอังคาร กลางที่ลูกค้ายืนรอ**
แบบตี 4 → หมดอายุนอกเวลาทำการ **ตราบใดที่ร้านไม่เปิดตอนตี 4** ต้นทุนเท่ากัน แต่เจ็บน้อยกว่าคนละเรื่อง

> ⚠️ **สมมติฐานที่ยังไม่มีเอกสารไหนยืนยัน (scrutinize 2026-09-04):** "ไม่มีวันเด้งกลางบิล" ตั้งอยู่บน
> เวลาเปิดร้านที่ไม่มีใครจดไว้ ถ้ากะที่เปิดก่อนเที่ยงคืนยังเปิดอยู่ตอน 04:15 (ตลาดนัดกลางคืน/เทศกาล)
> จะโดนล็อกอินใหม่กลางกะ และคนที่ล็อกอิน 03:55 จะได้ refresh token อายุ 5 นาที
> → เพิ่มกติกา: **refresh ที่ออกหลัง 03:00 ให้หมดอายุตี 4 ของวันถัดไป** (กัน token อายุไม่กี่นาที)
> และถามร้านตามหัวข้อ "ยังไม่เคาะ"
> "ตี 4" คิดตาม **`tenants.timezone`** (ADR-0003) เสมอ ไม่ hardcode เวลาไทย

## 🔴 ข้อขัดแย้งที่ต้องแก้ก่อนเฟส 2 (บันทึกไว้ตั้งแต่ตอนนี้ อย่าไปเจอเอาตอนนั้น)

**ถ้า token ตายตอนกลางคืน แล้วเช้ามาเน็ตล่ม เครื่องจะล็อกอินไม่ได้ = เปิดร้านไม่ได้เลย**
ซึ่ง **ล้มเจตนาทั้งหมดของการออกแบบ offline** — เราอุตส่าห์ทำให้ขายออฟไลน์ได้ แต่ดันเข้าระบบไม่ได้ตั้งแต่แรก

* **เฟส 1 ไม่เจอปัญหานี้** — ออนไลน์อย่างเดียว และไม่ cutover ร้าน (`03_ARCHITECTURE.md §7`)
  ถ้าเน็ตล่มก็ใช้ระบบไม่ได้อยู่แล้ว การล็อกอินไม่ได้จึงไม่ได้ทำให้แย่ลง
* **เฟส 2 ต้องแก้** — เครื่อง `role='pos'` (ADR-0004) ต้องยืนยันตัวตนตอนเปิดกะได้**โดยไม่ต้องมีเน็ต**
  ทางที่มีอยู่แล้วในระบบ: `users.pin_hash` (ตอนนี้ใช้เป็น manager PIN สำหรับงานเสี่ยง)
  → เก็บ hash ไว้ในเครื่องตอนซิงก์ แล้วให้เปิดกะออฟไลน์ด้วย PIN ได้ ค่อยไปต่อ token จริงตอนเน็ตกลับมา

## ผลที่ตามมา

* `02_API_SCREENS.md §1.1` ต้องระบุอายุ token ทั้งสองตัวให้ชัด ไม่ใช่ปล่อยว่าง
* `/auth/refresh` **ต้องเช็คทั้ง `users.is_active`, `tenants.status` และ `devices.retired_at` ของ
  `did` ใน token** ทุกครั้ง (ไม่ใช่แค่ตรวจลายเซ็น) — ข้อสุดท้ายเพิ่ม 2026-09-04: ถ้าไม่เช็ค
  เครื่อง `pos` ที่ owner กด "ย้ายเครื่องขาย" (ADR-0004) จะยังต่อ token ที่มี `drole='pos'` ได้
  จนถึงตี 4 = ร้านมีเครื่องขาย 2 เครื่องทั้งวันโดยที่ `one_pos_per_tenant` ช่วยอะไรไม่ได้
  ช่องที่เหลือหลังแก้คือ ≤15 นาที (อายุ access token) เท่ากับกรณีปิด `users.is_active`
* ไม่ต้องทำ refresh-token rotation + Redis denylist ตามข้อเสนอเดิม — **ตัดงานออกไปหนึ่งก้อน**
* ต้องมีข้อความไทยตอน session หมดอายุ — 🔴 **ห้ามแต่งเอง** (กติกา `02_API_SCREENS.md §8.1`)
