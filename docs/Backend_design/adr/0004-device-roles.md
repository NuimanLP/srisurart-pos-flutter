# ADR-0004 — บทบาทของเครื่อง: 1 เครื่อง `pos` ต่อร้าน + เครื่อง `backoffice` กี่เครื่องก็ได้

* **สถานะ:** Accepted — 2026-09-04 (รายการ endpoint ที่จำกัดเฉพาะ `pos` รอยืนยัน)
* **ผู้ตัดสิน:** เจ้าของโปรเจกต์
* **แทนที่:** ข้อความ "ร้านมีเครื่องเดียว → conflict เป็นไปไม่ได้ทางโครงสร้าง"
  ใน `03_ARCHITECTURE.md §7` (เหตุผลผิด — ดูด้านล่าง)
* **เกี่ยวข้อง:** `01_DATABASE.md §7.2` (doc_counters), `§7.5` (shifts), `03_ARCHITECTURE.md §5`

## บริบท — เอกสารเดิมขัดกันเอง 2 ชั้น

**ชั้นที่ 1 — schema ขัดกับข้อสรุป:**
`03_ARCHITECTURE.md §5, §7` เถียงจากสมมติฐาน *"1 ร้าน = 1 เครื่อง POS"* แต่ DDL ใน
`01_DATABASE.md` **ออกแบบเผื่อหลายเครื่องไว้แล้ว**:

* `devices.device_no SMALLINT` (1..99) + `UNIQUE (tenant_id, device_no)`
* `doc_counters` มี `device_id` ใน PK พร้อมคอมเมนต์ *"⭐ ขาดไม่ได้ ไม่งั้นสองเครื่องเขียนทับกัน"*

**ชั้นที่ 2 — เหตุผลที่ยกมาไม่ถูก:**
เอกสารอ้างว่าต้องมีเครื่องเดียวเพราะ *"conflict ของสต็อกเป็นไปไม่ได้ทางโครงสร้าง"*
ข้อนี้**ไม่จริงและไม่จำเป็น** — ในโหมดออนไลน์ server เป็นเจ้าของสต็อก ตัดในทรานแซกชัน
พร้อม row lock อยู่แล้ว ยิ่งกว่านั้น สมมติฐานนี้ไม่มีอะไรบังคับเลย — แอปเป็น Flutter Web
เปิดแท็บที่สองก็พังแล้ว

> ⚠️ **แก้หลักฐาน (scrutinize 2026-09-04):** ฉบับแรกอ้างเกณฑ์ *"ยิง `POST /sales` พร้อมกัน 200 ครั้ง
> → ได้ 50 บิลพอดี"* เป็นข้อพิสูจน์ว่าหลายเครื่องปลอดภัย แต่ ADR นี้เองจำกัด `POST /sales` ให้เครื่อง
> `pos` เครื่องเดียว การแข่งกันที่**มีอยู่จริง**หลังตัดสินใจคือ **`pos` ขาย กับ `backoffice`
> รับของเข้า (`/purchase-orders/:id/receive`) หรือปรับสต็อก (`/adjust-stock`) บนสินค้าแถวเดียวกัน**
> → เพิ่มเคสนี้ลง DoD ใน `03_ARCHITECTURE.md §8` แล้ว เกณฑ์ 200 ครั้งยังมีประโยชน์ในฐานะ
> เทสต์ row lock แต่ไม่ใช่ข้อพิสูจน์เรื่องหลายเครื่อง

## การตัดสินใจ

เลิกนับ "จำนวนเครื่อง" เปลี่ยนเป็น **บทบาทของเครื่อง**

```sql
ALTER TABLE devices
  ADD COLUMN role       TEXT NOT NULL DEFAULT 'backoffice'
       CHECK (role IN ('pos','backoffice')),
  ADD COLUMN retired_at TIMESTAMPTZ;

-- ร้านหนึ่งมีเครื่องขายที่ยังใช้งานอยู่ได้ "ไม่เกิน 1 เครื่อง" — บังคับที่ฐานข้อมูล
CREATE UNIQUE INDEX one_pos_per_tenant ON devices (tenant_id)
  WHERE role = 'pos' AND retired_at IS NULL;
```

* JWT พก `did` (device id) + `drole` เพิ่มจาก `tid` — **ที่มาของสองค่านี้อยู่ในหัวข้อ
  "การผูกเครื่อง" ด้านล่าง** (ฉบับแรกประกาศ claim ไว้แต่ไม่มี endpoint ไหนสร้างมันได้)
* guard ตรวจ `drole` ต่อ endpoint ตามตารางด้านล่าง

### การผูกเครื่อง (device binding) — เพิ่ม 2026-09-04 หลัง scrutinize

**ปัญหาที่พบ:** ฉบับแรกของ ADR นี้ (และ ADR-0007 / 0009 ที่พึ่งมัน) สมมติว่ามี "เครื่อง" ที่ server
รู้จัก แต่ `POST /auth/token` รับแค่ user/password, ไม่มี endpoint ลงทะเบียน/ปลดเครื่อง,
`devices.id` เป็น client-generated → เครื่อง `backoffice` ส่ง id ของเครื่อง `pos` มาก็กลายเป็น
`pos` ได้ และบน Flutter Web "เครื่อง" คือ browser profile ซึ่งอยู่ใน IndexedDB ก้อนเดียวกับ
counter ที่ ADR-0007 บอกว่าผู้ใช้ล้างได้

**การตัดสินใจ:** เครื่อง = **device token** ที่ owner ออกให้ browser นั้นครั้งเดียว

| ขั้น | ใคร | endpoint | ผล |
|---|---|---|---|
| 1. สร้างเครื่อง | `owner` (หน้า Settings) | `POST /devices` `{label, role}` | server กำหนด `device_no` ถัดไปที่ยังไม่เคยใช้ (**ห้ามใช้ซ้ำแม้เครื่องนั้น retire แล้ว**) คืน **enrolment code ใช้ครั้งเดียว** อายุสั้น |
| 2. ผูก browser | คนที่เครื่องนั้น | `POST /auth/device` `{code}` | คืน **device token** ยาว (opaque, เก็บ `devices.token_hash` ฝั่ง server) เครื่องเก็บใน localStorage/IndexedDB |
| 3. ล็อกอินประจำวัน | พนักงาน | `POST /auth/token` `{username, password, deviceToken?}` | server แปลง `deviceToken` → `did`/`drole` ใส่ JWT เอง **ไม่รับ `deviceId` จาก body เด็ดขาด** ไม่มี token = ไม่มี `drole` = เรียกได้เฉพาะแถว "ทั้งคู่" ในฐานะ `backoffice` |
| 4. ดู/ถอน | `owner` | `GET /devices` · `POST /devices/{id}/retire` | ตั้ง `retired_at` + `audit_log` — นี่คือปุ่ม **"ย้ายเครื่องขาย"** ที่ ADR นี้สัญญาไว้ |

กติกา:

* **`did` มาจาก device token ที่ server ตรวจแล้วเท่านั้น** — เหตุผลเดียวกับ `tid` (ห้ามรับจาก request)
* ล้าง IndexedDB = device token หาย = **ต้องให้ owner ออก enrolment code ใหม่** (ขั้น 1–2 ซ้ำ ได้
  `device_no` ใหม่) ไม่ใช่การเสียข้อมูล และชุดเลขใบเสร็จของ `device_no` เก่าปิดตัวไปโดยไม่ชนกับใคร
  → **นี่คือคำตอบของ ADR-0007 เรื่อง "counter ในเครื่องหาย"** ที่แท้จริง: ไม่ใช่ seed กลับ แต่เป็นเครื่องใหม่
* `/auth/refresh` ต้องเช็ค `devices.retired_at` ของ `did` ใน token ทุกครั้ง (ADR-0009 แก้ตามแล้ว)
  ไม่งั้นเครื่องที่ retire แล้วยังเป็น `pos` ต่อจนถึงตี 4
* **ย้ายเครื่องขายกลางกะ:** `uq_shift_active` ผูกกับ `(tenant_id, device_id)` เครื่องใหม่จึงเปิดกะ
  ที่สองของวันเดียวกันได้ = ลิ้นชักใบเดียวมีสองกะ **ขั้นตอน retire ต้องปิดกะที่เปิดอยู่ของเครื่องเก่า
  ก่อนเสมอ** (`POST /shifts/close` ในทรานแซกชันเดียวกับ `retired_at` โดยบันทึก `physical_cash`
  ที่ owner กรอก) แล้วเครื่องใหม่ค่อยเปิดกะใหม่ — ยอมให้วันนั้นมี 2 ใบปิดกะ ดีกว่ามีกะค้างที่ปิดไม่ได้
* enrolment code และ device token **ไม่ใช่ตัวแทนของ user** — token ระบุแค่ "เครื่องนี้คือใคร"
  สิทธิ์ของคนยังมาจาก `users.role` เหมือนเดิม

### เส้นแบ่งคือ "แตะลิ้นชักไหม" ไม่ใช่ "แตะสต็อกไหม"

| ความสามารถ | `pos` | `backoffice` |
|---|---|---|
| ขาย (`POST /sales`) | ✅ | ❌ |
| รับคืน (`POST /returns`) | ✅ | ❌ |
| รับชำระเครดิตช่าง (`credit_payments`) | ✅ | ❌ |
| **เปิด-ปิดกะ + `drawer_entries`** (เขียน) | ✅ | ❌ |
| *อ่าน* กะปัจจุบัน / ประวัติกะ / ใบปิดกะ | ✅ | ✅ **การอ่านไม่แตะลิ้นชัก** |
| พักบิล (parked sales) | ✅ | ❌ |
| ออกเลขใบเสร็จ | ✅ | ❌ |
| รับของเข้า (PO) / แก้สต็อก / นับสต็อก | ✅ | ✅ |
| สินค้า / ลูกค้า / ช่าง / ซัพพลายเออร์ | ✅ | ✅ |
| ใบเสนอราคา (ไม่แตะสต็อกและเงิน) | ✅ | ✅ |
| อ่านทุกอย่าง + รายงาน | ✅ | ✅ |
| **เขียนตอนออฟไลน์ (เฟส 2)** | ✅ | ❌ ออนไลน์เท่านั้น |

## เหตุผล

**ทำไม `pos` ต้องมีเครื่องเดียวจริง ๆ** — ไม่ใช่เรื่องสต็อก แต่เป็นของที่มีอยู่**ชิ้นเดียวทางกายภาพ**:

1. **ลิ้นชักเก็บเงินมีใบเดียว** — `shifts` / `drawer_entries` / ใบปิดกะ ตั้งอยู่บนสมมติฐานนี้ทั้งชุด
   ถ้าสองเครื่องรับเงินสด ตอนปิดกะจะนับเงินไม่ตรง **โดยไม่มีบั๊กสักตัว**
2. **เลขที่ใบเสร็จควรเป็นชุดเดียว** — `doc_counters` แยกตาม `device_no` สองเครื่องขาย =
   สองชุดเลข = บัญชีต้องไล่สองเล่ม

เหตุผลสองข้อนี้ **ไม่หายไปแม้ระบบจะออนไลน์ 100%** ต่างจากเหตุผลเรื่องสต็อกที่หายไปทันที
ที่มี server — จึงเป็นฐานที่มั่นคงกว่าให้ยึด

**ทำไมถึงเปิดให้ `backoffice` แตะสต็อกได้:** รับของเข้าหลังร้านขณะหน้าเคาน์เตอร์ขายอยู่
เป็นเรื่องปกติของร้านอะไหล่ และ Postgres จัดการ concurrency ให้แล้ว การห้ามไว้คือการ
จ่ายค่า UX ทุกวันเพื่อกันความเสี่ยงที่ไม่มีอยู่

## ผลที่ตามมา

* **ได้คำตอบของเฟส 2 มาฟรี** — "ใครเขียน offline ได้" = "เครื่องที่ `role='pos'`"
  ไม่ต้องมีแฟล็กที่สอง ไม่ต้องมี lease **ไม่เพิ่ม state ฝั่ง server เลย** ตรงกับเจตนาเดิม
  ตอนที่ทีมตัดสินใจทิ้งกลไก stock lease
* ต้องแก้ `03_ARCHITECTURE.md §7` — เปลี่ยนจาก "conflict เป็นไปไม่ได้เพราะมีเครื่องเดียว"
  เป็น "conflict เป็นไปไม่ได้ **ตราบใดที่มี offline writer เดียว** ซึ่งบังคับด้วย
  partial unique index `one_pos_per_tenant`"
* ต้องมีฟังก์ชัน **"ย้ายเครื่องขาย"** (เครื่องเดิมพัง/เปลี่ยนเครื่อง) ในหน้า Settings —
  `owner` เท่านั้น + เขียน `audit_log` ขั้นตอน: ปิดกะค้างของเครื่องเดิม → `retired_at` ของเครื่องเดิม
  → สร้างเครื่องใหม่ **ด้วย `device_no` ใหม่ ห้ามใช้เลขเดิมซ้ำ** ไม่งั้นชุดเลขใบเสร็จชนกับของเก่า
  (รายละเอียดในหัวข้อ "การผูกเครื่อง")
* ADR-0001 (provisioning) ต้องสร้าง device แรกเป็น `role='pos'`, `device_no=1` ให้ด้วย
  **พร้อม enrolment code** ที่ส่งให้ร้านคู่กับรหัส owner
* `01_DATABASE.md` เพิ่ม `devices.token_hash TEXT` + `devices.enrol_code_hash` / `enrol_expires_at`
* `02_API_SCREENS.md §4` เพิ่มแถว `/devices/*`, `/auth/device` และ `deviceToken` ใน `POST /auth/token`
  (ทำแล้ว 2026-09-04) และคอลัมน์ "device role ที่เรียกได้" (ทำแล้วรอบก่อน)
