# ADR-0004 — บทบาทของเครื่อง: 1 เครื่อง `pos` ต่อร้าน + เครื่อง `backoffice` กี่เครื่องก็ได้

* **สถานะ:** Accepted — 2026-09-04 (รายการ endpoint ที่จำกัดเฉพาะ `pos` รอยืนยัน)
* **ผู้ตัดสิน:** เจ้าของโปรเจกต์
* **แทนที่:** ข้อความ "ร้านมีเครื่องเดียว → conflict เป็นไปไม่ได้ทางโครงสร้าง"
  ใน `03_ARCHITECTURE.md §7` (เหตุผลผิด — ดูด้านล่าง)
* **เกี่ยวข้อง:** `01_DATABASE.md §7.2` (doc_counters), `§7.5` (shifts), `03_ARCHITECTURE.md §5`

## บริบท — เอกสารเดิมขัดกันเอง 2 ชั้น

**ชั้นที่ 1 — schema ขัดกับข้อสรุป:**
`03_ARCHITECTURE.md §5, §7` เถียงจากสมมติฐาน *"1 ร้าน = 1 เครื่อง POS"* แต่ DDL ใน
`01_DATABASE.md` **ออกแบบเผื่อหลายเครื่องไว้แล้ว**:

* `devices.device_no SMALLINT` (1..99) + `UNIQUE (tenant_id, device_no)`
* `doc_counters` มี `device_id` ใน PK พร้อมคอมเมนต์ *"⭐ ขาดไม่ได้ ไม่งั้นสองเครื่องเขียนทับกัน"*

**ชั้นที่ 2 — เหตุผลที่ยกมาไม่ถูก:**
เอกสารอ้างว่าต้องมีเครื่องเดียวเพราะ *"conflict ของสต็อกเป็นไปไม่ได้ทางโครงสร้าง"*
ข้อนี้**ไม่จริงและไม่จำเป็น** — ในโหมดออนไลน์ server เป็นเจ้าของสต็อก ตัดในทรานแซกชัน
พร้อม row lock อยู่แล้ว และเกณฑ์ปิดเฟส 1 ข้อ *"ยิง POST /sales พร้อมกัน 200 ครั้งบนสินค้า
50 ชิ้น → ได้ 50 บิลพอดี"* **คือการพิสูจน์ว่าหลายเครื่องพร้อมกันปลอดภัย**
ยิ่งกว่านั้น สมมติฐานนี้ไม่มีอะไรบังคับเลย — แอปเป็น Flutter Web เปิดแท็บที่สองก็พังแล้ว

## การตัดสินใจ

เลิกนับ "จำนวนเครื่อง" เปลี่ยนเป็น **บทบาทของเครื่อง**

```sql
ALTER TABLE devices
  ADD COLUMN role       TEXT NOT NULL DEFAULT 'backoffice'
       CHECK (role IN ('pos','backoffice')),
  ADD COLUMN retired_at TIMESTAMPTZ;

-- ร้านหนึ่งมีเครื่องขายที่ยังใช้งานอยู่ได้ "ไม่เกิน 1 เครื่อง" — บังคับที่ฐานข้อมูล
CREATE UNIQUE INDEX one_pos_per_tenant ON devices (tenant_id)
  WHERE role = 'pos' AND retired_at IS NULL;
```

* JWT พก `did` (device id) + `drole` เพิ่มจาก `tid`
* guard ตรวจ `drole` ต่อ endpoint ตามตารางด้านล่าง

### เส้นแบ่งคือ "แตะลิ้นชักไหม" ไม่ใช่ "แตะสต็อกไหม"

| ความสามารถ | `pos` | `backoffice` |
|---|---|---|
| ขาย (`POST /sales`) | ✅ | ❌ |
| รับคืน (`POST /returns`) | ✅ | ❌ |
| รับชำระเครดิตช่าง (`credit_payments`) | ✅ | ❌ |
| **เปิด-ปิดกะ + `drawer_entries`** (เขียน) | ✅ | ❌ |
| *อ่าน* กะปัจจุบัน / ประวัติกะ / ใบปิดกะ | ✅ | ✅ **การอ่านไม่แตะลิ้นชัก** |
| พักบิล (parked sales) | ✅ | ❌ |
| ออกเลขใบเสร็จ | ✅ | ❌ |
| รับของเข้า (PO) / แก้สต็อก / นับสต็อก | ✅ | ✅ |
| สินค้า / ลูกค้า / ช่าง / ซัพพลายเออร์ | ✅ | ✅ |
| ใบเสนอราคา (ไม่แตะสต็อกและเงิน) | ✅ | ✅ |
| อ่านทุกอย่าง + รายงาน | ✅ | ✅ |
| **เขียนตอนออฟไลน์ (เฟส 2)** | ✅ | ❌ ออนไลน์เท่านั้น |

## เหตุผล

**ทำไม `pos` ต้องมีเครื่องเดียวจริง ๆ** — ไม่ใช่เรื่องสต็อก แต่เป็นของที่มีอยู่**ชิ้นเดียวทางกายภาพ**:

1. **ลิ้นชักเก็บเงินมีใบเดียว** — `shifts` / `drawer_entries` / ใบปิดกะ ตั้งอยู่บนสมมติฐานนี้ทั้งชุด
   ถ้าสองเครื่องรับเงินสด ตอนปิดกะจะนับเงินไม่ตรง **โดยไม่มีบั๊กสักตัว**
2. **เลขที่ใบเสร็จควรเป็นชุดเดียว** — `doc_counters` แยกตาม `device_no` สองเครื่องขาย =
   สองชุดเลข = บัญชีต้องไล่สองเล่ม

เหตุผลสองข้อนี้ **ไม่หายไปแม้ระบบจะออนไลน์ 100%** ต่างจากเหตุผลเรื่องสต็อกที่หายไปทันที
ที่มี server — จึงเป็นฐานที่มั่นคงกว่าให้ยึด

**ทำไมถึงเปิดให้ `backoffice` แตะสต็อกได้:** รับของเข้าหลังร้านขณะหน้าเคาน์เตอร์ขายอยู่
เป็นเรื่องปกติของร้านอะไหล่ และ Postgres จัดการ concurrency ให้แล้ว การห้ามไว้คือการ
จ่ายค่า UX ทุกวันเพื่อกันความเสี่ยงที่ไม่มีอยู่

## ผลที่ตามมา

* **ได้คำตอบของเฟส 2 มาฟรี** — "ใครเขียน offline ได้" = "เครื่องที่ `role='pos'`"
  ไม่ต้องมีแฟล็กที่สอง ไม่ต้องมี lease **ไม่เพิ่ม state ฝั่ง server เลย** ตรงกับเจตนาเดิม
  ตอนที่ทีมตัดสินใจทิ้งกลไก stock lease
* ต้องแก้ `03_ARCHITECTURE.md §7` — เปลี่ยนจาก "conflict เป็นไปไม่ได้เพราะมีเครื่องเดียว"
  เป็น "conflict เป็นไปไม่ได้ **ตราบใดที่มี offline writer เดียว** ซึ่งบังคับด้วย
  partial unique index `one_pos_per_tenant`"
* ต้องมีฟังก์ชัน **"ย้ายเครื่องขาย"** (เครื่องเดิมพัง/เปลี่ยนเครื่อง) ในหน้า Settings —
  `owner` เท่านั้น + เขียน `audit_log` ขั้นตอน: `retired_at` ของเครื่องเดิม → สร้างเครื่องใหม่
  **ด้วย `device_no` ใหม่ ห้ามใช้เลขเดิมซ้ำ** ไม่งั้นชุดเลขใบเสร็จชนกับของเก่า
* ADR-0001 (provisioning) ต้องสร้าง device แรกเป็น `role='pos'`, `device_no=1` ให้ด้วย
* `02_API_SCREENS.md §4` ต้องเพิ่มคอลัมน์ "device role ที่เรียกได้" ในตาราง API catalogue
