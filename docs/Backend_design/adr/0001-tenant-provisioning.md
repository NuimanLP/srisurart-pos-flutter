# ADR-0001 — ร้านใหม่เข้าระบบผ่าน platform admin (ไม่มี self-service signup ในเฟส 1)

* **สถานะ:** Accepted — 2026-09-04
* **ผู้ตัดสิน:** เจ้าของโปรเจกต์
* **เกี่ยวข้อง:** `00_INDEX.md` รายการ "ตัดสินใจแทนไม่ได้" ข้อ 5, `02_API_SCREENS.md §4`

## บริบท

เอกสารชุดนี้ออกแบบเป็น multi-tenant (หลายร้าน คนละเจ้าของ) แต่ `02_API_SCREENS.md` มี auth
endpoint แค่ `/auth/token`, `/auth/refresh`, `/auth/me` — **ไม่มี endpoint ไหนสร้าง tenant ได้เลย**
แปลว่าตามเอกสารปัจจุบัน แม้แต่ **tenant สาธิตที่จะใช้ส่งอาจารย์ก็สร้างไม่ได้** ต้องไปแทรก INSERT
ด้วยมือใน psql ซึ่งไม่มีใครเขียนไว้ว่าต้อง insert อะไรบ้าง

## การตัดสินใจ

**platform admin ของทีมเราเป็นคนสร้างร้านใหม่** ผ่าน `POST /platform/tenants`
(+ สคริปต์/CLI ที่ห่อ endpoint เดียวกัน) — **ไม่ทำ self-service signup ในเฟส 1**

การสร้าง 1 ร้าน = **ทรานแซกชันเดียว** ที่ต้องได้ครบทุกอย่าง ไม่งั้นร้านที่สร้างเสร็จจะใช้งานไม่ได้:

1. แถวใน `tenants` (ชื่อร้าน, `status='active'` — ดู ADR-0003)
2. `users` แถวแรก `role='owner'` ผูก `tenant_id` นั้น
3. `settings` 1 แถวของร้านนั้น (เดิมเป็น singleton แถวเดียว → `01_DATABASE.md §5.7`)
4. seed ข้อมูลตั้งต้นที่แอปต้องมีถึงจะเปิดหน้าจอได้ — **เฉพาะ 5 หมวดหมู่** ตามรายการ
   `seedCategories` ใน `database.dart` (`เครื่องยนต์ / ไฟฟ้า / น้ำมัน / เบรก / ตัวถัง`)
   ⚠️ **ไม่เอาสินค้าตัวอย่าง** ที่ `_seed()` ใส่ต่อจากหมวดหมู่ (นั่นคือ demo ของแอป ไม่ใช่ของร้าน)
   และ **ไม่มี "หน่วยนับ"** — ฉบับแรกเขียนไว้ แต่แอปไม่มี entity นี้ (แก้ 2026-09-04)
5. `devices` แถวแรก `role='pos'`, `device_no=1` + **enrolment code** (ADR-0004 "การผูกเครื่อง")
   ส่งให้ร้านคู่กับรหัส owner

ถ้าข้อใดข้อหนึ่งล้ม ต้อง rollback ทั้งหมด — ห้ามมี tenant ที่ไม่มี owner หรือไม่มี settings

## เหตุผล

* จำนวนร้านใน scope นี้น้อย (นักศึกษา + ร้านจริงไม่กี่ร้าน) — signup อัตโนมัติยังไม่คุ้ม
* self-service เปิดโมดูลใหม่ทั้งก้อน: verify email, กัน bot, กัน tenant ขยะ, rate limit ต่อ IP
* ได้ **tenant สาธิตทันที** ซึ่งเป็นสิ่งที่เฟส 1 ต้องใช้ส่งอาจารย์ (`03_ARCHITECTURE.md §7`)

## ผลที่ตามมา

* `POST /platform/tenants` อยู่ใน API catalogue แล้ว (`02_API_SCREENS.md §4.1`)
* **tenant สาธิต/โหลดเทสต์ใช้ `tenants.plan` ตัวเดียว** (เคาะ 2026-09-04) — ฉบับแรกเสนอ
  `is_demo` ส่วน ADR-0006 เสนอ `plan='loadtest'` สำหรับสิ่งเดียวกัน → ยุบเหลือ `plan`:
  `basic` = ร้านจริง, `demo` = ร้านสาธิต (ไม่นับในรายงานระดับแพลตฟอร์ม, โควตาปกติ),
  `loadtest` = ไม่นับ + ไม่จำกัดอัตรา ไม่มี `is_demo`
* endpoint นี้อยู่ใต้ **admin plane** ไม่ใช่ผัง `/auth/*` ปกติ (ดู ADR-0002)
* ต้องมี seed fixture ที่ระบุชัดว่า "ร้านใหม่ได้อะไรมาบ้าง" — ใช้ซ้ำได้ทั้ง test/demo/prod
* ถ้าวันหนึ่งอยากทำ signup เอง โครงนี้ไม่ขวาง: signup แค่เรียก service ตัวเดียวกันหลังผ่าน verify
