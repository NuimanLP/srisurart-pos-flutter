# ADR-0005 — export ข้อมูลรายร้านได้ แต่ไม่รับปาก restore รายร้าน

* **สถานะ:** Accepted — 2026-09-04
* **ผู้ตัดสิน:** เจ้าของโปรเจกต์
* **เกี่ยวข้อง:** ADR-0003 (tenant lifecycle), `01_DATABASE.md §10` (นโยบายการลบ), `03_ARCHITECTURE.md §5`

## บริบท

T1 (shared DB + shared schema) มีข้อเสียที่ตารางเปรียบเทียบระบุไว้เอง:
**"Backup/restore ทีละร้าน — ยาก (ต้อง filter)"** เพราะทุกร้านอยู่ในตารางเดียวกัน
`pg_restore` ทั้ง cluster = ทับข้อมูลของร้านอื่นที่ไม่เกี่ยวไปด้วย

และเมื่อร้านแต่ละ tenant เป็น **คนละเจ้าของกันจริง** คำขอสองแบบนี้จะมาแน่:
1. *"ขอไฟล์ข้อมูลร้านผมหน่อย"* (เลิกใช้ / อยากเก็บเอง / PDPA)
2. *"เมื่อวานพนักงานลบผิด ย้อนกลับให้หน่อย"*

## การตัดสินใจ

**รับปากข้อ 1 ไม่รับปากข้อ 2**

* ✅ **`POST /tenant/export`** — เจ้าของร้าน (`role='owner'`) ขอไฟล์ข้อมูลร้านตัวเองได้
  * ใช้ **โครงเดิมของ `DB.exportSnapshot()`** (`sa_*` + `__meta`) ที่แอปมีอยู่แล้ว
    → ร้านเอาไฟล์ไปเปิดในแอปเดิมได้จริง ไม่ใช่ไฟล์ที่ไม่มีใครอ่านได้
  * ทำเป็น **BullMQ job แบบ async** (export ทั้งร้านใหญ่เกินกว่าจะทำใน request เดียว)
    → เสร็จแล้วให้ลิงก์ดาวน์โหลดที่หมดอายุ
  * **เขียน `audit_log` ทุกครั้ง** — ไฟล์นี้มีชื่อ/เบอร์โทรลูกค้าทั้งร้าน (PDPA)
  * จำกัดความถี่ (เช่น วันละครั้ง) — เป็น endpoint ที่หนักที่สุดในระบบ
* ❌ **ไม่มี point-in-time restore รายร้าน** และ**ไม่โฆษณาว่ามี**
  * backup ระดับ cluster ยังทำ (กู้ตอน server พัง) แต่กู้ได้ทั้งก้อนเท่านั้น

## เหตุผล

* export เป็นงานที่ **ตรงไปตรงมาและได้ประโยชน์จริง** — โค้ดฝั่ง Flutter ทำอยู่แล้ว
  ย้ายมาฝั่ง server เป็นการ port ไม่ใช่การออกแบบใหม่
* restore รายร้านบน T1 ต้องมี **nightly per-tenant dump แยกทุกร้าน** + สคริปต์ลบ-แล้ว-โหลดกลับ
  ที่ต้องเรียงตาม FK ให้ถูกทั้ง 27 ตาราง — งานใหญ่ที่ **ถ้าทำครึ่ง ๆ กลาง ๆ จะแย่กว่าไม่ทำ**
  (restore พลาด = ข้อมูลร้านอื่นเสียหายด้วย)
* การรับปากแล้วทำไม่ได้ตอนลูกค้าเดือดร้อนจริง แย่กว่าการบอกตั้งแต่แรกว่าไม่มี

## ผลที่ตามมา

* ต้องประกาศให้ชัดในสัญญา/คู่มือ: **"ระบบไม่มีการย้อนข้อมูลรายร้าน"**
* → ยิ่งทำให้ **นโยบาย soft delete ใน `01_DATABASE.md §10` สำคัญขึ้นมาก**
  เพราะมันคือกลไกเดียวที่กู้ "ลบผิด" ได้ ต้องตรวจว่าทุกตารางที่ผู้ใช้กดลบได้เป็น soft delete จริง
* ควรมีปุ่ม export ในหน้า Settings ให้ร้านกดเองได้เป็นประจำ (ร้านถือไฟล์เอง = ประกันของร้านเอง)
* ADR-0003 ข้อ `'closed'`: ก่อนปิดร้านถาวร ต้อง export ให้เจ้าของร้านก่อนเสมอ

## 🔧 แก้ ADR นี้ (2026-09-04) — พบตอนนำไปลงเอกสาร `02_API_SCREENS.md`

**1. `POST /tenant/export` เป็น endpoint ซ้ำ — ยกเลิก**
`02_API_SCREENS.md §3.10` มี **`POST /backup/export`** อยู่ก่อนแล้ว และทำสิ่งเดียวกันเป๊ะ
(`202 Accepted` + `jobId` + BullMQ + signed URL + โครง `sa_*`) ADR ฉบับแรกเสนอ endpoint ใหม่
เพราะเขียนโดยไม่ทันเห็นของเดิม → **ใช้ `POST /backup/export` ของเดิม** แล้วรัดสเปคให้แน่นตาม ADR นี้
(owner เท่านั้น, audit ทุกครั้ง, จำกัดความถี่, ลิงก์หมดอายุ) ไม่สร้างตัวใหม่

**2. `POST /backup/import` เดิมขัดกับ ADR นี้ — ย้ายไป admin plane**
ของเดิมให้ `owner` + PIN อัปโหลด snapshot ทับข้อมูลทั้งร้านได้ — **นั่นคือ restore รายร้าน
แค่เรียกชื่ออื่น** ซึ่งขัดกับข้อสรุปของ ADR นี้ตรง ๆ

แต่การนำเข้าข้อมูลยังจำเป็นอยู่ **เหตุผลเดียว: ตอน onboard ร้านใหม่** (ย้ายข้อมูลจากแอปเดิมเข้ามา
ครั้งแรก — `01_DATABASE.md §9`) จึงย้ายเป็น **`POST /platform/tenants/{id}/import`** ของ admin
plane (ADR-0002) และ **ต้องปฏิเสธถ้า tenant นั้นมีบิลอยู่แล้ว**

→ กลายเป็น **เครื่องมือ provisioning ไม่ใช่เครื่องมือ restore** ซึ่งไม่ขัดกับ ADR นี้อีกต่อไป
ร้านยังกด export เก็บไฟล์เองได้ตามเดิม แค่กด import ทับเองไม่ได้

## ยังไม่เคาะ

* [ ] ลิงก์ดาวน์โหลดหมดอายุกี่ชั่วโมง และเก็บไฟล์ไว้ที่ไหน (disk ของ server / S3-compatible)
* [ ] export ต้องใส่รหัสผ่านไฟล์ไหม (ไฟล์มี PII ทั้งร้าน)
