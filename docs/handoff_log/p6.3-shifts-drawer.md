## 3. ตัดสินใจอะไรไปบ้าง เพราะอะไร

- **ตรวจก่อนสร้าง** — issue เขียนเหมือนงานใหม่ทั้งใบ แต่โค้ดมีอยู่แล้ว · ถ้าเชื่อ issue แล้วสั่ง agent ลงมือเลย จะได้ module ซ้ำหรือ diff ใหญ่ที่ทับของที่ merge ไปแล้ว
- **ไม่รวมเทสต์ใหม่เป็นเคสแยก** สำหรับช่องว่างข้อ (ก) — Dart เช็ก history/drawer ต่อท้ายเคส auto-archive เคสเดียวกัน การแยกเคสใหม่แปลว่าต้อง seed กะที่ลืมปิดซ้ำอีกรอบโดยไม่ได้พิสูจน์อะไรเพิ่ม
- **ไม่แตะเคส `200 concurrent bills`** — ทั้งไม่ดัน pool ทั้งไม่แก้ assertion · handoff รอบก่อนลองดัน pool มาแล้ว (8→8, 20→20, 50→50) จะเขียวต้อง pool ≥ 200 ซึ่งเกิน `max_connections=100` · การแก้ที่ถูกคือ `tx.*` ของ ADR-0003 ไม่ใช่ปรับเลขให้เทสต์เขียว
- **ให้เลขบิลใหม่เป็น `R24` ไม่ไล่เลขใหม่ทั้งไฟล์** — ไฟล์นี้ถือกติกา "หนึ่งเทสต์หนึ่งเลข" ไม่ใช่ "เรียงติดกัน" · การไล่เลขใหม่คือ diff ใหญ่ที่ไม่ได้พิสูจน์อะไร
- **ไม่ปิด gap ข้อที่สามที่ audit เจอ** (`closeForRetirement` ไม่มีคนเรียกจริง) — issue เขียนเองว่า #28 "provides the operation the device endpoint calls" คือให้ของ ไม่ใช่ให้ endpoint · เป็นของ slice device ในอนาคต บันทึกไว้แทน

## 5. ยังไม่ชัวร์ / สมมติฐานที่ยังไม่พิสูจน์

- **ยืนยันแล้ว:** AC ทั้ง 6 มีหลักฐานเป็น assertion จริง ไม่ใช่การอ่านโค้ดเฉย ๆ (agent 2 ตัวไล่แยกกันได้ผลตรงกัน) · สาเหตุของเคส concurrent วัดจาก log จริงแล้ว ไม่ได้เดา
