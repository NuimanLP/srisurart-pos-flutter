## 1. ทำไมถึงเกิดงานนี้

อาจารย์อ่าน `PRIMARY KEY (tenant_id, id)` ใน `01_DATABASE.md` แล้วถามว่า

> "ทำไม primary key มีหลายอัน ควรมีอันเดียวไม่ใช่เหรอ"

คำถามนี้ **ถูกต้องในแง่ที่ว่าเอกสารเราอธิบายไม่พอ** — ทั้งชุดไม่เคยมีประโยคไหนบอกว่านั่นคือ
composite primary key **อันเดียว** ที่ประกอบจาก 2 คอลัมน์ `00_BASICS.md §5` มีตารางศัพท์ SQL อยู่แล้ว
แต่มีแค่ PK / FK / Unique / Index / Constraint / NULL ไม่มีคำว่า composite เลย

---

## 2. ต้นเหตุจริงคือรูป ER ไม่ใช่ข้อความ 🔴

จุดที่สำคัญที่สุดของรอบนี้ และเกือบพลาด — **แก้ข้อความอย่างเดียวไม่พอ**

Mermaid ER syntax ไม่มีสัญลักษณ์สำหรับ composite key จึงเรนเดอร์ `01_DATABASE.md §3` ออกมาเป็น

```
SALES {
    uuid tenant_id PK
    text id        PK      ← เห็นแบบนี้ ใครอ่านก็แปลว่า "PK สองอัน"
    text receipt_no UK     ← ของจริงคือ UNIQUE (tenant_id, receipt_no) ไม่ใช่คอลัมน์เดี่ยว
```

นี่คือภาพที่ผลิตคำถามขึ้นมา ถ้าเติมคำอธิบายไว้ที่ `§2` อย่างเดียว คนที่เลื่อนลงไป `§3` ก็เจอ
ภาพเดิมที่ยังโกหกอยู่ จับได้ในรอบ `/scrutinize` ไม่ใช่ตอนเขียน

**กติกาที่ได้: รูป Mermaid ER ทุกรูปที่มีตารางแบบ multi-tenant ต้องมีป้ายกำกับว่า Mermaid เขียน
composite key ไม่ได้** ตอนนี้มีบรรทัดเดียวคร่อมทั้ง 3 รูปใต้ `## 3. ER Diagram` แล้ว

## 4. ของที่เขียนผิดรอบแรก และรอบตรวจจับได้ 🔴

รอบแรกเขียนเสร็จแล้ว **ดูเหมือนถูกหมด** ส่งเข้า `/scrutinize` + `/code-review` แล้วเจอ 6 จุด
ทุกจุดเป็นของจริง ตรวจซ้ำเองแล้วทั้งหมด

| จุด | ผิดยังไง | ทำไมสำคัญ |
|---|---|---|
| นิยาม **candidate key** | เขียนว่า "ทุกชุดคอลัมน์ที่ระบุแถวได้" — นั่นคือนิยามของ **superkey** ขาดเงื่อนไข minimality ⇒ `(tenant_id, id, part_no)` ก็จะนับเป็น candidate key ด้วย | เป็นคำถามแรกที่คนสอน relational theory จะถามต่อ และเราตอบผิด → แก้นิยาม + เพิ่มแถว **Superkey** ไว้เทียบให้เห็นความต่าง + ระบุว่า PK คือ candidate key อันที่ถูกเลือก |
| `products.part_no` = **natural key** | overclaim — index เป็น **partial** (`WHERE deleted_at IS NULL`) แถวที่ soft-delete แล้วซ้ำกันได้ และไม่ซ้ำแค่ **ต่อร้าน** | key ที่ยอมให้ซ้ำได้ในบางเงื่อนไข ไม่ใช่ candidate key ของ relation → เขียนข้อจำกัดให้ครบ แล้ว**พลิกเป็นข้อดี**: นี่คือเหตุผลที่เราเลือก surrogate key เป็น PK |
| ชื่อ index | อ้าง `uq_products_partno_ci` ซึ่งเป็นแค่คอมเมนต์ `-- 🆕 migration 1788652800007:` **ที่ยังไม่ apply** ของจริงที่บังคับอยู่คือ `uq_products_partno` (case-sensitive) | อ้าง migration ที่ยังไม่มีอยู่จริงว่าเป็นของที่ใช้อยู่ ผิดทั้ง 2 ไฟล์ |
| `adr/README.md` | pointer เขียนว่า "งงกับ PK สองอันใน **ADR-0003**" ทั้งที่ทั้งโฟลเดอร์ `adr/` **ไม่มีคำว่า `PRIMARY KEY` เลยสักไฟล์** | อ้างของที่ไม่มีอยู่ ใส่ให้อาจารย์อ่านแล้วเขากดเข้าไปดู = เสียความน่าเชื่อถือทันที |
| `architecture-primer.md` | pointer อ้าง "หลักการเดียวกับ **Composite FK** ที่พูดถึงใน **§4**" ทั้งที่ `§4` คือ *ทางเลือกและข้อแลกเปลี่ยน (Options & Trade-offs)* A/B/C ไม่เกี่ยวกับ FK | เหมือนข้างบน |
| `04_QA_SCRUTINY.md` | เขียนว่าถก Composite FK "หลายครั้ง" ทั้งที่มีครั้งเดียว | overstate เล็ก ๆ แต่ตรวจได้ |

**บทเรียนร่วมของ 3 ข้อล่าง:** ที่ทำให้เกิดข้อความเท็จคือ **ตัวอย่างเฉพาะไฟล์ที่แต่งขึ้นเอง**
ไม่ใช่ประโยคนิยามที่ซ้ำกัน — reviewer เสนอให้ตัดประโยคอธิบายออกจากไฟล์บริวารเหลือแค่ลิงก์เปล่า
**เจ้าของงานเลือกไม่ทำตาม** เพราะคนที่เปิดไฟล์เดียวควรได้คำตอบโดยไม่ต้องคลิกต่อ และนิยามไม่ drift
แต่บังคับกติกาแทนว่า **hook เฉพาะไฟล์ทุกอันต้อง `grep` ยืนยันก่อนเขียน** ตอนนี้ทุกอันยืนยันแล้ว

## 5. ของเดิมที่ขุดเจอระหว่างทาง — ยังไม่แก้ ไม่ใช่ของที่งานนี้ทำพัง

1. **`architecture.md` มี DDL ที่ขัดกับ `01_DATABASE.md`** — `id UUID PRIMARY KEY` คอลัมน์เดียว
   + `tenant_id` แยก + ไม่มี composite FK ซึ่งขัดกับกติกาข้อ 2 ของ `01 §2` ตรง ๆ และยังมี
   `offline_ok` ที่ถูกทิ้งไปตาม **#272** · ที่แย่คือ `00_INDEX.md` โฆษณาไฟล์นี้ว่าเป็น
   "สเปกสถาปัตยกรรมฉบับอ้างอิง" โดยไม่มีป้ายเตือน
   **รอบนี้ทำแค่ติดป้าย 🔴 ว่าให้ยึด `01_DATABASE.md §5`** การเคลียร์จริงควรเป็นใบแยก
2. **`audit_log` — เอกสารตามหลัง migration** · `01_DATABASE.md §5.1` เขียน
   `id BIGSERIAL PRIMARY KEY` (คอลัมน์เดียว) แต่ migration ที่ ship ไปแล้วใช้ `(tenant_id, id)`
   ซึ่งบันทึกไว้ที่ `adr/README.md` ท้ายไฟล์ในหัวข้อ "ที่ต่างจาก DDL ในเอกสาร"
   **รอบนี้ใส่หมายเหตุชี้ความต่างไว้ทั้งสองฝั่งแล้ว แต่ยังไม่ได้ทำให้ตรงกัน** — ถ้าอาจารย์จับจุดนี้
   ต้องตอบว่า *เอกสารตามหลัง migration* ไม่ใช่ *ออกแบบขัดกันเอง*
3. `uq_products_partno_ci` ยังเป็น migration ที่ยังไม่ apply — ถ้าวันไหน apply แล้ว
   ต้องกลับไปแก้แถว Natural Key ทั้ง 2 ไฟล์ให้ชี้ชื่อใหม่

## 6. วิธีตอบอาจารย์ (เก็บไว้ใช้ตอน present)

> มี PK อันเดียวครับ เป็น **composite primary key** ที่ประกอบจาก 2 คอลัมน์ `(tenant_id, id)` —
> เหมือนเลขห้อง 101 ที่ซ้ำได้ทุกตึก ต้องบอก "ตึก A ห้อง 101" ถึงจะชี้ถูก
> ที่เห็นเป็นสองบรรทัดในรูป ER เพราะ Mermaid เขียน composite key ไม่ได้
> เหตุผลที่ไม่ใช้ `id` เดี่ยว: พอ PK เป็นคู่ **foreign key ก็พา `tenant_id` ไปด้วย** ทำให้บิลของร้าน A
> อ้างสินค้าของร้าน B ไม่ได้ในระดับโครงสร้าง ไม่ต้องหวังพึ่ง `WHERE` ที่โปรแกรมเมอร์อาจลืมใส่

ถ้าถามลึกกว่านั้น เอกสารมี superkey / candidate / alternate / natural / surrogate ครบแล้ว
รวมถึงข้อที่ตอบยากที่สุด — ทำไม `part_no` ถึงยังไม่ใช่ candidate key เต็มตัว

## 7. วิธีทำงานรอบนี้ (ถ้าจะทำซ้ำ)

เขียนขนาน 2 agent (แยกไฟล์ไม่ให้ชนกัน โดยตกลง anchor `#keys` ไว้ล่วงหน้าเป็นสัญญา)
→ `/scrutinize` + `/code-review` ขนานกัน → เจ้าของงานตรวจ finding เองทุกข้อก่อนสั่งแก้
→ แก้ขนาน 2 agent → ตรวจ diff ปิดท้ายเอง

**ที่ได้ผลจริง:** รอบเขียนแรกดูเรียบร้อยมากและผิด 6 จุด รอบตรวจคือสิ่งที่กันไม่ให้ของผิด
