# Pain points ที่ AI ทำให้ "คุ้มที่จะแก้" — ร้านศรีสุราษฎร์ (สำรวจก่อนสร้าง)

- วันที่: **2026-10-23** · ขอบเขต: สำรวจอย่างเดียว ไม่มีโค้ด ไม่แตะ schema
- ที่มา: อ่านโค้ด + เอกสารใน repo นี้ (ข้อเท็จจริงที่ใช้หนักได้เปิดไฟล์ตรวจซ้ำแล้ว — ดู §7)
- 🔴 **ข้อจำกัดใหญ่ของเอกสารนี้:** ไม่พบหลักฐานคำบอกเล่าจากพนักงานหน้าร้านโดยตรง
  และไม่มีเอกสารว่าร้านทำงานอย่างไรก่อนมี POS (กระดาษ / LINE / Excel) ไม่มีงานสิ้นเดือน งานบัญชี หรืองานตรวจนับสต็อกที่เขียนไว้เลย
  ดังนั้น "ใครเจ็บ / บ่อยแค่ไหน" ในตาราง §3 เป็น **[สมมติฐาน]** ที่อนุมานจากโค้ดทั้งหมด ต้องให้เจ้าของยืนยัน (คำถามใน §6)

## 1. สรุป 5 บรรทัด

1. **แนะนำทำอันดับ 1: รายการบิล โอน/QR รายวันแบบพิมพ์ได้ ให้เจ้าของติ๊กเทียบกับแอปธนาคาร** (ขนาด S ใช้ได้ทุกธนาคาร ไม่ต้องอ่าน statement) เพราะเป็นช่องโหว่ที่ระบบไม่มีการยืนยัน [สมมติฐาน] (`qr_payment_panel.dart:10` "No confirmation step") · การ import statement อัตโนมัติเป็นขั้นต่อไป ทำเมื่อรู้คำตอบคำถามข้อ 4–5
2. อันดับ 2: ใบแจ้งยอด/ใบวางบิลช่างพร้อมอายุหนี้ · อันดับ 3: รายงาน "เงินสดออกไปไหน" รายเดือน (เริ่มจากนับโน้ตจริงใน backup ก่อนเขียนโค้ด)
3. ทั้ง 3 ข้อเป็น **AI-as-builder**: AI ทำให้เขียนซอฟต์แวร์ได้ถูกลง แต่ตอนรันเป็นโค้ด deterministic ล้วน ไม่ส่งข้อมูลลูกค้าออกไปไหน และไม่มีค่า API รายเดือน
4. เลือกงานฝั่ง client เพราะร้านจริงยังใช้ **Drift build ออฟไลน์** (cutover #231 ยังเปิดอยู่) งานฝั่ง server จะไปไม่ถึงร้านจนกว่าจะ cutover
5. pipeline ของบริษัทเจ้าของ (สลิป → ใบกำกับ → บัญชี → กระทบยอด → cashflow → ส่งสรรพากร) ใช้ที่นี่ได้แค่ส่วนกลาง ส่วนภาษีต้องรอคำตอบก่อนว่า **ร้านจด VAT หรือไม่ (ไม่พบหลักฐาน)**

| 4. บัญชีรายรับ-รายจ่ายในบ้าน | **บางส่วน** | รายรับมีครบ (sales / returns / credit_payments) · รายจ่ายมีแค่ `note` ข้อความอิสระ (ไม่บังคับกรอก) ของ drawer entry ไม่มีหมวด (Drift `frontend/lib/data/db/tables.dart:356-366` ซึ่งเป็นตารางที่ร้านใช้จริง · server `*InitialSchema.ts:494-505`) · ไม่มีตารางค่าใช้จ่าย ไม่มีเจ้าหนี้การค้า ไม่มีการจ่ายเงินซัพ |

| 6. Dashboard cashflow (เดือน/ปี, หมวดจ่าย, โปรเจกต์/BU) | **บางส่วน** | server มี `summary/closing/top-products/by-category/stock-value/low-stock/product-sales` (`server/src/reports/reports.controller.ts`) แต่ **Flutter ไม่เรียก `/reports/*` เลย** (สูตรคำนวณจึงมีสองที่ คือ `frontend/lib/domain/reports/net_sales.dart`) · ส่งออก CSV ได้ใน `settings_screen.dart` · ไม่มีรายงาน cashflow / P&L / VAT · "โปรเจกต์/BU" ไม่เข้ากับร้านเดียว ถ้าจะมีมิติที่ใกล้เคียงก็คือ "บัญชีรับเงิน" หรือ "ช่าง" |
| 7. สต็อก | **มีเกือบครบ** | stock, movements, PO, ต้นทุนถัวเฉลี่ย, `stockLevel()` (`low_stock_alert.dart`) · **ขาด:** ขั้นตอนตรวจนับ, หมวดเหตุผลการปรับยอด (`movements.note` เป็นข้อความอิสระ), รายงานสินค้าที่ไม่เคยขาย (Slow Movers เลือกจากสินค้าที่ขายได้เท่านั้น: `products_screen.dart:3759-3764`), และการแนะนำจำนวนสั่งซื้อ |
| 8. ส่งออกเอกสารให้สรรพากร | **ไม่มี** | มี `taxRate`/`taxId`/`branchNo` ใน settings · ไม่มีข้อมูล ภ.พ.30, ไม่มีภาษีหัก ณ ที่จ่าย, ไม่มี e-Tax · **ร้านจด VAT หรือไม่: ไม่พบหลักฐาน** (ค่า `taxRate 7` อาจเป็นแค่ค่าตั้งต้น) |

**ข้อสังเกต:** บริษัทเจ้าของมี "ฐานข้อมูลรายจ่าย + ข้อมูลธนาคาร" เป็นแกนของ pipeline แต่ร้านนี้ยังไม่มีทั้งสองอย่าง
ขั้น 4–6 จึงทำไม่ได้ด้วยการต่อ AI เข้าไปเฉย ๆ ต้องเริ่มเก็บข้อมูลก่อน ส่วนขั้น 7 ร้านนี้แข็งแรงกว่า

## 3. ตาราง pain point (เรียงตามความคุ้ม × ไปถึงร้านได้จริง)

คำย่อ: **(a)** = AI-as-builder (AI ทำให้เขียนโปรแกรมได้ถูก แต่ตอนใช้งานเป็นโค้ดธรรมดา) · **(b)** = AI-at-runtime (OCR / จัดหมวดด้วย LLM / สรุปข้อความ ทุกครั้งที่ใช้)
ขนาด: S ≈ 1–3 วัน · M ≈ 1–2 สัปดาห์ · L = หลายสัปดาห์ หรือต้องรอ cutover/ผู้ให้บริการภายนอก (ประเมินคร่าว ๆ)

| # | Pain | ใครเจ็บ / บ่อยแค่ไหน [สมมติฐาน] | ทำไมเมื่อก่อนไม่คุ้มที่จะแก้ | AI ช่วยตรงไหน | ขนาด | ความเสี่ยง | ขึ้นกับ | วัดว่าได้ผลอย่างไร |
|---|---|---|---|---|---|---|---|---|
| 1a | รู้ไม่ได้ว่าบิล โอน/QR มีเงินเข้าจริงทุกใบ (สลิปปลอม/ลูกค้าไม่ได้โอน) ตอนปิดกะเห็นแค่ยอดรวมต่อบัญชี (`closing_report.dart:985`) ถ้ายอดไม่ตรงต้องไล่หาเองว่าบิลไหน | เจ้าของ: ทุกวันตอนปิดกะ | งานเล็กเกินกว่าจะมีใครจัดลำดับให้ | **(a)** รายการบิล โอน/QR ของวัน (เวลา, ยอด, บัญชี) แบบพิมพ์ได้ ให้เจ้าของติ๊กเทียบกับแอปธนาคาร | S | ยังพึ่งคนติ๊ก · บิลบนเครื่องอื่นมองไม่เห็น (API build ไม่ดึงยอดขายข้ามเครื่อง) | ไม่มี ใช้ได้ทุกธนาคาร | ทดลอง 5 วัน: เจ้าของหาบิลที่เงินไม่เข้าได้จากรายการนี้ และจับเวลาเทียบกับวิธีเดิม (จับเวลาวิธีเดิมไว้ก่อน) |
| 1b | (ต่อจาก 1a) ให้เครื่องจับคู่กับ statement แทนการติ๊ก | เจ้าของ: ทุกวัน/ทุกเดือน | API ธนาคารต้องเป็น biller/นิติบุคคล การเขียนตัวจับคู่ statement ต่อธนาคาร ร้านเดียวจ้างทำไม่คุ้ม | **(a)** ตัว import + ตัวจับคู่ (ยอด + เวลา + บัญชี) เป็นโค้ดธรรมดา · ถ้า statement เป็น PDF ก็ยังดึงข้อความในเครื่องแบบ deterministic ได้ **ไม่จำเป็นต้องเป็น (b)** (ยกเว้น PDF ที่เป็นภาพสแกน) | M | **จับคู่ด้วยยอดพิสูจน์ไม่ได้ว่าไม่พลาด:** เงินเข้ายอดเดียวกันจากที่อื่น (ยอดกลม ๆ, ช่างโอนชำระเครดิต, โอนส่วนตัวเข้าบัญชีเดียวกัน) กลบบิลที่ไม่มีเงินเข้าได้ · บิล QR ที่ไม่มีบัญชีก็บันทึกได้ (`qr_payment_panel.dart:9`) · statement มีชื่อผู้โอน (PDPA ต้องอยู่ในเครื่อง) | ธนาคารไหน และได้ไฟล์รูปแบบใด **[ยังไม่ยืนยัน]** (บัญชีบุคคลอาจได้แค่ PDF ที่ล็อกรหัส CSV น่าจะมีเฉพาะ business banking) · คำถามข้อ 4–5 | ทดลองด้วย statement จริง 5 วันที่ **ฝังบิลที่รู้ว่าไม่มีเงินเข้าไว้ 1 ใบ**: บิลนั้นต้องขึ้นเป็น "บิลไม่มีเงินเข้า" หรือ "ต้องตรวจเอง" ห้ามขึ้นเป็น "ตรง" |
| 2 | ตรวจสลิปตอนขาย (real-time) | แคชเชียร์: ทุกบิล QR | ต้องสมัคร vendor ต้องมี server ถือ API key และสลิปอายุ 7–30 วัน | ไม่ใช่ AI: vendor ค้นข้อมูลธนาคารจาก mini-QR · (a) สำหรับตัวต่อ | L | ค่าบริการต่อสลิป · PDPA (รูปสลิปส่งไป vendor ซึ่งบางเจ้าประมวลผลนอกประเทศ) · ไม่มี vendor ไหนประกาศ SLA · ยังไม่ได้พิสูจน์ว่า `mob04` ต่อออกไปหา vendor ได้ | **cutover #231** + server + การตัดสินใจเรื่องเงินและ PDPA | หลัง cutover: สลิปซ้ำ (`UNIQUE transRef`) ถูกปฏิเสธ 100% ในชุดทดสอบ และพบสลิปปลอม 0 ใบใน 1 เดือน |
| 3 | ช่างค้างเครดิตแต่ไม่มีใบแจ้งยอด/ใบวางบิล ไม่รู้ว่าหนี้ค้างมานานเท่าไร | เจ้าของ: ทุกเดือน (รอบเก็บเงิน) · ช่าง: ขอดูยอดค้าง | งานพิมพ์ใบแจ้งยอดจ้างทำแพงเมื่อเทียบกับจำนวนช่างที่มี | **(a)** สร้าง PDF A4 โดยยึด `creditBalance` เป็นยอดจริง แล้วกระจายย้อนจากบิลเครดิตล่าสุด เพื่อบอกอายุหนี้ (แสดงผลเท่านั้น) | S–M | บิลอธิบายยอดได้ไม่ครบเสมอ เพราะยอดถูกปัดที่ 0 และ import แบบ legacy เขียนยอดตรง ๆ (รายละเอียด §4.2) จึงต้องมีบรรทัด "ยอดยกมา" · การกระจายอาจไม่ตรงกับที่ร้านตกลงกับช่าง | กำหนดเงื่อนไขเครดิต (กี่วัน) | ยอดรวมบนใบ = `creditBalance` ทุกสตางค์ · บรรทัด "ยอดยกมา/ไม่มีบิลอ้างอิง" ขึ้นทุกครั้งที่ไม่เป็น 0 · เจ้าของใช้จริงครบ 1 รอบเก็บเงิน |
| 4 | ปิดกะแล้วเงินขาด/เกิน ไม่มีเหตุผลและไม่มีประวัติ | เจ้าของ: ทุกวัน | งานเล็ก ไม่มีใครมาจัดลำดับให้ | **(a)** | S | ต้องเพิ่มคอลัมน์ทั้งใน Drift (lane B เป็นเจ้าของ) และ server (`shifts` มีแค่ `physical_cash`) | ไม่มี | 30 วันหลังใช้: ทุกกะที่เงินไม่ตรงมีเหตุผลกำกับ 100% และเจ้าของเปิดดูย้อนหลังรายเดือนได้ |

## 4. 3 งานที่แนะนำให้สร้างต่อ

ทั้ง 3 ข้อ: เป็นงานฝั่ง client ที่ทำงานได้ทั้ง Drift build และ API build (แบบเดียวกับ favourites / บัญชีรับเงิน QR)
ไม่แตะกติกาเงินและสต็อกฝั่ง server (เป็นการอ่านอย่างเดียว) ข้อความภาษาไทยใหม่ทุกข้อความเป็น `agent ร่าง` จนกว่าเจ้าของจะรับรอง
🔴 **ร้านจะได้ใช้ก็ต่อเมื่อมีคน build web ใหม่แล้วนำไปวางบนเครื่องร้าน** ยังไม่พบหลักฐานว่าตอนนี้ทำแบบนี้อย่างไรและบ่อยแค่ไหน (คำถามข้อ 2)

### 4.1 รายการบิล โอน/QR ให้ติ๊กเทียบแอปธนาคาร → ภายหลังจึงจับคู่ statement (pain #1a → #1b)

- **ทำไมเป็นอันดับ 1:** เป็นช่องโหว่ที่ระบบไม่มีการยืนยัน [สมมติฐาน: ยังไม่รู้ว่าเกิดความเสียหายจริงบ่อยแค่ไหน ดูคำถามข้อ 5]
  1a ถูกที่สุด ใช้ได้ทุกธนาคาร ไม่ต้องรอ cutover และไม่มีข้อมูลธนาคารเข้าเครื่อง
  ข้อมูลพร้อมแล้ว เพราะรายงานปิดกะแยก โอน/QR ตามบัญชีอยู่แล้ว (`closing_report.dart:65-101, 985`) เหลือแค่แสดงเป็นรายบิล
- **Tracer bullet ของ 1a:** ในรายงานปิดกะ (หรือหน้ารายงาน) มีปุ่ม `พิมพ์รายการ โอน/QR` เลือกวันแล้วได้รายการบิล
  (เวลา · เลขบิล · ยอด · บัญชี โดยบิลที่ไม่มีบัญชีอยู่กลุ่มแยก) พร้อมช่องว่างให้ติ๊กและยอดรวมต่อบัญชีที่ตรงกับรายงานปิดกะ
  ไม่แก้ schema และไม่มีข้อมูลธนาคารเข้าเครื่อง
- **วัดว่าได้ผล (1a):** ยอดรวมต่อบัญชีในรายการ = แถวบัญชีในรายงานปิดกะทุกสตางค์ (ทดสอบอัตโนมัติ) · ทดลอง 5 วัน แล้วจับเวลาเทียบกับวิธีเดิม (จับเวลาวิธีเดิมไว้ก่อน)
- **1b (ทำต่อเมื่อคำถามข้อ 4 ได้คำตอบว่าได้ไฟล์ statement ที่อ่านได้ และข้อ 5 บอกว่าปัญหาเกิดบ่อยพอ):**
  import statement ทีละไฟล์ ประมวลผลในเครื่อง ไม่เก็บลง DB
  - ใช้เฉพาะรายการเงินเข้า (credit) ส่วนรายการเงินออก (เช่นคืนเงินแบบ `โอน`) ไม่สนใจ
  - จับคู่**แบบนับจำนวนต่อยอด** ในแต่ละวันและบัญชี: จำนวนบิลยอด X เทียบกับจำนวนเงินเข้ายอด X
  - หน้าต่างเวลาเป็นด้านเดียว คือเงินเข้าต้อง**ก่อน**เวลาบิลไม่เกิน N นาที (แคชเชียร์กดบันทึกหลังเห็นเงินเข้า)
  - ผลแบ่ง 4 กลุ่ม:
    - "ตรง" = ยอดนั้นมีบิลและเงินเข้าอย่างละ 1 ใน 1 หน้าต่าง
    - "บิลไม่มีเงินเข้า"
    - "เงินเข้าไม่มีบิล"
    - **"ต้องตรวจเอง"** = กลุ่มยอดที่มีหลายรายการ หรือมีเงินเข้ายอดเดียวกันจากที่อื่น
  - 🔴 การจับด้วยยอด**รับประกันไม่ได้**ว่าไม่พลาด เงินเข้ายอดเดียวกัน (ยอดกลม ๆ, ช่างโอนชำระเครดิตซึ่งใน Drift ไม่มีคอลัมน์วิธีชำระ: `tables.dart:291-301`, เงินโอนส่วนตัว) กลบบิลที่ไม่มีเงินเข้าได้
  - ร้านไม่มีการแบ่งจ่าย ทำให้ 1 บิล = เงินเข้า 1 รายการ ซึ่งช่วยให้จับคู่ได้ แต่บัญชีแบบ "รูป QR" ลูกค้าพิมพ์ยอดเอง จึงอาจไม่ตรง
- **รูปแบบไฟล์ [ยังไม่ยืนยัน]:** บัญชีบุคคล (K PLUS / SCB Easy / Krungthai NEXT) น่าจะได้ statement เป็น PDF ที่ล็อกรหัส ส่วน CSV/Excel น่าจะมีเฉพาะ business banking
  ถ้าเป็น PDF ที่เป็นข้อความ ก็ดึงข้อความในเครื่องแบบ deterministic ได้ ไม่ต้องใช้ AI ตอนรัน แต่ต้องเห็นไฟล์จริงก่อน
- **ต้องให้เจ้าของตัดสินใจ:**
  - ธนาคาร/บัญชี และรูปแบบไฟล์ statement (ส่งตัวอย่างที่ลบชื่อออกแล้ว 1 ไฟล์)
  - ยืนยันว่า statement ประมวลผลในเครื่องเท่านั้น
  - บัญชีรับเงินร้านใช้รับโอนส่วนตัวด้วยไหม
  - ร้านใช้กี่เครื่องในการขาย
- **วัดว่าได้ผล (1b):** ทดลองกับ statement จริง 5 วัน โดย**ฝังบิลที่รู้ว่าไม่มีเงินเข้าไว้ 1 ใบ** (หรือนำบิลจริงที่เจ้าของรู้ว่าเงินไม่เข้ามาใช้)
  บิลนั้นต้องขึ้นเป็น "บิลไม่มีเงินเข้า" หรือ "ต้องตรวจเอง" ห้ามขึ้นเป็น "ตรง" · นับสัดส่วน "ต้องตรวจเอง" ถ้าเกินครึ่ง 1b ก็ไม่คุ้มกว่า 1a

### 4.2 ใบแจ้งยอด/ใบวางบิลช่าง + อายุหนี้ (pain #3)

- **ทำไม:** มีข้อมูลอยู่แล้ว ได้แก่บิล `เครดิตช่าง`, `credit_payments` ที่มี `receipt_no`, ledger รายช่าง, แท็บ "มียอดค้าง" (= `creditBalance > 0`: `mechanics_screen.dart:179`)
  ที่ยังขาดคือเอกสารที่ส่งให้ช่างได้ และการบอกว่าหนี้ค้างมานานแค่ไหน งานนี้เกี่ยวกับการเก็บเงินเข้าร้านโดยตรง
- 🔴 **บิลกับการชำระ "ไม่รวมกันได้เท่ากับ" `creditBalance` โดยโครงสร้าง** จึงห้ามคำนวณยอดค้างจากบิลเอง ตรวจในโค้ดแล้ว:
  - ยอดถูกปัดที่ 0 ตอนรับชำระ (`mechanics_repository.dart:127-129`), ตอน void (`sales_repository.dart:327`) และตอนคืนของ (`return_plan.dart:141`)
  - import แบบ legacy เขียน `creditBalance` ตรง ๆ (`snapshot_repository.dart:762`)
  - `หักจากเครดิต` เลือกได้กับทุกบิลที่มีช่าง รวมถึงบิลเงินสดด้วย (`returns_screen.dart:1040`)
  - คืนของครบทั้งบิลจะ auto-void โดยไม่หักเครดิตซ้ำ (`returns_repository.dart:149-152`) ถ้า "ตัดบิล void แล้วลบยอดคืน" จะนับซ้ำ
  - ใน API build ยอดรวมบิลจากเครื่องอื่นด้วย
- **Tracer bullet:** ปุ่ม `พิมพ์` บนหน้าช่าง 1 คน → PDF A4 (ใช้ `PdfPreview` แบบเดียวกับใบ PO/ใบเสนอราคา)
  - ยึด `creditBalance` เป็นยอดจริง
  - กระจายยอดนี้**ย้อนจากบิลเครดิตล่าสุด** ไปหาบิลเก่า:
    - แต่ละบิลใช้ยอดสุทธิหลังหักคืนแบบ `หักจากเครดิต` ของบิลนั้นเอง
    - ข้ามบิลที่ void ด้วยมือ (`voidReason != null`)
    - แสดงจำนวนวันนับจากวันที่บิล
  - ส่วนที่บิลอธิบายไม่ได้แสดงเป็นบรรทัด **"ยอดยกมา/ไม่มีบิลอ้างอิง"**
  - มียอดรวมและช่องลงชื่อ
  - ยังไม่ทำ: การตัดยอดเข้าบิลจริงใน DB, การเตือนผ่าน LINE/SMS และการพิมพ์ทีละหลายคน
- **ต้องให้เจ้าของตัดสินใจ:**
  - เงื่อนไขเครดิตกี่วัน
  - การกระจายแบบนี้ (แสดงผลเท่านั้น) รับได้ไหม
  - หัวกระดาษ/ข้อความบนเอกสาร (`agent ร่าง`)
  - ส่ง PDF ให้ช่างทาง LINE ได้ไหม (PDPA: เอกสารมีชื่อและยอดหนี้)
- **วัดว่าได้ผล:**
  - ทดสอบอัตโนมัติ: ยอดรวมบนเอกสาร = `creditBalance` ทุกสตางค์ · บรรทัด "ยอดยกมา" ขึ้นทุกครั้งที่ส่วนที่เหลือ ≠ 0 และไม่ขึ้นเมื่อ = 0
    (ไม่ใช่ "บิลต้องรวมได้เท่ากับยอด") · มีกรณีทดสอบสำหรับการปัดที่ 0, `หักจากเครดิต` บนบิลเงินสด และการคืนครบที่ auto-void
  - ใช้จริง 1 รอบเก็บเงิน แล้วนับว่าช่างที่ได้รับใบชำระภายในรอบกี่คน (ยังไม่มีตัวเลขก่อนใช้ ให้เจ้าของจดไว้)

### 4.3 รายงาน "เงินสดออกไปไหน" รายเดือน (pain #5)

- **ทำไม:** เป็นก้าวแรกที่ถูกที่สุดไปสู่ขั้น "บัญชีรายจ่าย/cashflow" ใน pipeline ของบริษัทเจ้าของ ถ้ารายงานนี้ไม่มีประโยชน์ ก็ไม่ควรลงทุนทำบัญชีรายจ่ายเต็มรูป
  **ข้อควรระวัง:** ยังไม่มีข้อมูลว่าโน้ตจริงหน้าตาเป็นอย่างไร
  - คำว่า "จ่ายซัพ / เติมทอน / ค่าน้ำมัน" ได้มาจาก hint ในช่องกรอก (`cash_drawer_screen.dart:624`) ไม่ใช่จากข้อมูลจริง
  - โน้ตไม่บังคับกรอก (`tables.dart:361`)
- **ขั้น 0 (ไม่เขียนโค้ด):** ขอ owner backup 1 ไฟล์ (snapshot มี drawer entries อยู่แล้ว: `snapshot_repository.dart:485-494`) แล้วนับ:
  - จำนวน drawer-out ต่อเดือน
  - สัดส่วนโน้ตว่าง
  - คำที่ใช้บ่อย

  ถ้าโน้ตว่างเกินครึ่ง หรือมีรายการน้อยมาก ให้หยุดตรงนี้แล้วไปทำ #4 หรือ #7 แทน · ไฟล์ backup มีข้อมูลลูกค้า ต้องอ่านในเครื่องเจ้าของเท่านั้น
- **Tracer bullet (ถ้าผ่านขั้น 0):** หน้ารายงาน 1 หน้า เลือกเดือนแล้วแสดง drawer-out ทุกรายการ จัดกลุ่มด้วยตารางจับคำแบบตายตัวที่ได้จากขั้น 0
  - แสดงโน้ตว่างเป็นกลุ่มแยก ไม่รวมกับ "อื่นๆ"
  - แสดงยอดรวมต่อหมวดเทียบกับยอดขายสุทธิของเดือน
  - ใช้เฉพาะ type `out` (เติมทอนปกติเป็น type `in` จึงไม่อยู่ในรายงานนี้)
  - ไม่เพิ่มคอลัมน์ ไม่ใช้ LLM ถ้าเจ้าของใช้จริง ขั้นต่อไปจึงค่อยเพิ่มช่องหมวดตอนบันทึกเงินออก (schema bump ของ lane B)
- **ต้องให้เจ้าของตัดสินใจ:**
  - รายการหมวด
  - รายจ่ายที่ไม่ผ่านลิ้นชัก (ค่าเช่า/ค่าไฟที่โอนจ่าย) จะเก็บที่ไหน ตอนนี้ไม่อยู่ในระบบ
- **วัดว่าได้ผล:**
  - ผลรวมทุกหมวด + โน้ตว่าง = ผลรวม drawer-out ของเดือน (ทดสอบอัตโนมัติ)
  - ปรับตารางคำบนเดือน A แล้ววัดสัดส่วน "อื่นๆ" บนเดือน B ที่ไม่เคยเห็น (เพื่อไม่ให้ปรับคำจนตัวเลขดูดีเกินจริง)
  - เจ้าของตอบว่า "ได้ใช้ตัดสินใจอะไร" อย่างน้อย 1 เรื่อง

**ลำดับนี้มีเงื่อนไข:**
- ถ้าคำถามข้อ 5 ตอบว่าแทบไม่เคยเจอเงินโอนไม่เข้า 4.1 จะตกลงไป
- ถ้าคำถามข้อ 6 ตอบว่าเงินขาด/เกินเป็นปัญหาประจำวัน #4 ควรขึ้นมาแทน 4.3 (ที่ไม่เลือก #4 ตั้งแต่ต้นเพราะต้องแก้ schema ทั้งสองฝั่ง)

## 5. สิ่งที่ยังไม่ควรสร้างตอนนี้ และเหตุผล

- **ตรวจสลิปอัตโนมัติด้วย API (pain #2):** ต้องมี server ถือ API key จึงไปไม่ถึงร้านจนกว่าจะ cutover #231
  และยังมีเรื่องค้างอีกหลายอย่าง: ค่าบริการต่อสลิป, PDPA (รูปสลิปมีชื่อและบัญชีลูกค้า บาง vendor ประมวลผลนอกประเทศ), ไม่มี SLA, ยังไม่ได้ตรวจว่า `mob04` ต่อออกไปหา vendor ได้
  ผลวิจัยพร้อมแล้ว (`slip-verification-api.md` §4.3) ให้กลับมาดูหลัง cutover และหลังข้อ 4.1 แสดงว่ามีสลิปปลอมจริง
- **ใบกำกับภาษีเต็มรูป / e-Tax / ภ.พ.30 / ส่งออกให้สรรพากร / ออกใบกำกับทาง email:** อยู่นอกขอบเขต v1 (CLAUDE.md) · ยังไม่รู้สถานะ VAT
  ลูกค้าไม่มีช่องเลขผู้เสียภาษีหรือ email · ถ้าทำผิดรูปแบบจะมีความเสี่ยงทางกฎหมาย ควรคุยกับคนทำบัญชีของร้านก่อน
- **Dashboard cashflow/P&L ฝั่ง server:** ข้อมูลพื้นฐานยังไม่มี (ไม่มีตารางรายจ่าย ไม่มีข้อมูลธนาคาร) และ client ไม่ได้เรียก `/reports/*` ด้วย จึงไปไม่ถึงร้านก่อน cutover
- **เจ้าหนี้การค้า / vendor master / OCR ใบส่งของ (pain #9):** ต้องแก้ schema หลายตารางและแตะ `receivePO` (กติกาต้นทุนถัวเฉลี่ยอยู่ฝั่ง server)
  OCR ที่อ่านผิดจะทำให้ต้นทุนเพี้ยนแบบไม่มีใครเห็น
- **สรุปด้วย LLM / แจ้งเตือนทาง LINE (pain #11):** ส่งข้อมูลยอดขายและลูกค้าออกนอกเครื่อง ขณะที่รายงานปิดกะ 80mm มีข้อมูลเดียวกันอยู่แล้ว ไม่พบหลักฐานว่าเป็นปัญหา
- **งานใดก็ตามที่ต้องพึ่งการตรวจสลิปของ vendor เพื่ออนุมัติบิลอัตโนมัติ:** ขัดกับการตัดสินใจของเจ้าของที่บันทึกไว้ใน `qr_payment_panel.dart:10` ("No confirmation step") ต้องให้เจ้าของเปลี่ยนการตัดสินใจนั้นก่อน

## 6. คำถามถึงเจ้าของ (ตอบได้ในบรรทัดเดียว)

1. ร้านจดทะเบียน VAT หรือไม่ (`taxRate 7` ใน settings เป็นค่าจริงหรือค่าตั้งต้น)
2. ตอนนี้เครื่องในร้านอัปเดตเป็น build ใหม่อย่างไร และล่าสุดอัปเดตเมื่อไร
3. ร้านใช้กี่เครื่องในการขาย (เครื่องเดียว หรือหลายเครื่องแยกฐานข้อมูลกัน)
4. บัญชีรับเงิน QR อยู่ธนาคารไหน (บัญชีบุคคลหรือนิติบุคคล) และ statement ออกมาเป็นไฟล์แบบไหน (CSV/Excel/PDF) — ยังไม่ยืนยัน
5. เคยเจอสลิปปลอม หรือลูกค้าแจ้งว่าโอนแล้วแต่เงินไม่เข้า กี่ครั้งต่อเดือน
6. ปิดกะแล้วเงินขาด/เกิน บ่อยแค่ไหน และปกติขาด/เกินเท่าไร
7. ช่างที่มีเครดิตมีกี่คน เงื่อนไขชำระกี่วัน และตอนนี้ทวงเงินอย่างไร
8. รายจ่ายของร้านส่วนไหนที่ไม่ผ่านลิ้นชัก (ค่าเช่า ค่าแรง ค่าไฟ ฯลฯ) และตอนนี้จดไว้ที่ไหน
9. มีสำนักงานบัญชีหรือคนทำบัญชีให้ร้านไหม เขาต้องการไฟล์อะไรจากร้านทุกเดือน
10. เคยตรวจนับสต็อกทั้งร้านไหม ถ้าเคย ทำปีละกี่ครั้ง
11. ส่งข้อมูลลูกค้า (รูปสลิป/statement) ไปผู้ให้บริการภายนอกได้ไหม หรือต้องอยู่ในเครื่องเท่านั้น (PDPA)
12. ส่ง PDF ใบแจ้งยอดช่างทาง LINE ได้ไหม หรือให้พิมพ์ยื่นให้เท่านั้น (PDPA: มีชื่อและยอดหนี้)
13. ขอให้พนักงานหน้าร้าน 1 คนเล่าว่า "งานไหนน่าเบื่อหรือเสียเวลาที่สุด" 3 ข้อได้ไหม (ตอนนี้ยังไม่มีคำบอกเล่าโดยตรงเลย)
